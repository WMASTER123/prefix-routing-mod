## 2. 最终交付与首版范围

### 2.1 应交付的内容

1. 一个预构建、可独立启动的 Router 制品，含强基础策略、状态适配和可开关的优化。
2. 必要时才提供的独立 observer 制品；原生事件足够时无需安装。
3. 最小配置、启动示例、能力预检、故障诊断及关闭/回退说明。
4. CPU 测试、模拟后端、NPU 功能脚本、性能实验入口及证据导出。
5. MOD manifest/metadata、兼容矩阵、依赖与来源清单、真实生效证据。
6. 可复现的基线与增量实验报告，说明优势、无收益条件和未覆盖范围。
7. 与制品版本匹配的最小后端能力报告；若后续方法依赖成本预测，再提供执行配置指纹和校准档案，明确适用范围与回退。不要求先建立完整预测体系，也不要求用户手填底层算子参数。

产品可以包含多个制品；正常使用者无需修改引擎源码，也不应为了安装而自行编译路由宿主。

### 2.2 首版的明确边界

- 验收文本 Chat Completions / Completions、流式和非流式响应；工具描述等影响模板的字段按声明范围透传，不执行工具。
- 首先验证一个同模型副本池。多模型池隔离可以保留接口，但未测试前不宣称完整支持。
- 必须处理取消、超时、失联、重启、排空、有界接入和状态降级。
- 必须有一个经验证的精确前缀配置；无法达到时可以提供基础模式，但精确路由里程碑仍标记未完成。
- 后台计划有独立开关、版本和有效期；它可以保留为实验能力，默认开启须通过收益验收。
- 首版一个 Router 进程；进程故障的客户端重连说明必须有，多 Router 高可用不计入本版承诺。
- LoRA、多模态、混合注意力、特殊 KV 布局、复杂租户配额不作为首版性能验收范围；不能识别的身份必须进入已定义的受限模式或明确拒绝，不错误合并缓存域。

### 2.3 三个不同的完成标志

| 标志 | 完成条件 |
|---|---|
| 可用闭环 | 两个及以上真实副本，正确请求处理、可信状态/明确降级、基础路由、安装预检、完整测试入口 |
| 优化成立 | 在预先约定的负载与评价口径下，相对强基线有可重复增量，且退化与控制成本在约定范围内 |
| 可发布 MOD | 干净安装、插件规范、实际启用与停用、支持矩阵、证据、来源与许可证均完成，并通过目标 Manager 的适用验收 |

能运行不自动代表有优势；某项后台增强无收益时可以关闭或移除，不用它的存在作为产品完成条件。

### P0：工程契约与规范映射

目标：让后续三人和 AI 使用同一份可执行约束。

- 建立需求编号、支持边界、状态模式和能力说明；沿用 F1–F12 与 M1–M8 作为追踪编号。
- 编写七类数据对象的契约与样例，明确字段单位、未知值、所有权、代次和错误语义，详见第 4 节。
- 确定组内 MOD 中外部 Router 的合法描述/Provider/host contract；明确 Router 自身策略扩展与引擎插件的不同加载位置。
- 建立单一项目仓库的基本目录、锁定依赖方式、PR 模板、CPU CI、测试结果格式和最小模拟后端。具体包布局随 P1 选型落实。
- 记录规范来源提交；建立支持矩阵，初始全部标记待验证。

- 将语义兼容域、缓存布局/事件协议与性能配置分开；先落实基础接入需要的能力与身份字段。ExecutionProfile 仅在选定方法需要时细化，不作为基础闭环的前置实现，不增加逐请求控制服务。
- 补基础接入的设备无关 CPU 合同用例：未知字段、身份不匹配、数据源不覆盖、不同 block size/rank 映射；档案过期、图缺测等测试随实际采用的增强功能引入。mock 不能证明对应 NPU 能力。

交付：范围清单、接口契约 v0、规范映射表、最小 CI、模拟后端、任务模板。

通过条件：样例能被校验；安装/发现测试可在无 NPU、无目标引擎的 CPU 环境执行适用部分；所有未知接入点有明确验证任务。若 Manager 未提供外部 Router 契约，可继续独立 Router 验证，但不得把 Manager 准入项标成完成。

- 同步提供最小安装包、配置预检和观测指标，使第二位成员能在干净环境复现。
- 建立直连、仅代理、基础路由的开销基线；固定一组小型冒烟负载和证据目录。

- 在同一 NPU 后端建立必要基线：缓存复用、代理开销先测；第 7.5 节 N1–N4 按实际风险和待选方法逐步执行，不阻塞最小链路。eager 可先做功能探测，但不能作为对比已优化后端的唯一性能基线。
- 先接两卡两个 TP=1 副本，按已确认逻辑映射分配；压测与 Router CPU 竞争可测且有界。可用闭环不要求先完成所有底层微基准，P4 前必须有目标执行配置的性能证据。

交付：基础闭环、模拟/真机功能报告、安装示例、分层开销报告。

通过条件：两个副本可正确接入，异常终态清楚，NPU 手动脚本有稳定退出状态和可机器读取的结果。此时可以演示服务，但尚未宣布精确前缀优化完成。

### P3：可信前缀状态与工作量账本

- 接入选定索引与原生事件；完成存入、移除、清空、代次变更、缺口恢复及容量上限。
- 将计划建立、已分派、实际观测驻留分别表达；事件不足时使用 unknown/受限信息。
- 建立请求工作量账本，处理预记账与真实执行的重叠、迟到结果、取消失败和旁路流量覆盖限制。
- 在请求发送前核对目的地代次；后台计划、索引与请求执行共享明确的身份规则。
- 输出能力模式与降级原因；加入唯一前缀持续流量、事件中断和 worker 重启测试。

- 将匹配 tokens、实际可跳过 tokens、分配 blocks、可回收 blocks 和 HBM 字节分开表达。实际可跳过量不可得则保留未知，不能把全命中请求仍需的后端工作省略。
- 执行档案更新或配置变化先判定影响：性能条件变化失效档案；缓存身份/协议变化失效相应索引；worker 重启由 epoch 统一失效。避免一个宽泛版本号同时误清所有状态或误复用旧成本。

交付：前缀匹配与工作量快照、恢复/对账实现、确定性事件测试及真实观测对照。

通过条件：可信身份不错误跨域匹配；过期/缺口状态不能无限期当成命中；账本最终可对账；索引、队列和历史有界。P2+P3 加基础策略组成第一个完整可用版本。

### P4：即时路由优化与强基线比较

- 在稳定契约上接入候选优化；先做离线决定回放与影子选择，检查合法性和计算开销。
- 保留同一底座上的 RR/P2C/cache-aware 等对照，选择实际较强者作为主要基线；原系统基线与同底座消融分开报告。
- 借助 P2/P3 数据再选择具体方法；每次引入一个可解释的增量，记录假设、适用条件和失败条件。
- 在真实服务中比较达标容量、分类延迟、完成率、额外 CPU 与缓存行为；检查冷请求和低复用负对照。
- 提供可靠的基础策略回退和配置版本记录。

- 每个论文/现有策略候选附迁移卡：原平台与假设、可借鉴机制、NPU 要重测的系数/阈值、可得状态、开销和退出条件。
- 先测“成熟基线在本机合理配置”“只用 NPU 校准”“加入阶段干扰状态”等最小增量；图/shape 输入只有低成本可得且有消融收益才纳入在线策略。不同时叠加所有机制。

交付：即时优化候选、校准档案、强基线结果、增量与负对照报告。

通过条件：正确性/资源限制全部通过；收益与噪声能够区分；默认策略依据测量确定。影子选择只证明逻辑与开销，不能证明它会形成更优缓存分布。

### P5：后台亲和控制

- 先运行有界历史分析但不发布计划，测纯后台成本；随后加入固定软亲和，再评估动态调整。
- 发布版本化计划，明确作用前缀、兼容域、实例代次、有效期及撤销语义。
- 即时决策继续执行健康筛选和拥塞逃逸；后台计算失败不阻塞请求。
- 测变化期间的额外重算、计划调整率、过渡期延迟和收益持续性。
- 分别验证“无后台”“只观察”“固定计划”“动态计划”及必要的变化约束。

- 同时查看 batch/上下文分布、Host 争用和有效缓存工作集变化；将图冷启动与 KV 重建分开归因。后台只能改变未来请求软偏好，不控制算子、图捕获或 token scheduler。

交付：可独立关闭的后台控制、计划接口测试、消融结果、默认开启或实验性保留的决定。

通过条件：旧计划/重启状态不污染新请求，资源有界，净收益成立才默认启用；否则保留接口、关闭无收益机制。具体控制方法在此阶段选择。

### P6：持续运行、跨节点与兼容加固

- 覆盖持续唯一前缀、极长/极短输入、慢客户端、频繁取消、事件积压、节点重启与状态恢复。
- 持续运行时间按实际申请时段和生产目标制定；以存量上界、内存趋势、队列积压、恢复耗时与尾延迟验收，不只观察进程是否存活。
- 安排至少一次跨两台服务器的验证；同机结果不外推为跨节点可靠性或扩展性。
- 增加第二档模型或配置以检查结论迁移；具体型号在容量验证后定。
- 针对官方 vLLM/Ascend 建立独立兼容验证；未完成时发布范围只列已验证的 HUST 组合。
- 对升级、回退、缺少观测和错误配置执行完整测试，记录支持与拒绝边界。

交付：持续运行与故障报告、跨节点结果、支持矩阵、故障处理手册。

通过条件：声明支持的范围全部有证据；未覆盖范围公开列出，默认配置中不启用未经验证能力。

### P7：发布候选验收

- 在离开源码目录的干净环境安装预构建制品；检查依赖、入口、静态发现与最小配置。
- 逐项核对 MOD/插件实现规范及目标 Manager 契约，验证启用、生效、停用和卸载的实际行为。
- 第二位成员按 README 独立复现基础闭环与代表性实验，第三位复核性能口径和原始证据。
- 整理兼容矩阵、已知限制、许可证/NOTICE、依赖与补丁来源、变更记录及基准复现说明。
- 固定候选制品哈希与对应提交；正式发布使用通过验收的同一制品。

交付：可供审阅的发布候选包与完整验收报告。当前私有源码仓库已建立；推送日常开发 PR 不等于正式发布。公开仓库、发布包和组内正式收录须在验收后按授权办理。

## 4. 三人协作前应冻结的接口语义

字段名称可以调整，但以下语义要有样例和契约测试。

| 对象 | 最低需明确内容 | 关键约束 |
|---|---|---|
| RequestFeatures | 请求 ID、兼容域、输入规模、可用 token/block 特征、精确度 | 模型/template/tokenizer 与额外身份一致；unknown 不等于 0 |
| PrefixMatches | 目的副本、连续匹配长度、来源、观测时间、覆盖度、代次 | 已分派不等于驻留；缺失记录不自动等于未缓存 |
| WorkerState | 可路由单元、健康、代次、负载分量、时间、覆盖范围 | TP rank 不独立充当完整副本；外部与本地计数不双加 |
| RouteDecision | 目的地、代次、决定 ID、策略/配置版本、原因 | 决定不等于已经发送；执行端检查合法性 |
| RequestOutcome | 对应请求/尝试、已发/可能接纳/终态、时间及错误类别 | 重复/迟到通知幂等；前端取消不等于后端已释放 |
| PlacementPlan | 兼容域、前缀作用范围、候选实例与代次、版本、有效期 | 是软偏好；过期、冲突、失效时退回即时选择 |
| CapabilityReport | 接口来源、已验证能力、受限原因、版本/配置指纹 | 可发现、可启用、真实执行和性能证据分别记录 |

另需明确：时间使用本进程单调时钟测间隔，跨主机时间不能未经校准直接相减；管理配置原子切换，身份配置变化使旧索引/计划失效；记录来源与序号处理乱序，而非假设网络按产生顺序到达。

每项接口由一位成员维护、另一位审查。变更先更新小型决策记录与契约样例，再改消费者；不用同时扩张全部模块的临时兼容字段。

### 4.1 Ascend 档案和数据分级

BackendCapability 是 M7 的后端描述，ExecutionProfile 是 M6 的校准产物；名称为规划，不是已实现 API。通过 CapabilityReport/WorkerState 引用，M4/M8 只读经过验证的版本。

| 信息 | 采集和使用要求 | 缺失/变化时 |
|---|---|---|
| 模型语义、缓存布局、执行指纹 | 分开记录；布局含已验证的 block/head/dtype/事件身份，执行含图、并行、调度预算、软件/硬件及 Host 条件 | 按影响范围失效；不得跨配置套用实测曲线 |
| 在线必要状态 | 健康/epoch/账本；精确模式额外要求有效前缀身份和可解释事件 | 无合法实例拒绝；状态不可信退基础模式，不虚构命中 |
| 在线可选阶段状态 | 未命中工作、活跃 Decode/上下文摘要、抢占、有效 KV 压力，均带时间/来源/覆盖 | 不可得为 unknown；不用设备利用率替代缺失阶段信息 |
| 离线诊断 | 图桶/回退/padding、Cube/Vector/搬运、布局与 HCCL 暴露成本 | 不强制安装常驻 profiler；仅在必要时采短窗口 |
| 校准结果 | 输入/并发范围、冷暖状态、版本、样本数/误差、单位、证据引用；不是单一 tokens/s 常数 | 失效、缺失或超出范围时回退；不阻止基础功能上线 |

不要求应用方了解 CANN 才能使用：最终 doctor 输出可执行的缺口说明和模式等级；生产配置读取已生成档案，而不是要求用户手填几十个评分权重。

## 5. 测试设计与 CI 接入

### 5.1 统一入口先于 runner

仓库已实现跨手动与 CI 的统一入口。cpu/integration 当前覆盖脚手架和合成后端；以下 NPU/性能/release 入口仍为保留占位，返回 not-run 与退出码 3：

```text
python tools/check.py --suite cpu
python tools/check.py --suite integration
python tools/check.py --suite npu-smoke --config <环境配置>
python tools/check.py --suite npu-routing --config <环境配置>
python tools/check.py --suite performance --config <实验配置>
python tools/check.py --suite release --config <候选制品配置>
```

该入口负责任务编排与报告，不替代 pytest、cargo test 或已有 benchmark。具体工具按最终语言和底座选定。CI 只负责调用、设备调度与产物归档，不能另写一套测试逻辑。

统一约定：配置先校验；退出状态明确；输出机器可读 summary 与必要的 JUnit/原始记录；结果区分 pass/fail/skipped/not-run/inconclusive。缺少 NPU 的任务不得自动变成通过；发布要求的测试未执行就不满足发布验收。

### 5.2 测试层次与触发

| 套件 | 环境 | 触发方式 | 阻止进入下一阶段的条件 |
|---|---|---|---|
| 格式/静态/构建/manifest | CPU | 每个 PR | 格式、类型、编译、声明或制品不一致 |
| 单元/契约/确定性状态轨迹 | CPU | 每个相关 PR | 身份、账本、索引、计划或配置语义错误 |
| 模拟后端集成 | CPU | 每个影响在线链路的 PR；主分支全量 | 流式、取消、异常、恢复或资源边界错误 |
| NPU 单副本冒烟 | 1 个可用 NPU | 适配/依赖/插件加载变更后，手动 | 引擎启动、APC、事件、插件生效不符 |
| NPU 多副本功能 | 2 个独立副本起 | P2/P3 等阶段验收及相关重大变更 | 路由、代次、事件映射或恢复失败 |
| 性能/持续运行 | 主实验池，独占时段 | 优化候选、重要回归、发布前，手动 | 可信的退化超门槛、资源无界、结果不足以支持声明 |
| 发布安装与 MOD | CPU + 声明宿主 | 每个发布候选 | 干净安装、契约、启停/回退或证据缺失 |

CPU CI 不要求下载大模型或占用 NPU。无硬件结果不能代替宿主测试；需要 NPU 验证的变更应附结果引用，必要测试未完成时暂缓相关合并或发布。

### 5.3 必须覆盖的高价值测试

- 身份：模板参数、边界块、相同后缀不同前缀、不同兼容域、未知字段、超长输入。
- 索引：增加/移除/清空、缺失父链、重复/乱序事件、超出重放窗口、无 token 的快照、断流后恢复、新代次隔离。
- 账本：并发选点预记账、发送前失败、可能已执行的超时、客户端取消、后端未确认取消、重复终态、迟到回执。
- 执行：SSE 不被聚合缓冲、慢客户端背压、错误透传、健康变化、排空、无可用副本和有限等待。
- 计划：过期、乱序发布、实例代次变化、前缀范围重叠、后台失败、关闭增强及拥塞逃逸。
- 资源：唯一前缀长期输入、事件过载、历史窗口与指标标签上限；故障不引发无界缓存或队列。
- 插件：未启用无副作用、重复注册、目标进程实际执行、版本不匹配、资源冲突、kill switch、干净安装与关闭重启。

对事件状态机使用固定种子轨迹/性质测试；并发测试围绕实际竞态，不靠短 sleep 碰概率。协议测试检查响应语义和生命周期；不同副本/批处理下生成文本可能存在数值与采样差异，不把所有端到端响应逐字相等作为路由正确性的唯一标准。

### 5.4 接入 NPU CI 时的条件

先用手动脚本积累稳定结果，再接受控 runner。测试任务使用设备锁/预约，记录当前运行者、设备和配置；超时后只清理由本次任务创建的 PID/容器。外部贡献的未审查代码不直接运行在带服务凭据的共享 NPU runner 上。

CPU 的目标体系结构必须记录；若 NPU 服务器为 aarch64，x86 构建成功不等于发布制品已可安装。真实安装测试覆盖声明支持的目标架构。无新增故障或变更时不反复重跑昂贵套件。

### 5.5 Ascend CI 与组合验收

CPU PR 检查增加档案/能力 schema、指纹失配、单位、unknown、状态失效及文档引用；这些测试按接口实现逐步落地，不将本次规划算已覆盖。硬件阶段按目标场景分层：

- npu-smoke：完整版本指纹、设备映射、正确性、目标模型最小组合、APC 冷/热对照及实际事件样本。
- npu-routing：两个独立副本的协议/取消/重启/恢复，重点覆盖已声明的图+APC+chunked prefill 组合，事件开关有独立对照。
- performance：固定资源和执行档案；低复用、热点、上下文变化、混合阶段及图形状边界；报告 Host、有效 KV 和控制开销。
- release：目标 aarch64 制品、必要 CANN 依赖边界、真实引擎加载与关闭、能力缺失时的正确降级。

不要求穷举所有 dtype×图×模型×并行组合。先固定一套主配置，再以配对/风险驱动用例覆盖声明范围；不支持或未测的组合从支持矩阵排除。异步算子微基准在适当边界同步，正式服务不每请求同步；profiler 开启/关闭分别计量，不拿带采样运行报最终成绩。

## 6. MOD 与插件实现规范

### 6.1 规范映射在 P0 完成，运行证据逐阶段补齐

2026-10-10 核查的 extension-template 区分 `in_process_plugin`、`kv_service_adapter` 和 `import_only`；KV 服务适配器围绕 connector 配置及外部服务检查。**外部请求 Router 是否已有对应 contract，必须单独查明，不能仅因它也是外部服务就套用 KV connector 类型。**[模板说明](https://github.com/vLLM-HUST/extension-template/blob/0d537f3193f217b21cf730a32f0a2629b631244b/README.md)

若已有适用契约，按它实现与测试；若没有，形成最小契约提案与缺口记录，交由组内流程确定。在契约成立前，允许独立 Router 功能和性能工作推进，但对应 Manager 扩展须保持不可错误启用，不能宣称完整准入。禁止用更换名称绕过契约。

### 6.2 实现要求与验收映射

| 要求 | 实现与验证方式 |
|---|---|
| 描述与执行分离 | 静态发现不启动模型、网络线程或外部服务；metadata、manifest、README 与实际入口一致 |
| 默认关闭 | 安装/导入不改变引擎；显式启用；补丁 kill switch 优先；启用状态与机制真正安装分别验证 |
| 可重复注册 | 注册幂等，不多次包装函数，不重复订阅或启动线程；资源释放有确定生命周期 |
| 版本守卫 | 固定已测试宿主及配置；必要补丁检查真实目标签名/实现；不匹配则拒绝对应机制 |
| 资源与依赖 | 如实声明冲突资源和扩展依赖；不自动启用依赖，不争夺 Ascend 平台插件职责 |
| 进程边界 | 逐目标进程验证实际加载与执行，证据含 PID/机制/版本；API server 有日志不代表 worker 已生效 |
| 小型适配 | 原生接口优先；确需补丁时聚焦单一机制，不替换整套 scheduler/worker 取得普通指标 |
| 等价与差分 | 观测补丁以固定宿主原行为作对照，验证原返回值、异常、参数转发及副作用；来源保留归属 |
| 关闭/回退 | 区分运行时策略回退、入口切回和引擎插件关闭后重启；不承诺任意热卸载 |
| 外部生命周期 | Provider 仅使用适用契约允许的 plan/render/check；不擅自启停或清理共享外部服务 |
| 可复现交付 | 干净环境安装/发现/启用/运行/停用；限定支持范围与必要配置 |

来源：[Extension 审查清单](https://github.com/vLLM-HUST/extension-template/blob/0d537f3193f217b21cf730a32f0a2629b631244b/CONTRIBUTING.md)、[Patch 模板](https://github.com/vLLM-HUST/patch-plugin-template/blob/42908cc083c66b8daa766034c290ffb396b2558b/README.md)、[插件实践说明](https://github.com/vLLM-HUST/patch-plugin-template/blob/42908cc083c66b8daa766034c290ffb396b2558b/docs/PITFALLS.md)。差分等价针对被适配的原功能；新路由策略不要求与基线选择相同 worker，而要满足共同正确性约束。

vLLM 的 general/stat logger 等插件按目标版本真实接口选用，注册入口需可重入。插件 allowlist 保留必要的现有插件；不能创建另一个 platform plugin 覆盖 Ascend。进程加载策略要检查目标宿主，不能直接泛化模板中的 spawn 处理方式。[官方插件说明](https://docs.vllm.ai/en/latest/design/plugin_system/)

## 7. NPU 资源与实验方案

### 7.1 资源申请和环境冻结

当前没有 NPU，先使用 CPU 资源完成 R1。进入 G2/G3 时申请 1 张卡，G4 两个 TP=1 副本申请 2 张；四副本扩展须在基础闭环和收益成立后另行评估。TP=2 的两卡实例仍只有一个路由目的地。历史物理卡映射不用于当前操作，重新申请后独立核验。

用户指定主模型为 `/data/shared_models/Qwen2.5-14B-Instruct`，直接只读使用，不复制权重；配置为 Qwen2ForCausalLM/BF16，模型 revision 不能由目录名推断。初验 TP=1、最大序列长度 8192，具体容量以运行证据为准，不合适时先讨论，不自行改回 7B。每卡 64 GiB HBM 不是 KV 专用预算。16 核是 CPU 时间配额，cpuset 当前 0–191，不等于独占 192 核；评估分词、引擎、Router 和压测争用。

实验前记录设备映射、驱动/固件/CANN 组件、CPU 配额、模型来源/配置、图/Attention/缓存/并行有效配置、软件提交、网络/事件接线及独占窗口。镜像 digest、模型 revision 无法取得时明确未知，不伪造来源；已记录宿主上的研发基线与可移植发布制品分开验收。预装环境、项目 CPU venv 和隔离推理环境分别记录，开发与基准环境分开。

服务器访问使用本项目明确提供的新目标与授权边界；本计划不沿用其他项目的 SSH 别名。测试清理只针对本次运行管理的进程/目录/容器。

### 7.2 评价口径在正式优化实验前冻结

- 请求从客户端实际提交开始计时，Router 内排队计入 TTFT。TTFT 的第一有效输出定义须覆盖声明支持的文本/工具字段；heartbeat 和纯元数据事件不算内容输出。
- 输出停顿按客户端可见的有效输出间隔统计，另报 TPOT；不将 SSE chunk gap 伪装成真实 token 间隔。
- 达标请求须成功完成并满足适用 SLO；错误、拒绝、超时都在原始到达请求结果中保留。外部主动取消与超时诱发取消分别统计，不能靠剔除失败提高容量。
- 用固定到达窗口及完整后续收尾结果计算该请求队列的达标率与有效请求速率；处理尚未终结的请求，避免窗口边缘截断产生虚高。可持续容量还要求队列不持续增长和完成率达标。
- TTFT/停顿阈值、不同长度类别口径、性能退化容忍度先经基础校准确定，再对所有方法固定。没有业务 SLO 时报告多个明确阈值下的曲线，不在结果出来后只挑有利阈值。
- 记录输入/输出长度、生成设置、APC、chunked prefill、图模式、并行度、引擎缓存容量及控制器 CPU 资源；对照双方保持一致。

### 7.3 工作负载矩阵

| 负载类别 | 要回答的问题 |
|---|---|
| 低复用/大量唯一前缀 | 增强是否增加无收益成本，索引是否有界 |
| 稳定共享前缀 | 是否把缓存复用转化为容量收益 |
| 热点与突发 | 亲和是否引发拥塞，分流是否及时 |
| 热点迁移/工作集变化 | 调整是否值得，过渡期代价是否可控 |
| 长短输入与长短输出混合 | 是否保护生成停顿、冷请求与低频请求 |
| 多轮/依赖请求 | 是否保持会话因果，避免未来请求提前泄露 |
| 超出缓存承载的工作集 | 是否减少反复重算，而非只在全部装得下时有效 |
| 失联/重启/事件延迟 | 性能与状态能否恢复，受限模式是否可用 |

公开数据用于内容真实性，受控/半合成数据用于复用和变化机制；具体数据集在选取阶段检查许可、字段和代表性。校准集与正式评测集分开，固定版本和种子。在线策略只能看到当时可用信息，不能读 trace 的未来请求或真实最终输出长度。

### 7.4 基线、消融与证据

至少包含直连/仅代理开销、基础负载策略、成熟 cache-aware 策略、当前优化，以及后台开关消融。同底座实验隔离策略增量，原系统对照体现整体工程效果，二者不可混写。基线同样合理调参。

基线与候选顺序使用同一组独占设备；分别建立预先定义的冷/热状态，并交替运行或使用 ABBA 等顺序控制漂移。混用同一缓存池的逐请求 A/B 会互相影响，不用于证明放置策略收益。

重复次数由噪声和所需精度决定；保存各次结果与离散程度。差异不能与噪声区分时标记“未证实”，不写增幅结论。严格性能 CI 阈值在稳定环境形成后启用，共享环境结果作为诊断或不确定结果。

每次实验保存：项目及依赖提交/dirty 状态、环境与硬件、模型/模板版本、配置/命令、数据摘要和种子、原始请求结果、服务指标、机制生效证据、报告与校验和。明确标注 microbenchmark、simulation、replay 或真实服务端到端实验，真实模型上的回放也要说明负载为回放。可参考[组内报告模板](https://github.com/vLLM-HUST/patch-plugin-template/blob/42908cc083c66b8daa766034c290ffb396b2558b/docs/REPORT_TEMPLATE.md)。

### 7.5 进入优化前的最小 Ascend 实验

下列 N 编号是本工程验收，与 [NPU 知识应用摘要](../ascend-design.md) 的学习实验 E0–E10 对齐。不能要求团队先完成全部算子/通信研究，也不能跳过与实际路由收益直接相关的服务校准。

| 编号 / 阶段 | 实验与约束 | 必须获得的产物 |
|---|---|---|
| N0 / P1b | E0：环境和支持矩阵；单副本基础正确性，物理/逻辑/rank/端点映射 | 完整能力描述，失败组合明确记录；包可导入不算通过 |
| N1 / P1b–P2 | E3/E8：固定总上下文，扫有效复用/后缀；另固定后缀扫已缓存上下文，包含全命中边界 | 实际命中、未计算/仍需计算的区别及 TTFT 曲线；事件无字段则标未知 |
| N2 / P2 | E3/E4：固定配置扫 batch/上下文；目标支持的 eager/图策略独立对照，观测 shape 边界 | 有效执行配置、冷捕获/稳态成本、KV blocks 与内存；不从文档填支持状态 |
| N3 / P2 | E7：已有 Decode 中注入长 Prefill，目标 chunk/budget 固定并记录 | 新请求 TTFT、已有请求可见停顿、恢复时间和请求轨迹 |
| N4 / P2 | Host：直连/仅代理/加观测/加索引；在实际 CPU 配额下运行，关闭 profiler 评分 | Router/分词/事件/后台成本，压测是否成为瓶颈，资源隔离建议 |
| N5 / P3–P4 | E8/E9：两个副本的缓存收益与拥塞取舍、唯一前缀负对照、工作集压力 | 本机强基线与校准档案；更新策略前冻结 SLO/误差与退化标准 |
| N6 / P3/P6 | E10：已声明图/APC 组合下事件延迟、取消、重启和目录恢复 | 正确性、资源有界、unknown/降级及恢复；不要求 NPU 错误注入影响整机 |

E1 小 GEMM 可用于基本能力检查和曲线归因，但不把达到理论算力作为验收。E2 搬运/布局仅在时间线表明有影响时深入；E5 量化/融合不是首版强制；E6 HCCL 在 TP>1 或通信瓶颈时执行。TP=1 多副本路由不因“要考虑 NPU”自动新增通信层。

区分模型已加载、图已捕获、KV 已热三种状态。至少比较“图已预热/KV 冷”和“图已预热/KV 热”；首次启动/捕获另报。需要清缓存时使用该后端支持且获准的测试方式，不能通过重启同时清除图后误称单纯 KV 冷对照。

冻结后端执行配置先于路由策略对比；另外评估图或 chunk 的实验必须单独分组，不把改变后端带来的收益记给 Router。正规主基线应包含本机合理配置的强 cache-aware 策略，不只对比 NVIDIA 参数原封不动的弱移植。

若 N1/N3 未显示足够的可优化差异，或通用强基线已经达到目标，就优先交付可靠适配与易用工具；不为区别已有系统强加形状感知或复杂后台。

以上是已确定的实验问题与验收方式，不是已经跑出的 NPU 成绩。

## 8. 三人团队与 AI 辅助开发

### 8.1 工作方向先划分，人员随后安排

|---|---|---|
| A：接入与宿主 | Router 复用、Ascend 整栈/实际路径、能力适配、生命周期、MOD 安装 | 向 B 提供可信字段与缺失语义，向 C 提供可运行制品和配置指纹 |

| C：验证与交付工具 | 模拟器、CPU/NPU 脚本、N0–N6 校准、强基线、报告与发布验收 | 验证测量/归因和 Host 竞争，维护可复现档案，不承担他人所有单测 |

### 8.2 给 AI 的任务必须可验收

每个任务说明包含：目标、适用提交/接口、允许修改的范围、输入输出、必须保持的行为、验收命令、所需证据，以及不包含的功能。任务规模控制在能够独立审查和回退的范围。

AI 开发遵循：

- 实现前读取项目约束与相关契约；引用真实 API，不根据最新网页臆造归档版本接口。
- 在各自分支/工作区完成改动，不能多人或多个会话同时修改同一共享 checkout 的核心文件。
- 不为了通过测试而同步放宽断言、删除失败用例或扩大兼容声明；变更契约须有独立理由。
- 对接口、线程/进程生命周期、超时/取消和索引回收的修改附针对性测试与解释。
- 最终报告区分已执行、未执行和失败的检查；没有 NPU 就明确缺少真机结果。
- 保留第三方源码来源和补丁范围，不把复制改名作为自主贡献。

人工审查重点是状态所有权、错误处理、复用范围、引擎影响和实验口径。格式、静态检查与常规回归交给自动化。每个合并 PR 至少一位其他成员审查；大范围接口改动先形成简短设计记录。

### 8.3 每个工作包的完成定义

代码可构建；相关契约与测试通过；错误/未知情况有定义；配置和用户说明同步；性能关键变更有开销证据；涉及插件有真实生效或明确待验项；另一成员能够复现；没有把待验项写成兼容承诺。
