## 1. 本轮明确的方向

**做一个以华为 Ascend NPU 为主要服务对象、接入 vLLM-Ascend 同构多副本的前缀路由 MOD：在可信前缀状态基础上，按目标 NPU 的实际执行成本、生成干扰和资源约束选择副本，使缓存节省真正转化为固定资源下满足延迟要求的服务容量。复用成熟外部 Router，但不继承未经 NPU 验证的性能参数、设备依赖和执行假设。**

用户本轮确认：

- 当前按用户指定 HUST 固定源码继续隔离验证；预装上游保留为历史对照，后续官方组合单独验收。版本选择不等于完整能力已通过。
- 遵循组内 MOD 的交付、启用、兼容、证据与回退规范。
- 独立确定合理架构，随后评估旧实现的复用；本轮不搬迁、修改旧代码。
- 当前不设计分层 KV、P/D 分离；首先明确组件和总体架构。
- 旧对话只用于核对 MOD 规范，不继承旧路由设计；附件七模块只是参考。优先复用，必要适配，自主设计优化增量。

沿用的边界：同构、多副本、池内同模型兼容配置；接入既有模型服务，提供启动示例和检查工具。设备申请、模型进程、算子、batch 调度、KV 分配与本地淘汰由原有部署及引擎负责。一个可路由副本可以是 TP 实例，不把 TP 内各卡当作独立目的地。

主指标仍是固定 NPU、Host CPU 和内存预算下，同时满足 TTFT 与生成停顿服务要求的可持续容量。分类延迟、完成率、公平性和路由成本构成约束。当前 2026-10-11 新机器为 4×910B2、每设备 65536 MiB HBM、aarch64、16 核 CPU 时间配额、128 GiB RAM；只验证过单卡基础配置，独占性和性能 SLO 未冻结。重新分配后须重核硬件映射。

### 1.1 与此前版本相比，具体修正什么

上一版重视通用保护，但没有把性能功能拆清楚：

1. “前缀身份与驻留目录”混合了请求特征生成和全局缓存查询，难以确定数据接口和代码归属。
2. “运行保护与观测”过于笼统，未明确谁维护在途量、谁更新健康、谁关闭策略。
3. 后台优化被放进泛化的可选清单，没有说明它向即时路由提供什么，也没有说明没有它时如何运行。
4. 扩展范围超过当前需要，分层、P/D、多引擎掩盖了本项目的主要功能。
5. 将 MOD 当作普通安装包装讨论，未对照组内规范和官方 vLLM 的实际宿主边界。

本版保留 M1–M8 作为功能职责编号，包括请求分析、缓存索引、工作量、即时决策、执行、评测、适配和后台放置；不以附件数量决定架构。功能完整不等于全部重新实现：转发与基础设施优先复用，状态接口与索引先适配，自主设计集中在优化决策及必要的控制契约。

### 1.2 当前真正要解决的工程问题

同一个请求有两个相关但不同的决策：

- 现在发给谁：当前可复用前缀、尚需 prefill 的工作、排队和活跃生成共同影响结果。
- 接下来类似请求主要落在哪些副本：长期过度分散会重复建立缓存，过度集中会拥塞，频繁换落点会重新预热。

现有工作已研究这两类问题。项目目标是把可用方法落入当前可安装、可测量的 vLLM/Ascend 部署，并验证是否有性能增量。不能先假定所有成熟路由都失败，也不能仅因借鉴既有方法就认定工程没有价值。

建议保留的性能主线是：**可信前缀感知 + 工作量感知选点 + 有证据时启用的稳定亲和/渐进调整**。缓存干扰分析用于判断哪些调整值得做；不要求一开始就建立完整未来缓存预测器。

### 1.3 昇腾优先不是重写底层，而是改变决策依据

依据已阅读的 [NPU 知识应用摘要](../ascend-design.md)，原方案须补上“从缓存命中到实际节时”的硬件与执行桥梁。普通 dense 模型中，即使命中长前缀，未命中后缀的 Attention 仍可能读取已缓存的上下文，后续 Decode 也仍需访问历史 KV；省下多少 token 不能直接乘 NVIDIA 实验的常数换成毫秒。

| 影响因素 | 必须进入的设计边界 | 当前不做的事情 |
|---|---|---|
| Cube/Vector、搬运与算子 shape | M6 校准目标模型的 Prefill/Decode 曲线；M3/M4 使用有适用范围的档案 | Router 不调度 AI Core、不读写 UB/L1、不自行改 Tiling |
| ACL Graph、执行模式与 padding | M7 记录实际执行配置，M6 测形状边界；图预热和 KV 预热分开 | 不照搬 CUDA Graph 参数，不逐请求改捕获桶或为了凑 batch 无界等待 |
| 有效 KV 预算 | M2/M3 使用后端 blocks/占用语义，区分活跃与可回收缓存；包含图、workspace 等预算影响 | 不将整卡 HBM 空闲量直接当 KV 容量，不假设固定 block size |
| Host 下发、分词和 CPU 竞争 | M5/M8 有开销预算；在本机 CPU 配额和亲和条件下验收 | 不在在线路径运行 npu-smi/profiler/设备同步，不抢占引擎必要 CPU |
| Prefill 对 Decode 的干扰 | M3 保留阶段分量；M4 比较目标 NPU 上的真实收益/退化边界 | 不把“Prefill 必定算力瓶颈、Decode 必定带宽瓶颈”当规则 |
| TP 与 HCCL、设备映射 | M7 确认整个副本的端点、rank 和代次；TP>1 时再测暴露通信 | 首验 TP=1 不强加通信优化；不逐请求改变 TP 或绑定策略 |

ACL Graph 的捕获/重放、形状覆盖和 padding 由 Ascend 后端实现，不能用接口字段中出现 cudagraph 就推定 CUDA 语义；同一文档中的历史限制也不能外推到本机 CANN 9.1.0。[Ascend 图设计](https://docs.vllm.ai/projects/ascend/en/v0.18.0/developer_guide/Design_Documents/ACL_Graph.html)

工程特色调整为：**通用路由基础设施 + Ascend 能力与执行档案 + 可信缓存/阶段负载状态 + 可证明净收益的路由增强**。这是待验证的工程方案，不宣称 NPU 专属算法创新或必然优于已有系统。

### 3.0 实现分区与复用原则（本轮补充）

| 实现分区 | 承载功能 | 实施判断 |
|---|---|---|
| 单一路由宿主 | M5、M3 的基础健康与生命周期、基础策略及配置观测 | vLLM Router 为第一评估候选；不重造完整网关，不串联多套代理 |
| 状态与身份适配 | M1、M2、M3 状态对账、Router 侧 M7 | 复用 tokenizer、原生 KV 事件与已有索引；补身份、协议、代次、恢复及隔离契约 |
| 优化扩展 | M4 增量策略、M8 后台控制、必要工作量账本 | 本项目负责效果与控制边界，具体方法可借鉴，不要求逐行自研 |
| 工具与 MOD 交付 | M6、M7 包装/预检/兼容与证据 | 复用成熟评测工具和组内规范；只有确实缺观测才新增引擎插件 |

2026-10-10 的静态核查显示指定归档引擎有 KV 发布、重放与快照相关调用，候选 Router 有 KV 索引；这些仍是待验收的复用候选。必须继续确认 Ascend 实际 scheduler/worker 路径使用了哪些接口，不能用上游 CPU 定义替代 NPU 运行证据。复用明细和固定源码依据见[专项评估第 3–5 节](./组件复用与自研边界评估_2026-10-10.md)。

逐请求策略和索引查询优先同进程执行；不默认访问远程控制器。底座若需大规模修改才能接入请求上下文与生命周期，则否决该候选。完整功能清单不等于已经冻结语言、底座版本或每个包的目录。

后台统计不能长时间占住前台所需锁或 CPU；如果实现语言的线程模型不能隔离计算，需要有界增量处理或独立计算进程。现在不以“开一个线程”作为已经解决开销问题的证据。

### 3.1 两类档案，不新增一个逐请求网络服务

- **BackendCapability（M7 维护）**：硬件/设备映射、完整软件组合、模型及缓存语义、配置是否支持/实测、原生接口可得性。能力预检可失败或 unknown，不能靠安装包版本自动填“支持”。
- **ExecutionProfile（M6 产出，M7 校验、M3 引用，M4/M8 消费）**：在固定环境/执行配置下测得的服务曲线、适用输入与并发范围、采样数、误差或置信范围、证据位置。它不是设备理论峰值表，也不是强制某种预测算法。

七类数据对象保持不变。能力描述先实现接入需要的最小字段；ExecutionProfile 仅在选定优化需要成本估计时实现，不是基础 Router 的必装组件或 P2 前置条件。采用档案时在配置加载处解析、在线只读；缺失或超出适用范围则回基础策略，不凭空精确估时。

区分三种身份：语义兼容域决定是否可能复用；缓存布局/事件协议标识决定能否解释目录；执行配置指纹决定能否使用性能档案。权重/模板/布局变化按相应契约失效；仅更换 CPU 亲和或图策略时首先失效性能档案，不自动认定 KV 语义变化。若该变化触发 worker 重启，再由 epoch 使旧驻留和计划失效。

### 支撑设施的功能与归属

这些是必须实现的工程功能，但不再和性能模块混成一组模糊组件。

| 支撑设施 | 具体要求 | 负责位置 |
|---|---|---|
| 配置与管理 | 参数校验、版本化快照、明确可在线切换项；模型身份/哈希规则改变须失效旧状态，必要时重启 | M7 提供启动校验，M4/M8 接收运行配置 |
| 观测与诊断 | 健康、模式、降级原因、选点/转发分段耗时、事件积压、CPU/RSS、错误；日志采样、指标标签有界 | 各模块产出，统一观测设施汇总；M6 消费 |
| 安全与隔离 | 管理接口鉴权、凭据保护、缓存隔离域；默认不记录原始 prompt/输出；token/hash 元数据也限制访问 | M5 接入、M1/M2 隔离、M7 部署 |
| 资源与停机 | 输入、连接、队列、索引和历史均有上限；排空停止新接入并处理在途结果；启动时无法恢复的状态标记未知 | M5 生命周期，M2/M3 状态，M8 后台预算 |

首版不要求 Redis、Kubernetes 或大型监控平台。单 Router 是明确的首版边界，多 Router 共享账本和高可用不在本轮伪装成已完成能力。

### 一次正常请求的完整链路

1. M5 完成认证上下文、请求大小/超时检查，保留原始请求体和调用语义。
2. M1 生成与池配置一致的特征；不能准确识别的输入标记为不支持精确匹配。
3. M3 提供健康、兼容、未排空的实例集合；M2 查询这些实例的前缀状态。
4. M4 读取当前计划，计算候选；必要时越过软亲和，选择全池合法实例。
5. M5/M3 以一次明确的提交记录在途工作，复核实例代次与可用性，再执行发送。
6. 响应实时转发；M5 产生完成、失败、取消或结果未知的生命周期事件。
7. M3 对账，M2 接收真实缓存事件；M8 异步汇总后判断是否修改未来的软计划。
8. 观测记录策略版本、状态质量、选点理由及结果，供 M6 复现实验使用。

前缀目录与放置计划都只影响目的地，不替代引擎验证缓存正确性；即使目录估计错误，引擎也必须按自己的有效性规则命中或重算。

## 4. 八个组件的详细设计

### M1：请求解析与前缀特征提取（Prefix Analyzer）

回答：这个请求有什么可匹配的前缀，还有多少输入工作？

输入：业务请求、模型与 tokenizer/template 配置、适配器提供的缓存键规则。
输出：RequestFeatures，包括兼容域、token 数、可得 token/block 链、请求类型、精确度、可选会话提示。

主要功能：

- 支持首版验收的文本 Chat Completions / Completions，保持系统提示、工具描述、多轮角色和模板参数语义。
- 在路由确实需要 token 信息时使用匹配版本的模板与 tokenizer；输入已经是合法 token IDs 时避免再次编码。
- 构造链式前缀身份，纳入模型/配置域、块粒度、隔离盐和所支持的附加身份。
- 复用一次请求内的解析与编码结果；可使用有界结果缓存，记录 CPU 时间和内存。
- 不能以“文本前半段 tokenization + 新后缀 tokenization”简单拼接替代完整编码；跨边界 token 合并等情况要差分验证。

**边界修正：**M1 负责生成查询键，不负责维护每个副本的前缀树。最长可复用前缀的查找由 M2 承担，避免两处索引不一致。本地自定义哈希不能未经映射就与引擎事件哈希直接比较。

最低验收：相同请求在 Router 与固定后端版本得到一致 token 身份；模板差异、租户盐、边界块、超长输入不会错误匹配；额外 tokenization 成本单独计量。

### M2：前缀缓存索引与状态管理（Prefix Cache Index）

回答：哪些副本可能复用多少输入，依据是什么、信息有多旧？

输入：M1 的查询特征；M7 的缓存事件；M3 的实例代次失效；必要的请求历史。
输出：PrefixMatches，每个副本包含连续可复用范围、证据来源、观察时间、覆盖度和未知部分。

内部包含：

- 事件驱动目录：建立、移除、清空、代次变化；按真实可路由副本记录，不把 TP rank 上的部分事件误算成整副本完整缓存。
- 历史估计目录：兼容/降级使用；根据已执行请求估计可能驻留，单独标注，不冒充设备事实。
- 索引查询：检验完整依赖链及块边界，查询连续前缀；首版限定经过验证的缓存布局。
- 恢复与质量：乱序/缺口检测、重放窗口、重建标记、容量上限及过期信息处理。
- 可选短期移除记录：供 M8 分析重新建立，但不将全部移除都解释为可避免的干扰。

计划形成、已分派、观测驻留分别记录。派一个请求过去，不能立即把整个 prompt 标记为真实命中。事件索引“身份精确”也不意味着实时强一致。

如果无法证明事件覆盖完整，不用“查不到”断言不存在；采用已知下界或 unknown，并按策略保守处理。TTL 主要表达信息可信度，不等于真实引擎缓存的过期时间。引擎未提供快照时不得虚构完整重建接口。

最低验收：确定性事件轨迹能还原期望目录；移除、缺失父块、事件延迟、重启、重放缺口不产生无限期可信命中。

### M3：推理实例状态与在途工作管理（Worker Monitor & Ledger）

回答：有哪些合法实例，它们当前和刚接收的工作有多重？

输入：配置注册、健康/指标、M5 生命周期、可用的引擎请求进展。
输出：WorkerState 与候选集合；所有动态指标带单位、来源和时间戳。

四组功能：

1. 实例登记：地址、模型兼容域、worker ID、重启代次、ready/unhealthy/draining 状态。
2. 负载采集：可获得的等待/运行数、未完成 prefill 工作、活跃生成、抢占和 KV 使用等；缺失项为 unknown。
3. 本地在途账本：处理已选未发、发送中、已接纳、完成、取消及结果不明。
4. 校准数据入口：接收 M6 生成的设备/模型服务能力档案；为估计提供边界，不承担异构硬件调度。

NPU 型号、设备/副本映射、可用容量用于预检；低成本、带覆盖范围的阶段工作量和有效 KV 状态供在线决策，执行配置指纹关联 M6 档案。图桶/回退、算子瓶颈等默认是离线诊断项，只有接口可靠且消融显示增益才升级为在线输入。未知生成剩余长度不能由 max_tokens 冒充。不在每次请求中调用 npu-smi。当前没有 KV 传输，不加入传输带宽打分或跨节点搬运拓扑模型。

**所有权：**M5 是生命周期事件的产生者，M3 是负载账本唯一写入与对账者。选点后必须及时预记账。后端 running 与本地 outstanding 不能简单相加；无法判定重叠时保留分量，不宣称精确总量。

KV 使用率只能作为压力信号：空闲可回收缓存与活跃不可回收状态不同，高占用不自动说明容量不足。前端断开也不证明引擎已停止计算。

最低验收：突发分派不会全部看到同一份空闲；取消/错误/迟到回执不重复释放；外部旁路流量存在时报告账本覆盖限制。

### M4：即时路由决策（Routing Policy Engine）

回答：这个请求此刻应该发给哪个可用副本？

输入：RequestFeatures、PrefixMatches、WorkerState、可选 PlacementPlan、已验证配置。
输出：RouteDecision，含目的地、备选/回退原因、策略及状态版本；输出不等于实际发送。

固定执行顺序：

1. 硬筛选：模型/隔离、健康、排空、支持的输入形态，不由优化策略绕过。
2. 候选生成：结合命中位置、低负载候选与有效软计划；没有计划时仍完整工作。
3. 策略选择：比较可复用工作、剩余 prefill 和生成压力；策略接口不强制线性加权或预测时延模型。
4. 服务保护：拥塞、状态过期或计划不适用时扩大候选或回到基础策略。
5. 决定校验：不合法输出拒绝提交，交给明确回退流程；M5 负责实际执行。

候选策略包括 P2C/Least Load、亲和、Longest Prefix Match 诊断对照，以及 Cache + Workload 的强默认候选。Random/RR 用于回归与解释，不能作为证明性能优势的唯一对照。默认策略要由相同状态和开销口径下的测量选出。

同前缀请求并发到达时，可以读取已分派/预计建立的信息来避免无意识地扩大冷启动，但它不是 ready 命中，更不保证引擎合并并发 prefill。是否短暂等待或直接分流要单独测量，不能把所有同前缀请求串行化来获得好看的复用率。

不要求逐请求同步询问全部副本；读取快照。候选集合缩减也要检验遗漏更优节点的代价，不为降低查询复杂度强行限制任意固定个数。

最低验收：各种状态缺失均有明确路径；健康/隔离不会被长命中覆盖；策略切换可追溯；基础模式无需 M8。

Ascend 增量要求：有效复用收益必须考虑剩余输入长度、已有上下文和本池执行配置；NVIDIA 来源的吞吐系数、干扰阈值、batch 偏好只能作为待检验假设。Router 无法直接控制引擎下一步组成的 batch，不能以路由侧在途数断言图桶精确命中。具体使用表、规则或模型在 P4 决定，不现在设任意加权常数。

### M5：请求调度、转发与生命周期（Request Dispatcher）

回答：如何正确执行选点，并把请求结果还给客户端？

输入：原请求、路由决定；输出：业务响应及 RequestOutcome/生命周期事件。

包含接入和转发两端：必要认证、并发/请求体上限、连接复用、SSE 流式代理、有限等待、取消传播、超时、错误分类、实例排空期间的已有请求处理。业务生成参数与工具字段按已验证协议传递，不重写 prompt 或执行工具。

执行序列为“选择—预记账—发送—确认/不确定—终结/对账”。仅在能够证明未接纳，或协议提供对应幂等保障时考虑重试；已输出后不透明换副本，发送超时也不能自动等同未执行。默认不合并相同生成请求，不用响应缓存代替 KV 复用。

入口队列只用于有界接入与背压，不另做一套 token-level scheduler。等待进入客户端 TTFT；拒绝、丢弃和超时全部计入结果，不能用抑制冷请求换取表面容量。

若 Router 进程宕机，它无法自己执行回退。客户端重连或上游入口的故障切换需单独配置；当前单 Router 首版须明确其可用性边界，不宣称 HA 已实现。

最低验收：流式和非流式协议回归、客户端中断、半开连接、慢客户端、发送失败、取消失败、排空、进程退出均有定义。

### M6：性能校准、评测与实验工具（Benchmark Suite）

回答：哪里有损失，哪个组件带来多少净收益？

三类工具：

- 校准：固定引擎优化配置，获取单实例与多副本基线、可得负载指标、路由开销和模型输入输出范围。
- 回放：公开内容与受控负载，保存数据、到达过程、复用身份、会话依赖、种子和冷/热初态。
- 比较：策略、模块开关、故障注入、重复实验和分类结果，输出可复查证据包。

同时报告 TTFT、可见输出停顿、TPOT、达标容量、完成率、实际可得缓存复用、预估与实际差异、CPU/RSS/事件积压。SSE chunk 不一定等于一个 token，不能混淆 chunk gap 与逐 token TBT。

不得向在线策略泄露 trace 的未来请求和实际输出长度；max_tokens 也不是已知输出长度。公开内容被重新构造复用关系时标为半合成。影子选点不改变实际缓存，只能验证决定和开销；性能需独立 replay 或隔离池比较。

最低验收：相同配置可重复得到同类结论；观察模式、仅即时策略、静态计划、动态计划四种组合可独立运行；故障和负对照纳入报告。

Ascend 校准至少覆盖有效前缀复用、上下文/batch 变化、混合 Prefill/Decode、已支持图模式及有效 KV 预算，并测本机 Host 竞争。分离编译/捕获预热与 KV 热状态，采 profiler 的诊断运行不用于正式容量评分。微基准只解释服务曲线，不能单独生成上线阈值。

### M7：vLLM / Ascend 宿主适配与 MOD 集成（Integration & Adapter）

回答：怎样可靠获得信息、安装交付，以及证明扩展真的运行？

分为三个位置明确的子部分：

- Router 侧适配：协议客户端、事件订阅、指标读取、模型/配置描述的标准化，不承担路由评分。
- 可选引擎侧观测组件：只有原生信息不足且值得补充时加载；只补必要观测，不默认替换 scheduler/allocator。
- 交付适配：配置生成、doctor、包入口、Manifest/元数据、版本矩阵及启用/回退测试。

M7 负责“如何取得与解释原始数据”，M2/M3 负责“如何存储、查询与使用状态”。配置/Manifest 是部署契约，不直接嵌入业务评分函数。

新增 Ascend 能力核验：driver/firmware/CANN/算子包、torch/torch_npu、vLLM/Ascend 提交与补丁、实际 attention backend、图/量化/并行组合逐项记录。原生 KV 事件要验证是在何种缓存生命周期点产生，不能将 Host 提交等同设备完成或安全可复用。可选 observer 不允许在逐 token 路径增加全设备同步、搬回 KV 张量或与图捕获发生隐性副作用。

官方 vLLM 存在插件发现机制，但 entry point 不是任意内部调用点的稳定 hook。观测缺口需要核验原生扩展点、目标进程和调用位置；必要补丁单独声明与测试，不因为使用模板就变成官方稳定 API。[官方插件说明](https://docs.vllm.ai/en/latest/design/plugin_system/)

最低验收：干净环境安装、无需手改 site-packages、能力报告准确；安装而未启用不改变引擎；支持版本内功能和回退有效。

### M8：工作负载分析与持续放置控制（Workload & Placement Controller）

回答：相似前缀未来一段时间主要去哪些副本，什么时候值得改变？

该模块保留旧研究规划的性能内容，与即时路由分开。它是完整系统里的受控增强，包含三个内部职责：

1. 工作负载摘要：按有界前缀节点/族记录复访、输入后缀、实际可得输出、命中/重建和服务结果。不是把每个完整 prompt 永久存表，也不是依赖业务标签。
2. 计划生成：决定哪些前缀值得维持亲和、优选哪些实例、是否需要增加或减少优选落点；结合副本当前负载及过去计划。
3. 调整控制：限制变化规模、保留时间、迟滞与试探；观察服务结果，发布新版本、冻结或撤销建议。

输出 PlacementPlan：前缀作用范围、优选实例及必要导流建议、实例代次、版本、有效期、建立状态和停止条件。初期可以只有优选集合，不强制加入比例优化器。

计划不保证 KV 常驻、不修改本地淘汰、不搬运 KV。“增加前缀副本”在当前范围内只指让部分真实请求进入新目的地，由原生 prefill 自然建立缓存；“减少副本”是减少后续导流，不主动删除缓存。分流会产生额外重算，其成本须计入。

层级前缀可能重叠：同一请求只采用一个明确的有效计划作用范围，优先级规则固定，不把祖先/子前缀收益重复相加。同一物理缓存块的统计在可得范围内去重。

最低验收：M8 停止不阻断服务；计划过期自动失效；紧急拥塞立即允许 M4 越过亲和；低复用流量不会因缺少亲和计划被饿死。

Ascend 增量要求：扩大落点同时可能改变 batch 分布、Host 开销和有效缓存工作集。是否获益以本池端到端证据为准，不预设“摊得越开越好”或“集中到少数卡总能利用 Cube”。M8 不为预热图而发假请求、不改执行模式；CPU 紧张或两副本下无额外收益时保持关闭。

## 5. 状态与决定的所有权

| 对象 | 唯一负责维护者 | 主要读取者 | 必须避免的混淆 |
|---|---|---|---|
| 原请求、连接及执行结果 | M5 | M1、M6/M8 的受限记录 | 前端断开 ≠ 后端已结束 |
| 请求 token/前缀特征 | M1 | M2、M4、M8 | 文本相似 ≠ 精确可复用 |
| 观测到的 KV 目录 | M2 | M4、M8 | 计划驻留 ≠ 已观测驻留 |
| 实例健康/代次、在途账本 | M3 | M2、M4、M5、M8 | 本地预记账 ≠ 引擎资源预留 |
| 当前请求落点决定 | M4 | M5 | 评分成功 ≠ 请求发送成功 |
| 未来软亲和计划 | M8 | M4 | 有计划 ≠ 必须等待该副本 |
| 原始接口解释与版本能力 | M7 | M1/M2/M3、doctor | 接口存在 ≠ 本环境已验收 |
| 实验证据 | M6 | 开发者、使用者 | 微基准/模拟 ≠ 在线整机收益 |

接口建议围绕 RequestFeatures、PrefixMatches、WorkerState、RouteDecision、RequestOutcome、PlacementPlan、CapabilityReport 七类对象展开。这是数据语义，不是已冻结的代码类名。字段都有明确来源，未知值不能默认为零；跨进程数据带来源、时间与代次。

## 6. 快慢路径究竟有什么用

### 6.1 两个不同问题，不是两类请求

建议对外改称“即时路由”和“后台放置控制”，快慢路径只作为内部简称。

| 比较项 | 即时路由 M4 | 后台放置 M8 |
|---|---|---|
| 触发 | 每个请求 | 周期或持续变化触发，合并处理 |
| 决定 | 当前请求去哪里 | 一段时间内的前缀优选集合怎样调整 |
| 信息 | 当前请求与近期实例快照 | 一段历史、已有计划和调整结果 |
| 动作 | 一个目的地、越过软亲和、回退 | 发布有版本/有效期的软建议 |
| 主要收益假设 | 节省重算而不进入当前拥塞实例 | 减少反复改变分布和无收益副本建立 |
| 主要风险 | 指标过期或评分失准 | 计划滞后、误判需求、调整导致冷启动 |

**状态接收不是“慢路径”。**缓存移除、实例重启、健康变化及在途计数要及时更新，只是采用异步事件处理；不能等 M8 下一周期。M8 只负责较重的历史分析和计划，不拥有紧急安全决定。

### 6.2 一个四副本示例

以下为机制示例，不是实验结果。

- W0–W3 为相同模型副本；一个可重复使用的长前缀 A 近期在 W0 有缓存。
- A 的请求增加，W0 开始拥塞。M4 可以立即把部分请求送往其他健康副本，不等待后台计划。
- 若增加只是很短的尖峰，M8 可以维持原有计划；暂时付出少量重算，避免长期扩大亲和集合。
- 若压力持续且复用仍有价值，M8 提议 A 主要由 W0、W1 承接，并限制新导流规模。
- M4 在两者间依据实时状态选择；W1 的 A 尚未建立时视为冷启动，不能按命中评分；两者都拥塞时仍可用 W2/W3。
- A 降温后，M8 可减少优选落点；现有 KV 自然保留或被引擎回收。

该例只能说明职责。一个设计良好的即时策略也可能产生稳定分布，因此不能断言加 M8 必然更好。

### 6.3 已有论文是否使用类似做法

有，且有直接依据：

- Preble 第 4.1 节把重平衡和淘汰记账安排到后台线程，以保护逐请求调度；其全局/本地层次调度与这里的前台/后台也不是同一个划分。[Preble 原文](https://arxiv.org/html/2407.00023)
- CacheRoute 第 3.1 节将周期放置规划移出请求路径，请求执行查表与集合内负载选择；第 5.4 节同时指出重新规划会产生缓存重热代价。[CacheRoute 原文](https://arxiv.org/html/2608.19677v1)

所以，分离本身是可以借鉴的系统设计，不是我们的独创优势。值得争取的增量是：在目标 vLLM/Ascend 可得状态下，计划能否较少扰动有效缓存、在变化负载中维持收益，以及收益是否超过观测和调整成本。

### 6.4 优势成立的条件及代价

适合：有持续复用、变化有一定持续时间、现有路由产生多次无收益调整或分散，历史分析成本可摊销。

可能无益或有害：副本很少、没有复用、工作集轻松容纳、负载变化比计划更新快、原即时策略已足够稳定、后台与前台严重争用 CPU。

周期和保持时间不在本轮凭经验写死。需测量计划计算时间、状态延迟、负载变化尺度和缓存建立代价；找不到合理时间尺度时，关闭 M8。周期触发必须限频，不能每个请求都触发全局重规划。

### 6.5 怎样单独验证这项设计

| 对照 | 用途 |
|---|---|
| A：强即时路由，无 M8 | 性能与开销基线 |
| B：相同即时路由，加固定软亲和计划 | 区分简单亲和收益 |
| C：相同即时路由，加动态计划 | 检验随负载调整的必要性 |
| D：C 加渐进更新/变化约束 | 检验减少调整扰动是否有增量 |

对照保持相同引擎、流量、状态质量与资源；报告 CPU、计划变化率、过渡期重算、TTFT/停顿、分类完成率及达标容量。额外做“后台运行但不发布计划”观察模式，拆分纯分析成本。当前资源有限时不必实现一个逐请求全局优化器作为稻草人。

## 7. vLLM / Ascend 下怎样做成 MOD

### 7.1 产品、运行时和包装是三个层次

~~~text
产品 MOD
├── 外部 Router 制品：M1–M5、M8、Router 侧 M7
├── 必要时的 engine-observer 制品：只补原生接口缺口
├── M6 校准/评测工具
└── 包描述、MOD_METADATA、配置、证据与兼容报告

运行时
应用 → 外部 Router → 已验证的 vLLM / Ascend 宿主
                         │
                         └→ 原生观测，或显式启用的窄幅观测插件
~~~

一个产品可以有多个可独立启用的组件，不应把所有功能塞进“替换一个函数”的 patch template。能用原生接口就不安装补丁；确实需要补丁时，隔离为独立机制并固定宿主范围。

Router 与必要 observer 独立安装，避免安装 Router 就自动向所有 vLLM 进程注册副作用。已有私有仓库 WMASTER123/prefix-routing-mod；当前 Python 包仅为工具及 import_only 描述，尚未实现生产 Router，不能将包创建等同架构落地。

### 7.2 按能力逐项验收，不笼统说“支持 MOD”

| 层次 | 本项目需要做到 | 不能据此推出 |
|---|---|---|
| 可安装 | wheel/镜像和配置完整，离源码目录可运行 | 安装了就已启用 |
| 可发现/校验 | 元数据、Manifest 与实际依赖相符 | 官方 vLLM 支持 HUST 专有 contract |
| 可启动 | 外部 Router 由使用者启动；观测插件按已验证入口加载 | Manager 自动拥有外部服务生命周期 |
| 实际执行 | Router 有真实决定/结果记录；插件在正确 PID 内产出机制证据 | 仅有加载日志就证明性能提升 |
| 可关闭/回退 | 策略回退、Router 入口切换、观测插件重启关闭分别说明 | 一个开关能撤销所有已经执行的状态变化 |
| 有收益 | 固定环境下重复对照与负对照 | 模板测试通过等于 NPU 服务已验收 |

官方 vLLM 的 general/stat logger 等插件机制可作为适配候选，能否获取目标字段要逐版本验证。不要新增与 Ascend 平台插件争夺执行权的 platform plugin；不要通过覆盖其 worker 类来取得普通监控数据。插件 allowlist 也须保留部署中必要的其他插件，不能只留自己的名字。[官方插件类型与加载规则](https://docs.vllm.ai/en/latest/design/plugin_system/)

### 7.3 2026-10-10 核查发现的规范更新

指定对话《插件规范总结》最新摘要记录了 Manifest 0.3-experimental。本轮直接读取 Manager 当前源文件，文档已经要求新制品使用 schema_version 为 0.3，并保留 0.3-experimental 作为兼容别名。应以固定 Manager 版本及其 schema 测试为准，不直接照抄旧会话的字段值。[Manifest 0.3，固定文档提交](https://github.com/vLLM-HUST/extension-manager/blob/0e4939146d53bd24ce51459f7da2e6defd260832/docs/manifest-0.3.md)

遵循规范与 Manager 已支持官方宿主上的本组件是两件事。外部 Router 应选取经过核查的描述/Provider 方式；若没有对应有效 contract，不伪造 activation_ready，不冒用 scheduler-policy 或 KV connector。Manager 集成是独立准入项，不能用自定义 CLI 冒充已完成组内 Manager 激活。

若需要窄幅补丁，要求固定宿主、签名与行为测试、默认关闭、资源冲突声明及真正执行证据；发现机制和替换函数不是一回事。patch 模板只给骨架，不保证所有子进程自动加载。[组内 patch template](https://github.com/vLLM-HUST/patch-plugin-template)

停止 Router 的优化策略可以在进程内完成；已安装的运行时补丁通常需要新进程按关闭配置启动才能恢复，不能承诺热卸载。仅关闭 Router 也不会自动改变客户端入口。

### 7.4 必须区分两种失败处理

- 版本/身份/插件冲突等启动契约失败：拒绝启用相应能力，明确报错，不能绕过校验。
- 运行中事件迟到/缺失：标记缓存信息不可信，仍可在合法健康池内使用基础策略。
- 没有任何合法实例：返回明确不可用，不以“降级”为名跨模型、跨租户或投向错误实例。
- 观测组件故障：不得让无界队列反压引擎；记录丢失与状态失效。策略降级不等于容忍引擎进程内任意异常。

## 8. 功能实施优先级与方法空间

### 首个可用版本应包括

M1、M2、M3、M4、M5、M6、M7 的最小完整闭环，具备：

- 两个及以上独立副本的实际选点与正确响应。
- 一个经过核验的精确前缀/事件配置；若环境不支持，交付受限模式并公开限制，不能据此宣布精确路由完成。
- 一套强默认路由及低开销回退。
- 真实生命周期、重启失效、事件恢复/降级和有界资源。
- 启动预检、安装/停用说明、端到端对照。
- MOD 元数据与支持矩阵；Manager 准入是否完成单独报告。

M8 从当前架构就保留明确输入输出，不推迟到难以接入时再补。但先实现统计与固定计划，再做动态计划；是否默认启用由净收益决定。这样保留完整产品设计，也不把未验证的复杂控制塞入基础路径。

### 哪些方法需要后续选择

| 设计点 | 可借鉴方向 | 本项目要明确的条件 |
|---|---|---|
| 前缀身份/索引 | 原生块身份、radix/hash 索引、事件目录 | 与本版本 vLLM 一致，完整性、元数据规模与查询开销 |
| 即时选点 | Cache + Load、P2C、LMetric 类工作量指标 | 哪些状态真实可得，简单方法能否满足服务目标 |
| 亲和与候选 | Preble、DualMap 等局部性与拥塞思想 | 热点逃逸、未知前缀、候选遗漏及输出负载 |
| 持续放置 | CacheRoute 类周期规划、保持现有有效映射 | 前缀层级、调整成本、低复用流量和变化预算 |
| 干扰分析 | 近期移除/重建统计及工作集分析 | 相关性不等于因果，只有可避免损失才值得控制 |
| 成本校准 | 离线 profiling、在线有限统计 | 不要求能预知输出或精确预测每次完成时间 |

上述是参考方向，未同时选用全部算法。不要把 token、毫秒、请求数和显存比例无量纲地相加；也不为了统一公式强制训练预测模型。

## 9. 开发前审计与验收清单

当前无需服务器即可完成：协议字段范围、七类数据对象、模块所有权、配置与策略切换语义、候选网关底座的复用接口审计。优先复用成熟协议/连接库；选择已有 Router 底座与自有薄宿主之间的差异，应由模块能否接入及维护成本决定。

资源取得后，按顺序核验：

1. 收尾已验证 HUST 隔离候选的恢复入口，记录 CANN/驱动、模型与有效配置，再依次验收事件、单后端和双副本；不覆盖预装环境，官方组合后续独立验证。
2. 验证模板/token 一致、APC 实际行为、缓存事件、健康/指标及取消语义。
3. 列出每个状态的获取方式、时效、单位、缺失行为；证明后端事件能映射到可路由副本。
4. 测直接引擎、仅代理、加入状态观察、基础路由的分层开销。
5. 比较成熟基线，再验证 M8 的各个增量。
6. 做事件丢失、重启、失联、并发取消、流式错误及关闭增强的测试。
7. 完成干净安装、实际生效、回退和组内 MOD 准入证据；没有实际支持的版本不写进兼容范围。

2026-10-11 已新分配四张 910B2、16 核 CPU 配额和 128 GiB RAM；此前两卡清单保留为历史记录。主模型按用户要求使用公共 Qwen2.5-14B-Instruct，先单卡 TP=1，再双副本，再四副本；不自行换小模型，不把 TP=2 单实例当成路由验证。实际 revision、执行能力、KV 容量和性能逐项验收。

当前待定但不影响逻辑框架：

- 候选提交已指定，设备与部分安装元数据已盘点；完整兼容、图/缓存组合、接口运行行为和独占窗口仍须验证。
- 网关底座、实现语言和并发结构：完成接口审计与 CPU 基准后决定。
- 是否需要安装观测补丁：先检验原生能力，用户易用性要求不等于授权任意修改。
- TTFT、输出停顿口径与阈值：校准后冻结；正式比较使用相同合同。
- MOD 的 Provider/contract 与 Manager 支持版本：发布前单独验收。
- 是否有多模态或特殊缓存布局的首版刚需：目前按文本、经过验证的普通 dense 配置设计，未声称全面支持。

## 10. 当前结论与资料依据

当前可作为设计基线的是：**一个可复用的外部 Router 宿主 + 状态/身份适配 + 优化扩展 + 工具与 MOD 交付；即时选点、及时状态更新和后台规划相互分离。M1–M8 是职责目录，不是八个待重做的组件。**

不能提前确认的是：候选归档引擎组合已兼容、底座可以无修改接入所有优化、后台规划一定优于强即时路由、Manager 已能在目标宿主激活全部组件、以及未测硬件上的性能增幅。框架完整性与性能成功是两个验收阶段。复用选择及其否决条件见[组件复用与自研边界评估](./组件复用与自研边界评估_2026-10-10.md)。
