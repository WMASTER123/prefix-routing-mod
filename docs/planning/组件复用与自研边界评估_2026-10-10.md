## 1. 结论：做增量优化 MOD，不重造完整推理平台

建议的产品仍是接入现有 vLLM/Ascend 多副本服务的前缀路由综合套件，目标是提高固定资源下满足 TTFT、输出停顿和完成率要求的有效容量。

但实现原则应明确改为：**复用一个路由宿主及成熟基础能力，适配目标引擎的真实状态接口，把自主设计集中到状态如何影响决策、请求工作量与缓存收益如何协调，以及何时值得调整亲和。**

“自研责任”不意味着该部分每一行都重写。可复用的索引、统计、队列、策略组合接口和论文方法，仍应复用。项目成果是经过验证的优化闭环与易用交付，不是自建 HTTP 栈、tokenizer 或 radix tree。

vLLM Router 仍是第一评估候选，不是已选底座；Dynamo 的独立 KV 路由库、llm-d 的索引库保留为局部替代。NPU 主目标并不自动否决这些 CPU 组件，但必须检查最小依赖是否拉入 CUDA/NCCL/NVML、是否支持 Linux aarch64、是否暗含 GPU 指标/事件语义，以及本机 CPU 预算下的成本。不同时部署三套系统，不以“来自 NVIDIA”或“HTTP 能通”代替逐项判断。

### 1.1 本次修订改变什么

复用依次通过三个独立门槛：**能够构建运行 → 能正确解释 Ascend 服务状态 → 在目标负载与资源下值得使用**。第一个通过不能推出后两个通过。依据 [NPU 知识应用摘要](../ascend-design.md)，适配重点从“把事件格式接上”扩展为“能力、实际执行成本和有效容量有证据”；不扩展为重写算子、CANN 或设备内存管理。

## 3. 已核查的可复用能力，以及不能忽略的缺口

### 3.1 归档引擎已经有观测能力，先不要写新的 observer

指定核心提交中已经存在：

- KV `BlockStored`、`BlockRemoved`、`AllBlocksCleared` 事件；含 DP rank、group 等信息。
- ZMQ 发布与重放；扩展重放协议包含 publisher epoch、序号和快照。
- HTTP 前缀缓存事件上传器及快照对账，使用后台线程与有界队列。
- scheduler 中有发布器创建、事件发布和 shutdown 调用，不只是孤立定义。

因此第一条接入路线是复用原生事件，补 Router 侧协议适配和正确性检查；仅当目标字段确实缺失时才提出新 hook。[事件实现](https://github.com/intellistream/vllm-hust-legacy-20260831/blob/13f11da44455d2f85f00f810a04e1bd2eaf30ba6/vllm/distributed/kv_events.py)、[scheduler 接线](https://github.com/intellistream/vllm-hust-legacy-20260831/blob/13f11da44455d2f85f00f810a04e1bd2eaf30ba6/vllm/v1/core/sched/scheduler.py)、[事件配置](https://github.com/intellistream/vllm-hust-legacy-20260831/blob/13f11da44455d2f85f00f810a04e1bd2eaf30ba6/vllm/config/kv_events.py)。

**但源码接线不等于 NPU 运行验收。**仍须测哪些事件实际产生、事件时序、rank 到路由端点的映射、丢失恢复以及引擎 CPU 开销。后台发送不代表生成/编码事件没有成本。ZMQ 与 HTTP 不默认同时开启；选择一条验证过的主通道即可。

尤其要注意：该快照中的 `BlockStored` 可以只有块哈希，`token_ids=[]`、`parent_block_hash=None`。它能帮助对账块成员，但不能直接重建依赖 token 与父链的前缀树。消费者必须选择兼容的身份与恢复方式，不能看到“snapshot”就宣布目录可完整恢复。

### 3.2 vLLM Router 值得优先复用，但不能当作任意 Python 策略的即插即用宿主

本轮检查固定提交 `91b65ee4bdfbe98863a32a2205dced5dbb249ffe`，包括策略接口、工厂、索引、订阅器和哈希工具。其已有 HTTP 路由、健康与基础策略，以及 `KvBlockIndexer`、事件订阅、匹配查询等实现。[项目入口](https://github.com/vllm-project/router/blob/91b65ee4bdfbe98863a32a2205dced5dbb249ffe/README.md)、[KV 索引接口](https://github.com/vllm-project/router/blob/91b65ee4bdfbe98863a32a2205dced5dbb249ffe/src/kv_index/mod.rs)。

具体判断：

1. **转发、连接、流式处理与现有基线优先复用。**这些虽不构成课题创新，却直接影响延迟与正确性，不能称为“性能无关的通用模块”。
2. **索引先复用评估，不先写树。**已有索引是否满足长时间运行和隔离要求，必须单独验收。
3. **策略注入需要明确接入点。**所查 `LoadBalancingPolicy` 接收 worker、可选请求文本及 headers；完成回调主要是 worker URL 与 success。它不直接给出本项目需要的完整请求 token/block 上下文和逐请求生命周期账本。工厂也是显式注册内置策略，不等于安装任意 Python wheel 即可替换选点逻辑。[策略 trait](https://github.com/vllm-project/router/blob/91b65ee4bdfbe98863a32a2205dced5dbb249ffe/src/policies/mod.rs)、[工厂](https://github.com/vllm-project/router/blob/91b65ee4bdfbe98863a32a2205dced5dbb249ffe/src/policies/factory.rs)。
4. **已有功能不等于满足所有配置。**所查订阅器注明尚未完整处理 cache salt / 多模态 extra keys；索引中部分拓扑/anchor 数据未随驻留移除回收。前者影响状态隔离和命中判断，后者在大量唯一前缀持续到来时存在内存增长风险。这里指出的是此提交的具体边界，不是证明整个项目不可用。[订阅器](https://github.com/vllm-project/router/blob/91b65ee4bdfbe98863a32a2205dced5dbb249ffe/src/kv_index/subscriber.rs)、[索引实现](https://github.com/vllm-project/router/blob/91b65ee4bdfbe98863a32a2205dced5dbb249ffe/src/kv_index/indexer.rs)。
5. **索引库存在不等于在线策略已消费。**进一步检索同一固定源码，`KvIndexSupervisor` 和 `find_tiered_matches` 未在索引模块以外的在线路由代码中被调用；工厂的 cache-aware 策略使用请求历史树，不等同实际 KV 驻留。需补 M2→M4 的显式接线、失效资格与生命周期合同，不能直接把现有 cache-aware 策略称为精确事件路由。

另外，归档引擎默认 `xxhash`；Router 的 `kv_hash.rs` 请求序列哈希工具限定于较窄的 `sha256_cbor` 配置。而其事件索引又采用另一种本地 token 哈希。必须区分“引擎序列哈希”“索引本地哈希”“请求查询哈希”，不能直接互换。可优先验收一个双方支持的明确配置，但不能为了接入而静默修改用户缓存哈希，也不能把测试限定配置宣传为全配置兼容。[引擎缓存配置](https://github.com/intellistream/vllm-hust-legacy-20260831/blob/13f11da44455d2f85f00f810a04e1bd2eaf30ba6/vllm/config/cache.py)、[Router 哈希工具](https://github.com/vllm-project/router/blob/91b65ee4bdfbe98863a32a2205dced5dbb249ffe/src/kv_hash.rs)。

当前明确的接入候选是事件 token 索引路线：订阅器按每块 token 的 u32 little-endian 字节计算本地 SHA-256；引擎 hash 只用作 parent/removal 的不透明锚点。因此本路线不要求跨进程复现首块随机 seed，也不要求改引擎默认 xxhash。固定 HUST 默认事件 hash 是整数，不能据此宣称完整原生 bytes 链重算通过。快照缺少 token/parent 才是已热服务重建的直接缺口。

协议也需适配：HUST 的 legacy DEALER 回复为三个 frame，候选订阅器按至少四个 frame 解析；原生实时三帧又没有 epoch。用户已批准实验性窄幅 publisher hook，详见 [ADR](../decisions/2026-10-11-optional-hust-publisher.md)。它不意味着照搬订阅器即可完成恢复；缺父链的事件必须暂存或拒绝，不能使用候选默认的落到根节点行为掩盖缺口。

当前 Router 构建清单还引用 vLLM `v0.29.0` 的部分 Rust 库。不能据此断言 HTTP 代理不能连接旧引擎，但模板、哈希和协议相关部分必须针对归档宿主验证。不要直接选择移动的最新版作为发行依赖。[Cargo 清单](https://github.com/vllm-project/router/blob/91b65ee4bdfbe98863a32a2205dced5dbb249ffe/Cargo.toml)。

### 3.3 Dynamo 与 llm-d：可复用局部能力，不必引入全平台

**Dynamo。**所查 `dynamo-kv-router` 提供多种前缀索引、调度原语；Cargo 中 `default=[]`，`dynamo-runtime` 是可选依赖。这意味着不能简单以“Dynamo 是 NVIDIA 平台、太重”为由排除其 CPU 侧路由库。它还提供自定义 Filter/Scorer/Picker 与注册示例，但需要构建时链接对应策略 catalog，不是无条件动态加载。

建议：当 Router 内置索引或策略扩展不合适时，评估单独复用这个库；确认哈希/事件适配、依赖体积、架构支持和生命周期语义，不同时引入整个 Dynamo runtime、额外索引服务和另一套全局调度。源码可作为强基线及接口参考，不把其已有功能写成本项目原创。[库说明](https://github.com/ai-dynamo/dynamo/blob/0f01da1926505c897ea57c37f58f1ccea7581754/lib/kv-router/README.md)、[依赖边界](https://github.com/ai-dynamo/dynamo/blob/0f01da1926505c897ea57c37f58f1ccea7581754/lib/kv-router/Cargo.toml)、[策略扩展示例](https://github.com/ai-dynamo/dynamo/blob/0f01da1926505c897ea57c37f58f1ccea7581754/examples/router/custom-policy-example/README.md)。

**llm-d。**旧 `llm-d-kv-cache` README 已提示索引相关开发移至 `llm-d-router`。新位置的 `kvcache.Indexer` 接收外部 tokens，提供块键计算、连续前缀匹配与 per-pod 结果；事件接收和索引具有可区分的接口。因此“采用索引库”和“部署整个 Kubernetes 推理平台”不是同一选择。

建议：保留为索引/事件接口候选，尤其是最终选择 Go 宿主时。若采用 Rust Router，不为使用这一库就默认增加逐请求 Go RPC；需要证明它的收益超过跨语言部署与通信成本。[迁移说明](https://github.com/llm-d/llm-d-kv-cache/blob/main/README.md)、[新索引接口](https://github.com/llm-d/llm-d-router/blob/169629369ed86604371130092e44274a25ec75f4/pkg/kvcache/README.md)。

**SGLang、Ray、LMCache/Mooncake。**继续作为能力与实验对照资料；当前不把另一推理引擎、Ray 集群运行时或 KV 搬运/分层系统列为必装依赖。不是判断它们性能差，而是这些部署职责超出当前需求。后续若改变范围，再独立评估。

## 4. 复用 / 适配 / 自主设计决策矩阵

下表是实施责任划分，不代表所有组件都已通过复用验收。

| 能力 | 当前建议 | 需要我们做什么 | 性能与正确性准入 |
|---|---|---|---|
| HTTP 接入、连接池、SSE 转发 | 优先复用一个 Router 宿主 | 配置、接线、取消/超时/重试契约测试 | 不双重代理；不聚合缓冲流式输出；已发送请求不随意重试 |
| 请求模板、tokenizer | 复用对应版本实现 | 一致性适配、配置指纹、必要缓存 | 不重写 tokenizer；测重复编码成本；不擅自改变请求语义 |
| KV 事件产生和发送 | 优先用归档引擎现有接口 | 消费协议、rank/epoch 映射、恢复测试 | 证明真实事件和有界开销；缺口明确，非默认新 hook |
| 前缀目录与查询数据结构 | 先评估 Router 内置；Dynamo/llm-d 为替代候选 | 统一查询契约、隔离/过期/恢复适配 | 唯一前缀长期增长、并发更新、丢失恢复、命中正确率 |
| 实例发现、健康、指标 | 复用宿主基础设施 | 映射实际可路由单元，统一代次与能力 | 一个健康事实来源；外部观测迟到不覆盖新代次 |
| 请求生命周期 | 复用宿主执行链 | 增补必要事件/字段 | 发出、失败、取消与结束恰当结算；不制造重复请求 |
| 路由侧工作量账本 | 我们负责定义，能复用的计数器继续复用 | 将自有分派与引擎观测对账，区分请求数与工作量 | 不双计；不把路由记账误称为后端资源预留 |
| 基础策略与安全回退 | 复用现成 RR/P2C/cache-aware 等 | 固定配置与适用条件，建立强基线 | 基线公平调参；同一底座比较避免把代理差异算作算法收益 |
| 即时优化决策 | 自主设计增量策略，借鉴成熟方法 | 定义缓存收益、工作量、服务目标的组合与逃逸规则 | 端到端 goodput；不靠量纲混乱的随意加权 |
| 持续亲和/放置计划 | 自主设计控制边界，方法可复用 | 何时调整、调整多少、如何停止；输出软偏好 | 计划不阻断即时路由；收益不足可完全关闭 |
| 观测/配置/日志 | 复用 Prometheus、结构化日志、配置库 | 项目指标、配置校验、状态解释 | 采样、有限标签基数、有界历史；不记录默认完整敏感提示 |
| 压测与评测 | 复用服务压测工具和公开负载 | 多副本回放、SLO goodput、负对照及故障场景 | 不只平均 TTFT；公平对比、冷暖缓存与随机种子可追溯 |
| MOD 包装与兼容检查 | 复用组内规范、模板及验证器 | 声明真实能力、兼容版本、启停与证据 | 不用模板通过冒充运行生效；依赖锁定与干净安装 |

**需要独立设计的是几处关键契约，而不是所有基础实现：**请求真实身份、状态可信范围、工作量账本、选点输入输出、后台计划的生效/失效规则。之后在这些契约内选择最合适的已有实现。

### 4.1 Ascend 复用判定矩阵

以下是 4 节对原矩阵的补充准入；“复用”不表示已经在 NPU 后端通过。

| 层次 / 候选 | 优先保留 | Ascend 上必须补的证据 | 不通过时的处理 |
|---|---|---|---|
| HTTP/SSE/连接/生命周期：vLLM Router | 通用协议和 CPU 执行链 | 无 CUDA 运行依赖的最小构建、aarch64 ABI、取消行为、当前 16 核配额下争用、原样透传 Ascend 服务协议 | 有限接线或换宿主，不重做整个网关 |
| tokenizer、CPU radix/hash 索引 | 算法与成熟数据结构 | 模型实际 token 一致、真实 block size/hash/盐、事件可见性、epoch/rank、块链恢复与元数据回收 | 补适配；无法可信解释时退基础策略，不先断言索引算法不能用 |
| KV 事件：目标 vLLM/Ascend | 实际执行路径中的原生接口 | 发布位置、block 分配/完成/可复用语义、APC+图+chunked prefill 组合、恢复及观测成本 | 缺失字段先标 unknown；必要且低成本才加 observer |
| Dynamo / llm-d 局部库 | 设备无关索引和选择接口 | 在所选 feature/dependency 集合中排除非必要设备组件，适配事件并对照服务事实 | 不为一个库带入完整 runtime、Kubernetes 或逐请求跨语言 RPC |
| Prometheus / 日志 | 导出框架与有界标签机制 | GPU/NVML 指标不可换名即用；Ascend/Host 指标含义、窗口、单位和覆盖度明确 | 缺测不填 0，不把 AI Core 利用率当瞬时余力 |
| 既有路由策略和论文方法 | 目标函数思路、数据结构、分工、稳定控制 | 重测复用节时、阶段干扰、图/shape 和 Host 敏感性，不复用 NVIDIA 默认系数 | 简单 NPU 校准先行；无净增益不加机制 |
| 设备侧 Attention、Graph、内存和通信 | 已验证 vllm-ascend/CANN 实现 | 真正算子路径、布局、dtype、有效内存、图功能组合及 TP 行为 | 交由后端适配；无明确必要性不纳入本 MOD |
| Benchmark / profiler | CPU 到达生成、报告；诊断使用 torch_npu/msprof | CUDA Event/Nsight/NCCL 探针不能直接用；同步和采样不得污染主成绩 | 抽出后端适配，正式成绩关闭 profiler |

这不是“先把所有底层工具学完再做路由”。强制项只覆盖当前文本 dense、TP=1、已选择图/APC 组合；HCCL 微基准、量化、算子/布局细查按 TP 或实际瓶颈触发。目标后端已有 APC 与 chunked prefill 能力不代表本 MOD 已有收益，也不代表任意功能叠加都正确。[Ascend 功能矩阵](https://docs.vllm.ai/projects/ascend/en/v0.18.0/user_guide/support_matrix/supported_features.html)

### 4.2 论文方法的迁移合同

| 可借鉴的方法类别 | 本项目保留的内容 | 必须重测或改变的条件 |
|---|---|---|
| 前缀局部性、热点逃逸（如既有 Preble/DualMap 调研方向） | 局部性与拥塞共同考虑，保留强即时基线 | 有效跳过工作与剩余 Attention 成本；不能把命中 token 直接乘原文 GPU 节时系数 |
| 周期亲和/放置（如 CacheRoute 方向） | 请求路径之外计算软计划、约束调整扰动 | 两副本收益空间、Host 预算、工作集与 batch 分布；重新建立 KV 和图预热分别计量 |
| 工作量/时延估计 | 阶段化特征、校准与误差评估 | 上下文、图模式、执行形状、实际 KV 容量和适用范围；预测超出范围时明确回退 |
| 分块 Prefill / 计算通信协同 | 借鉴解释干扰的方法与实验设计 | chunk 与 HCCL 由已验证引擎管理；不为借鉴论文越界改 token scheduler |
| 算子/融合/IO 优化 | 用关键路径与有效成本解释现象 | CUDA kernel、warp、共享内存与 CANN 的执行资源不同，不能移植参数即用；当前不自研生产算子 |

上表是迁移评审框架，不表示本轮重读这些论文或采用了它们的全部方法。即使论文以 NPU 为对象，也需核对 910 子型号、并行规模、网络和模型，不能把大规模 910C 成绩外推到两卡 910B2。实现前每个候选方法记录：来源/原假设、目标可得状态、改动、开销、负对照、退出条件。

没有观测到硬件敏感的决策差异时，不为了“NPU 特色”添加新评分项。图桶、核利用率、HCCL 时间默认用于离线归因，不要求每个请求都实时读取。

## 5. 推荐总体架构：一个在线宿主，不是八个新服务

```text
客户端
  │
  ▼
单一外部 Router 进程
  ├─ 复用宿主：协议/转发/健康/连接/生命周期/基础策略
  ├─ 适配层：请求身份、引擎事件、状态与索引查询
  └─ 本项目优化：即时决策 + 工作量账本 + 可关闭的后台亲和控制
  │                       ▲
  │推理请求               │原生事件/指标（异步）
  ▼                       │
已验证的 vLLM-Ascend 同构 NPU 多副本池（官方或指定 HUST 组合分别验收）
  └─ 只有缺少必要观测时，才安装可选窄幅 adapter

离线/运维：预检、校准、回放、对照评测、MOD 兼容与生效证据
```

这是三个实现分区加工具链，不是新的固定模块数。旧文档 M1–M8 保留为便于描述功能的逻辑编号，其实现分配为：M5 大部分归宿主；M1/M2/M3/M7 大量复用或适配；M4 与 M8 的优化增量由本项目负责；M6 复用工具后补项目评测。

### 5.1 性能关键的接入约束

- 逐请求尽量在同一进程访问索引、worker 快照和策略；不默认引入同步“问一下控制器”的网络调用。
- 前缀分析成本必须计入收益。优先复用宿主已有结果，不能在多层重复模板处理与分词；需要精确身份时不能拿字符串相似替代。
- 后台控制发布版本化、可过期的计划；即时请求只读当前可用计划，不等待重新计算。
- 缓存事件、健康更新、请求结算要及时处理，不归入可以拖延的后台规划。
- 只保留一套生产索引和一套请求执行所有权；实验对照可以替换实现，不把所有候选常驻上线。
- 关闭优化应退回同一个宿主的已验证基础策略。回退不额外经过另一个代理。
- 数据结构、事件队列、历史记录都需有资源上限和失效语义；具体数值在基准测试后决定。

### 5.2 插件化不等于必须动态注入未修改的 Router 二进制

需要区分两个边界：

1. **相对推理引擎：**目标是外部接入，优先不改引擎；必要 observer 可独立安装关闭。
2. **相对路由宿主：**优先已有扩展点；若不能传递所需状态，可能需要很小的注册/上下文/生命周期接线，并随 MOD 发布已构建制品。

这样的产品仍可以按 MOD 交付，不要求用户编译 Rust，但必须诚实标明 Router 的定制部分。不能把大型长期 Router fork 包装成“轻量插件”。接线若蔓延到大量路由分支、需维护多套协议或不断追赶引擎内部结构，就应否决这个底座，改评另一宿主或基于成熟库构成薄宿主。

当前优先评估的是“构建时接入、发行时预构建”的方案；是否有可直接满足全部需求的稳定动态扩展点，尚未证明。WASM OnRequest 中间件存在也不自动说明它能访问 KV 目录、选择 worker 并接收完整生命周期。

## 6. MOD 规范应落实到交付，而不是决定算法结构

继承的是规范要求：独立制品、依赖声明、显式启用、兼容检查、资源冲突检查、正确进程中的生效证据、可验证关闭/回退。不要继承旧对话的前缀路由实现和模块绑定。

按已核查的 Manifest 0.3 文档，新制品使用 `schema_version: 0.3`；扩展依赖需要显式启用，资源声明不授予生命周期管理权限；外部服务仍由操作者管理。元数据、安装、发现、启用、运行生效与性能收益是分开的状态。[固定规范](https://github.com/vLLM-HUST/extension-manager/blob/0e4939146d53bd24ce51459f7da2e6defd260832/docs/manifest-0.3.md)。

实际交付建议包括：

- 预构建 Router 制品与明确依赖，正常用户不需要源码编译。
- 一个入口配置副本、模型身份和事件来源，提供最小示例及配置校验。
- 预检报告：精确/估计/基础模式、失效原因及如何修复，不静默退化。
- observer 独立可选；使用原生事件足够时无需安装。
- 支持矩阵精确到已测试提交/版本组合，不写无界的“兼容所有 vLLM”。
- 组内要求的 manifest/metadata、实际生效与性能证据；Provider/contract 必须在目标 Manager/宿主上确认，不能虚构字段或能力。
- 策略关闭、Router 入口切回、observer 重启关闭分开说明；不承诺任意运行时补丁热卸载。
- 第三方依赖版本、许可证及修改说明。源码复用时保留相应 NOTICE/归属，不能把复制代码宣称为原创。

## 7. 项目特色与收益：应当怎样表述才准确

不把以下内容单独作为创新：前缀感知、cache/load 联合选择、KV 事件、快慢路径、radix tree、插件打包。成熟系统中已有相应能力。

可以争取并通过实验验证的产品价值是：

1. **有效容量：**在可复用前缀和拥塞并存时，比强基线更好地选择副本，减少无收益的重算与排队。
2. **负载变化时的稳定性：**后台计划只在有证据时调整，减少反复换落点的代价；即时路由继续负责突发逃逸。
3. **目标环境可落地：**在指定 Ascend 组合上给出真实状态接入、易安装、可诊断的性能方案，而不是要求更换整套服务平台。
4. **退化与维护成本：**低复用、信息不完整或计划失效时，成本接近已验证基础策略；有限接线避免大规模引擎 fork。

这些是待证收益，不是现有系统“普遍失败”的结论。若一个现成底座配置后已满足目标，我们应直接复用或贡献适配；只有在相同资源、相同配置和强基线上仍有可重复增量，才值得增加新的控制机制。快慢分工用于限制逐请求成本与集中维护计划，本身不保证性能领先。

## 8. 冻结底座前的短期验证清单

| 验证关口 | 必须拿到的结果 | 不通过时怎么处理 |
|---|---|---|
| 基础运行 | 收尾 HUST 候选 G1，随后验证目标 Ascend 执行配置；已有 eager 基础证据 | 不把基础运行当完整兼容，不用路由设计掩盖宿主问题 |
| 身份契约 | 模板/token/块身份及隔离边界对照一致 | 限定配置或替换适配；不宣布精确命中 |
| 事件恢复 | 增删、重启、丢包和超出重放窗口后结果可信 | 使用快照兼容方案；未恢复期间降级 |
| 宿主接线 | 策略上下文、生命周期和索引可少量接入 | 修改范围失控则换底座，不坚持沉没成本 |
| 基础开销 | 直连、只代理、加观测、加索引的分层对照 | 找到主要开销再选实现，不先开发复杂策略 |
| 持续运行 | 唯一前缀/低复用流量下内存和 CPU 有界 | 补回收或换索引，而非关闭测试 |
| 优化价值 | 强基线、即时增强、后台增强逐层消融 | 无稳定增量就不默认开启对应增强 |
| 产品交付 | 干净安装、预检、生效、停用、错误配置均可重复 | 修交付契约，不把手工改环境当最终安装方式 |

最终底座/语言暂不冻结；上面已经给出优先候选、选择理由和否决条件，不是让实现阶段随意挑库。当前无需再选择新的学术问题，也无需先争论复杂算法。
