## 核心判断

本项目面向华为 Ascend 上的同模型多副本服务，在固定 NPU 与 Host 资源下把前缀复用转化为满足 TTFT、输出停顿与完成率的容量。不是重写 vLLM-Ascend，也不因系统或论文最初使用 NVIDIA 就全部弃用。HTTP、tokenizer、CPU 索引、生命周期等先复用；设备执行成本、缓存布局、事件含义、依赖与性能系数重新验证。

保留 M1–M8 的职责划分和一个在线 Router 宿主。快路径只做有界状态读取与选点，事件/终态及时更新，后台软计划不阻塞请求。此结构用于控制开销，不是已证明优于其他系统的创新；没有净收益时关闭 M8。

## 哪些 NPU 特性真正影响本项目

| 机制 / 事实 | 对路由的影响 | 本项目的动作与边界 |
|---|---|---|
| Cube/Vector、Attention 形状及数据搬运共同影响耗时 | 输入 token 数相同不保证耗时相同；命中后仍有 suffix Attention 与 Decode 工作 | M6 校准上下文、未命中长度及并发范围；不把 GPU tokens/s 常数搬入 M4，不改算子 |
| ACL Graph 捕获/重放、执行桶与 padding | 启动成本与稳态不同；路由改变到达分布可能间接影响引擎 batching | 冻结实际图配置，独立测图冷/热；Router 不声称控制下一批 shape，在线图指标为可选信息 |
| 模型、图、workspace 与 KV 共同使用 HBM | 64 GiB 总量不是缓存可用量；逻辑命中也不保证省下同等计算 | 使用实际 KV blocks/布局/容量；记录全命中边界；不把 UB/L1 当可放置的持久前缀池 |
| NPU 异步执行 | Host 提交返回不等于设备完成或 KV 可复用 | 核对原生事件的实际语义和安全复用条件，不用逐请求设备同步修饰观测 |
| aarch64 Host、CPU 时间配额、分词和任务下发 | Router/索引/观测可能与引擎竞争 CPU | 无 CUDA 依赖的目标制品验证、分层开销测量；npu-smi/profiler 不进请求热路径 |
| 实际本地 KV heads、rank 与设备映射 | 不能默认总 KV heads 简单除以 TP；两张 TP=2 卡不是两个路由副本 | 使用已验证布局和可路由端点；首验两份 TP=1，不增加 HCCL 管理层 |

图机制参考 [Ascend ACL Graph 设计文档（v0.18.0）](https://docs.vllm.ai/projects/ascend/en/v0.18.0/developer_guide/Design_Documents/ACL_Graph.html)，Host 约束参考 [CPU binding（v0.18.0）](https://docs.vllm.ai/projects/ascend/en/v0.18.0/user_guide/feature_guide/cpu_binding.html)。它们解释机制，不证明归档候选或预装版本的默认值、参数、支持范围；不照抄历史数值阈值或全局 IRQ/服务修改命令。

## 两类档案、三类身份

新增的是设计数据合同，不是两个新在线服务，也不是当前可用 API：

- **BackendCapability**：M7 产生，说明实际支持的接口、模型/缓存布局、执行配置、数据来源和可用性；通过 CapabilityReport 引用。
- **ExecutionProfile**：M6 产生的离线/显式校准产物，包含适用输入与并发范围、冷暖条件、耗时/干扰结果、误差、版本和证据。M7 校验适用性，M3 保存引用，M4/M8 只读；不能成为逐请求远程 RPC。

身份分开管理：模型/模板等形成语义兼容域；block/head/dtype/事件身份形成缓存布局与协议指纹；图模式、调度预算、软件/硬件、并行及 Host 条件形成执行性能指纹。依赖关系而非一个宽泛版本号决定失效范围：CPU 配额变化使性能档案失效，不自动证明 KV 语义变化；worker 重启通过 epoch 使相关驻留与计划失效。

健康/代次/生命周期是在线必需状态。精确前缀模式还要求可核验身份与事件；阶段摘要、抢占、KV 压力是带来源/时效/覆盖范围的可选增强。图桶、padding、Cube/Vector 时间线等默认属于离线诊断，不能要求所有用户安装常驻 profiler。unknown 不等于 0、未命中或空闲。缺少/过期档案则回到经验证的基础策略；身份无法核实则退出精确模式，但不省略健康和隔离约束。

## 复用的三道门槛

1. **能构建和运行**：审查最小依赖/feature，无 NPU 的 CPU 组件不应隐式要求 CUDA/NCCL/NVML；实际验证 Linux aarch64 制品。
2. **语义正确**：固定提交并验证 tokenizer、hash、block/rank、原生 Ascend KV 事件及恢复。导入成功、配置项存在均不算通过。
3. **值得使用**：在 NPU 合理配置的强基线上，验证收益、Host/内存成本和负对照。方法可以复用，阈值、代价曲线和性能结论不能从 GPU 直接移植。

优先评估 vLLM Router 的接入/生命周期和内置索引；不足时才审查 Dynamo/llm-d 的最小局部能力，不一起部署完整平台。原生 Ascend/vLLM 观测先验收，只有缺口阻止正确功能且开销可接受才增加小型 observer；不覆盖 Ascend platform plugin、scheduler、分配或淘汰策略。详见[复用评估](planning/组件复用与自研边界评估_2026-10-10.md)。

## N0–N6：最小真实服务验收

这里是按风险选用的实验目录，不是要求先做完全部项目才接基础链路。N0 与基本请求正确性先行；N1–N4 随缓存、成本估计或性能归因需要逐项展开；取消、故障等安全语义在对应功能放行前完成。ExecutionProfile 不作为基础路由前置依赖。

| 实验 | 阶段 | 需要回答的问题 |
|---|---|---|
| N0 整栈与映射 | P1b | 一套冻结配置能正确运行吗？模型/版本/物理卡/逻辑设备/TP rank/端点分别是什么？ |
| N1 有效缓存收益 | P1b–P2 | 固定上下文扫命中/后缀，固定后缀扫缓存上下文；真正节省多少 TTFT？ |
| N2 图与并发 | P2 | 目标支持的图/eager、并发/形状边界下，稳态、捕获成本和有效 KV 容量如何变化？ |
| N3 混合阶段干扰 | P2 | Decode 进行中注入长 Prefill，对新 TTFT 和已有输出停顿影响多大？ |
| N4 Host 开销 | P2 | 直连、仅代理、加观测、加索引分别增加多少成本？压测是否已受限？ |
| N5 两副本与强基线 | P3–P4 | 热点、低复用、工作集压力下，基础策略和增量机制的净收益是多少？ |
| N6 生命周期与恢复 | P3/P6 | 声明支持的执行组合下，事件延迟、取消、重启、恢复能否保持正确和有界？ |

先固定一个主配置，再按风险/配对组合扩展，不穷举模型×dtype×图×并行。至少分开图已热/KV 冷、图已热/KV 热，首次加载/捕获另报；重启后图也冷时不能冒称只清了 KV。profiling 做诊断，正式成绩关闭采样。后端调优与 Router 优化分组归因；所有基线获得相同合理调优机会。

GEMM/搬运/布局微基准仅用于必要的瓶颈归因，不是开工前必须完成的研究。量化/融合不新增为首版范围；TP>1 或已有证据显示通信瓶颈时再测 HCCL。研究方法逐一附迁移假设与消融，NPU 特定机制若无收益则不强加。详细阶段与 CI 见[实施计划](planning/前缀路由MOD_整体实现计划与工程验收.md)。

## 已知事实和未完成事项

当前分配为aarch64、8核CPU配额、64GiB RAM、两张910B2；逐卡单实例子集通过，不是双副本容量验收。历史CPU/四卡成绩保留原配置与日期。CPU配额不等于cpuset大小或独占核心；系统预装、CPU venv、新旧服务环境分别记录，见[兼容矩阵](compatibility.md)。完整恢复/图/性能仍未过。
