# 分布式 KV 智能路由系统：问题定义、现有工作的边界与工程规划

日期：2026-10-04  
状态：立项建议与待验证假设；尚未实现、未在 GPU 集群复现性能。  
输入：完整阅读用户提供的 `D:/QQ/近三年分布式KV与LLM推理路由论文调研.md`、`D:/QQ/高性能分布式KV智能路由系统调研.md`，并补查直接影响问题定义的原论文、官方接口和近期相关工作。

## 1. 立项判断

建议继续以“分布式 KV 智能路由管理系统”为产品方向，但把核心问题收敛为：

> **在同构、多副本 LLM 服务中，如何协调请求分配与 KV 恢复，使已有 KV 在有限计算、缓存容量和数据搬运资源下，持续转化为满足延迟目标的有效服务能力？**

这里的 KV 恢复指把 CPU、外部存储或其他实例上的兼容 KV，变成目标推理实例实际可使用的状态。路由和恢复会共同占用资源，决定一个请求多久能开始计算，并影响正在服务的其他请求。

建议的工程落点是**可插拔的请求路由与 KV 恢复协调层**：先服务于一个 vLLM 版本、一个同构模型副本池及一个现成 KV backend，再验证第二种引擎或 backend 的适配成本。

立项依据分成两部分：

- **已获得支持的事实**：缓存复用、负载、恢复延迟和本地调度相互影响；缓存命中增加不必然带来吞吐或延迟改善。
- **尚需验证的项目假设**：在已有强路由器与 KV backend 上，显式协调恢复准入、请求分配和未完成操作，能否取得足够稳定、足够普遍的增量收益，同时保持低接入成本。

当前可以合理决定投入“问题验证原型”，尚不能合理承诺“优于所有 vLLM/SGLang 插件”或“这是尚无人解决的新问题”。

## 2. 对已有资料的关键修正

两份资料适合建立知识地图，但其中某些“现有系统缺少什么”的结论不足以直接支撑立项。以下修正以本次查到的原文为依据；不覆盖改写原始资料。

### 2.1 时间预测、在线校准、置信度与回退，已经有直接近邻

新增核查的 **QUARTZ（Findings of ACL 2026）**在 SGLang 路由层使用分位数成本预测、backlog-aware 选点、准入排序、在线残差校准和预测退化后的回退。因此，上一版资料建议的“成本模型＋置信度＋在线校准”可以作为实现方法，但不能直接作为区别于现有工作的核心贡献。[Q1][Q2]

### 2.2 Dynamo 已经支持模块化、预记账和不同缓存层

本次检索的 Dynamo `dev` 文档提供独立 selection service、选点与 reservation、生命周期负载更新；路由模型区分 prefill、decode 和不同缓存层。配置页还提供 predict-on-route，缓解真实 KV events 尚未到达时的重复放置。[D1][D2][D3]

因此，“引擎外插件”“全局缓存索引”“在途请求记账”“CPU/SSD 不同权重”“真实事件＋近似索引”都属于已有能力。

注意：这些是访问当日的开发版文档能力，不能自动认定某个稳定发行版或任意后端全部支持。复现实验必须固定版本、配置和 backend。

### 2.3 必须区分 Mooncake 系统与 Mooncake Store 的某次集成

Mooncake FAST 2025 原论文的 Conductor 已经预测 prefill、传输和排队时间，进行 SLO-aware 调度，并有缓存负载均衡和热点复制。不能依据某篇 vLLM×Mooncake Store 博客的 future work，得出“Mooncake 没有联合路由”这一结论。[M1]

### 2.4 网络感知与并发传输计数也已有近邻

新增核查的 **NetKV（2026 预印本）**已经将 topology、背景拥塞和自己发起的 in-flight transfers 纳入 decode 选点。其结果来自流级仿真，不能当作真实集群实测；但它足以否定“给路由加带宽和在途传输数就是新方法”的说法。[N1]

### 2.5 多层管理与计算—存储协作不是空白

Strata 已处理 delay hit 和 loading-aware scheduling；Bidaw 已根据缓存层和 KV 大小组织准备/就绪队列，并把生成信息反馈给缓存管理。因此，“让计算和存储交流信息”本身也不能作为独特性。[S1][B1]

这些发现并不否定工程价值。它们要求本项目证明一个更具体的主张：**在明确的插件接口和控制权限内，某个协同机制比现有强配置组合更有效，且收益覆盖多类常见负载。**

## 3. What is the problem：究竟解决什么问题

### 3.1 从使用者遇到的现象出发

目标使用者是维护多副本、自托管 LLM 服务的团队。他们已经启用 prefix caching，也可能接入 CPU offload 或分布式 KV store，但仍可能遇到：

1. 指标显示 cache hit 很高，首 token 延迟却不稳定；
2. 有的 GPU 忙于长 prefill，有的 GPU 等 KV 恢复，集群增加了缓存容量却没有得到相应的有效吞吐；
3. 路由器把请求发给空闲实例，但它们都要访问同一个缓存源，形成新的传输热点；
4. 相同配置在白天短问答、晚上长会话或突发任务中表现不同，需要频繁调节亲和度和负载阈值；
5. 请求变慢后，难以区分是 worker 排队、重复计算、外部读取、HBM 装载，还是已有 decode 被干扰。

前两份资料为这些现象提供了合理动机，但没有给出本项目环境中的发生频率和损失比例。这部分必须测量，不能通过罗列论文替代。

### 3.2 技术问题：缓存“存在”与请求“能够受益”之间有距离

对于同一个请求，至少要回答三个不同问题：

| 问题 | 必要信息 | 不能由什么代替 |
|---|---|---|
| KV 能否复用？ | 模型/布局兼容性、完整前缀链、token/block identity、隔离域 | 相似文本、相同 session ID |
| KV 何时能供目标实例使用？ | 驻留层、恢复路径、已有搬运、目标容量、当前操作状态 | 命中 token 数、静态层权重 |
| 此刻复用是否有利？ | 等待和恢复时间、重算代价、decode 干扰、其他已接纳请求 | 单请求无竞争带宽、瞬时 GPU 利用率 |

已有系统分别对这些问题做了大量工作。本项目应研究它们在**插件组合运行时**是否仍存在决策脱节：上层作出了依赖某种恢复条件的选择，底层却以自己的独立策略执行，或者大量新选择在执行前已经改变了原来的资源条件。

### 3.3 可检验的根因假设

建议将根因限定为两个相互关联的假设：

**H1：决策所依据的恢复代价，与实际执行时的恢复代价不一致。**

例如，路由时读到 KV 位于 CPU，实际执行时它已被淘汰；或者当前带宽空闲，但一批并发路由已经承诺从同一 source 拉取数据。源端、链路、目标 HBM 和计算队列共同决定代价。

**H2：请求分配与恢复准入分别控制，导致各自合理的选择在组合后降低有效吞吐。**

例如，多次选择远端恢复都比单独重算便宜，但一起执行后占满恢复队列；反过来，为减少传输而将请求集中到缓存持有者，也可能使计算队列超时。

这两个假设必须通过真实 trace 和受控干预验证。如果成熟组件已经在目标环境中消除了这类损失，应缩小或放弃该主线。

### 3.4 用一个明确的例子解释

下表是机制示例，**数字是人为设定，绝不是测量结果**。假定三个副本同模型同硬件；该示例执行路径中的排队、恢复、剩余计算串行发生；decode 接纳压力相当。

| 选择 | 排队 | KV 恢复 | 首 token 前剩余计算 | 预计 TTFT |
|---|---:|---:|---:|---:|
| A：本地 KV 已就绪 | 250 ms | 0 ms | 40 ms | 290 ms |
| B：远端恢复 1 GiB | 20 ms | 50 ms | 40 ms | 110 ms |
| C：直接重算 | 10 ms | 0 ms | 140 ms | 150 ms |

无竞争时，B 最好。但若 B 的共享路径有效速率从 20 GiB/s 降到 5 GiB/s，恢复需 200 ms，TTFT 变成 260 ms，C 更好。若 C 的重算会使正在运行的 decode 大量违约，则仍不能只按新请求 TTFT 选择 C。

这里有两个要点：

- “缓存更多”“节点更空闲”都不足以确定答案；
- 能准确估计单个请求也不够，需要把已经接纳的资源消耗计入后续决策。

真实系统允许流水重叠时，应按照依赖关系计算关键路径，不能沿用表中的简单相加。

## 4. Why it matters：为什么重要，为什么具有工程普遍性

### 4.1 节省计算不一定兑现为服务容量

系统使用者关心的是同样的 GPU 和内存成本能服务多少达标请求。少算了 prefill，如果代价是更多等待、搬运或 decode 干扰，并不一定产生收益。Mooncake 的带宽分析、Strata/Bidaw 的恢复调度，都表明缓存收益与恢复条件有关。[M1][S1][B1]

因此，衡量对象应是 TTFT/TPOT 约束下的 goodput，同时报告所有输入请求的完成率、拒绝率和超时率。提高 cache hit 是解释收益的中间指标。

### 4.2 同构硬件仍然会出现不同的执行代价

不需要进入异构 GPU：同型号副本也会因驻留 KV、活跃请求、缓存容量、源端位置和同时发生的恢复操作而产生不同代价。这些差异就在用户已选择的范围之内。

### 4.3 适用性来自共同资源关系

| 常见业务 | 可复用内容 | 可能触发的共同瓶颈 |
|---|---|---|
| 多轮对话 | 递增历史 | 容量淘汰、轮次回流、亲和与负载冲突 |
| 企业问答/RAG | 相同提示模板及真正相同的文档前缀 | 冷热混合、长 prefill 与恢复竞争 |
| 编程/工具 agent | 仓库上下文、历史工具输出 | 长 KV、轮次间隔变化、恢复突发 |
| 批量抽取/共享模板 | 公共模板和文档前缀 | 大批并发到达、相同 KV 尚未就绪 |
| 混合在线服务 | 上述模式共存 | 策略适配与不同请求之间的干扰 |

这里不假设任意 RAG 文档片段都能用 exact prefix 复用，也不要求应用提供 DAG。`KVCache Cache in the Wild` 发现 single-turn 间复用同样重要；ServeGen 强调保留 client 层面的相关性。这支持跨业务评测，而非只用 agent 会话证明通用性。[W1][W2]

### 4.4 明确收益边界

单副本、低并发、几乎无复用、缓存全在 HBM 且不淘汰，或者恢复资源远未饱和时，本项目可能没有性能优势。decode 完全主导、入口路由空间很小时，入口插件也无法解决所有瓶颈。

工程通用性的合理定义是：覆盖多类有共同瓶颈的常见服务，其他场景能以很小开销保持现有策略表现。要求所有负载都显著获益并不现实。

## 5. Why existing work fails：哪些条件使现有方法不够用

“失败”在本文中指某个可说明条件下无法达到目标，不能理解为这些系统整体无效。

| 工作/方案 | 已经做得好的部分 | 本项目还需验证的边界 | 可以怎样公平比较 |
|---|---|---|---|
| SGLang 默认 cache-aware / 近似 prefix 路由 | 低成本保留局部性并结合负载阈值 | 请求历史与真实驻留/恢复状态不一致时，是否频繁选错 | 开启合理负载保护；再比较新增状态的独立收益 |
| LMetric | 以新增 prefill tokens 和 batch size 做简洁调度，并提供异常情况检测/回退 | 未表示恢复队列时，相似 load/prefix 是否对应不同实际代价 | 使用原实现或忠实移植并保留回退，不仅实现一个乘法公式 |
| Dynamo / Ray KVAwareRouter | 真/近似索引、token load、预记账、层级 credit、可扩展选点 | 已有最佳配置是否足够；恢复端资源与请求级动作是否仍脱节 | 将现有功能打开；单独对比层权重调优、传输估计和协调机制 |
| llm-d | K8s 中的 KV-aware 路由、可组合 serving 层 | 索引、picker 和外部 KV backend 的实际契约能否覆盖目标动作 | 固定 EPP/插件版本，同 engine、同存储和同资源预算 |
| Mooncake Conductor | 缓存中心调度、TTFT 预测、SLO、传输与热点管理 | 其方法能否在所需插件接口下复用；目标条件下还有多少剩余损失 | 同样部署条件可复现才做整系统对照；Store-only 对照不得称击败 Mooncake |
| Strata / Bidaw | 在 engine/storage 层处理加载与调度协作 | 多副本之间分配恢复压力是否仍有增量空间 | 保留其本地优化，再加外部策略做增量实验 |
| QUARTZ | 分位数预测、准入、在线校准、回退 | 已报告的动作是 worker 选择和准入排序；对明确的跨层恢复动作还需扩展 | 同时对比预测本身与恢复协调；不能把校准当独有贡献 |
| NetKV | 网络成本和自身在途传输进入 P/D decode 选点 | 原文主要是仿真、P/D 路径和逐请求选择；通用恢复执行仍需检验 | 纳入 topology-only 与 in-flight-aware 简单强基线 |
| Preble / CacheRoute | 复用与负载折中、前缀分布/规划 | 对多层恢复与并发资源约束是否足够 | 不把“长期规划”“热点副本”重新命名成新贡献 |

依据：[G1][L1][L2][D1–D4][R1][K1][M1][S1][B1][Q1–Q2][N1][P1][C1]。

### 5.1 三类可以论证的失效机制

**信息不足。** 如果两个候选在策略看到的 prefix/load 特征上相同，而真实恢复代价不同，策略无法仅凭这组特征识别差别。这是对特定信息模型的限制；若 Dynamo 或 connector 已暴露这些信息，该批评就不适用。

**动作不足。** 只有 `select(worker)` 的接口不能强制改变恢复源、禁止一次昂贵加载，或对恢复并发做准入。添加再好的预测器，也只能改变可执行动作中的选择。

**决策相互影响。** 已分派但尚未执行的请求会改变后续带宽和目标容量。异步指标若没有对应的记账/资源控制，容易反复使用同一份“空闲量”。但 Dynamo 已有请求 reservation，NetKV 已有传输计数，因此要验证的增量是具体恢复资源和执行确认，而非泛泛的“增加记账”。

### 5.2 不能声称的缺口

- “现有系统都只关心命中率”：不成立。
- “现有系统都不考虑网络”：不成立。
- “在线校准、预测回退和 SLO-aware routing 尚无人做”：不成立。
- “没有人联合考虑路由和 KV”：不成立，Mooncake 等已有大量工作。
- “插件形式和兼容多个引擎就构成技术创新”：不成立，但可以构成维护质量和使用成本上的产品价值。
- “文档未描述某项功能，就证明系统没有”：不成立；要固定版本检查实现和行为。

## 6. 推荐主线与其他候选的取舍

| 候选方向 | 工程价值 | 与现有工作重叠 | 当前建议 |
|---|---|---|---|
| 自动切换 cache-first/load-first | 有，容易接入 | LMetric、Dynamo、Ray、QUARTZ 等已有强方法 | 基础能力和 baseline |
| 预测输出长度，处理 straggler | 有，但预测不可避免有误差 | 已有多种预测与迁移工作 | 附加信号；不作为项目成立的前提 |
| KV 生命周期/预热与热点复制 | 有 | Preble、Mooncake、Dynamo、CacheRoute | 后续按实测需要加入 |
| 请求路由与 KV 恢复资源协同 | 有明确资源浪费来源；跨多种常见服务 | 同样有近邻，需要证明可执行接口与增量收益 | **推荐作为首个验证主线** |
| 全栈统一编排平台 | 功能空间大 | Dynamo、llm-d 已非常完整 | 不符合当前投入和轻量目标 |

选择恢复协同的原因：它既与“分布式 KV 管理”直接相关，也能提供超出静态选点的实际动作。其风险同样明确：如果底层接口无法支持动作，或者恢复在真实服务中占比很低，这个方向就不成立。

**产品定位建议：同构 LLM 副本池的 KV 感知路由与恢复协调插件。**

“智能”体现为根据真实运行条件选择并兑现动作，不要求使用大模型、强化学习或复杂预测网络。

## 7. 初步机制：把一个选择落实为可执行计划

本节是候选设计，不是已经确认有效的算法。

### 7.1 从 worker 分数扩展到有限候选计划

先根据兼容性、局部缓存、当前负载与已知恢复来源生成小规模候选集。每个计划描述：

```text
目标 worker
可直接复用的本地完整前缀
需要恢复的前缀范围 / 物理字节数 / 来源
需要重新计算的后缀
允许的最迟等待时间
需要的恢复并发预算与目标暂存容量
执行条件失效时的回退路径
```

首批动作只考虑：立即发往本地可用节点；发往支持恢复的节点；在支持跳过外部加载时重算；在网关中有界等待后重新决策。迁移正在 decode 的请求、全局主动复制和跨模型复用不进入首版。

重算动作不要求抹掉可用的本地 APC，只跳过预计不划算的外部恢复。不要通过清空缓存或改写用户 prompt 来模拟该动作。

### 7.2 按真实依赖预测首 token 的关键路径

仅在恢复和 compute queue 可以同时推进、且已具备暂存/目标分配条件时，可采用：

```text
TTFT ≈ 网关等待
     + max(计算可接纳时间, KV 就绪时间)
     + 剩余 prefill 与首 token 计算
```

若 backend 必须先完成引擎分配再启动恢复，应使用相应串行依赖；若支持逐层流水，则按阶段重叠建模。不同 backend 不应共用一个固定相加公式。

剩余 prefill 成本依赖未缓存 token 数、已有上下文长度、batch/chunk 状态；不能只把未缓存 token 乘固定常数。已有 decode 的保护用可观测负载和实测干扰曲线约束，入口层只能降低风险，不能保证每个未来 token 的延迟。

### 7.3 对恢复操作做明确准入和完成记账

候选核心机制：将“选中节点”与“同意开始恢复”连接起来。

1. 检查计划能否执行：来源还有效，目标具备所需能力，容量估计未超预算；
2. 对受本控制器管理的 source/target 恢复资源，记录将要发生的字节量和并发；
3. adapter 确认操作接受后启动；失败则释放记账并重新选择；
4. 从实际完成/失败/取消反馈修正负载和代价；
5. 不支持控制的 backend 只使用可观测信息选点，不谎称资源已预留。

这里的预算首先是软件准入约束，不等于交换机保证带宽，也不等于引擎保证未来显存。目标 HBM 的强预留只有 engine 明确接受相应接口时才成立；否则称作预测与保护余量。

相同 KV 到同一目的地的重复恢复可以研究合并，但必须查明 backend 是否已有该机制。不同目的地的相同前缀不能因为 hash 相同就被当作同一次搬运。

### 7.4 轻量校准是支撑机制

先采用分桶的实测 prefill/recovery 成本与滚动统计，检查加入新信号是否改善选点排序和最终 goodput。只有简单方法不能解释误差时，再引入更复杂模型。

模型失效后回退到经过验证的 token-load/LMetric 类策略。回退也必须使用可信状态；当 cache index 陈旧时，不能继续依赖同一个失真的命中量计算 LMetric。

置信区间只表述经验预测可信度。没有相应假设与证明，不宣称确定的 SLO 保证、最坏情况保证或在线 regret bound。

## 8. 从需求推导组件

| 组件 | 为什么需要 | 最小实现 | 不承担什么 |
|---|---|---|---|
| 引擎/缓存 adapter | 知道能观察和执行什么 | 版本、能力、KV/负载事件、恢复回执 | 不自行实现 attention 或 allocator |
| 有界状态目录 | 避免把过期、待完成和就绪 KV 混为一谈 | 前缀位置、worker generation、时间戳、pending/ready/unknown | 不做全局强一致 block 数据库 |
| 候选与成本模块 | 比较可行执行路径 | 少量候选、关键路径预测、简单校准 | 不声称预测所有未来请求 |
| 恢复协调器 | 控制自身造成的数据搬运竞争 | source/target 预算、operation ID、接受/完成/释放 | 不实现 RDMA、存储层或任意网络 QoS |
| 请求决策器 | 将服务目标变成动作 | 选择、有限等待、回退、截止时间检查 | 不接管运行中 decode 调度 |
| 观测与评测工具 | 证明收益、解释失败 | 预测/实际路径、TTFT、恢复字节、错误、replay | 不把日志反事实估计当真实收益 |

这些可以先是一个进程中的模块。没有证据要求拆成六个独立服务；单一控制器是首版的合理简化。多实例控制面需要后续处理预算归属与同步，不能把“最终一致”误写成“不会重复接纳”。

## 9. 插件兼容性的实际边界

### 9.1 三档能力

| 模式 | 用户接入要求 | 本系统可以承诺的能力 |
|---|---|---|
| 通用代理模式 | OpenAI-compatible endpoint，最好有基础负载指标 | 请求转发、近似亲和、健康/负载选择；不能控制 KV 恢复 |
| 引擎感知模式 | 指定版本的 KV events、负载与请求回执 | 更准确缓存选点和已分派请求记账 |
| 恢复协同模式 | 一个受支持的 connector/backend adapter | 暴露并控制已验证的恢复动作、反馈、并发预算 |

产品可易于接入，但最佳性能允许使用可选 adapter。“OpenAI API 兼容”不意味着“KV tensor 可以跨 engine 任意交换”。

### 9.2 必须先验证的接口事实

- vLLM `KVConnectorBase_V1` 有 scheduler/worker 两侧职责：外部匹配、分配后更新、加载与完成回报等。外部 HTTP router 不自动拥有这些权限。[V1]
- `get_num_new_matched_tokens` 可被重复调用并要求无副作用，不能把全局预算预留藏在这个查询函数里；需在真正的接受/分配阶段记账。
- LMCache 文档有 lookup/move/pin 等接口，但本次访问的相关页明确标注为 legacy in-process mode。必须核对选定版本和 MP mode 支持情况，不能据此承诺现版开箱即用。[LC1][LC2]
- plugin 能否逐请求跳过外部加载、选择 source、观察传输完成、取消或释放 pin，都应列为接口验收项。未通过时移出该版本动作集合。
- Dynamo 自定义选点策略主要替换 worker ranking，Dynamo 保留 discovery、queue、reservation 和 accounting；若方案需要新增恢复控制，只有写一个 ranking callback 可能不够。[D4]

首版建议采用一个 vLLM adapter 和一个外部 KV backend。基础模式可以先交付；**只有恢复协同模式通过验证后，才能以“路由—恢复协调”作为项目主要卖点。**

### 9.3 正确性和生命周期

KV 身份必须包含模型/适配器、token/前缀链和格式兼容域，并尊重租户 cache salt。参考 vLLM APC 的 block hash 与隔离机制。[V2]

worker 重启后以 generation 区分旧位置；丢事件时标记 unknown 并逐步重建。unknown 影响性能判断，不改变 engine 的最终 KV 有效性检查。

取消或超时后的回退要服从实际执行状态。已向用户发送 token 后，不应悄悄在另一个副本重新开始；后台恢复不能取消时，应继续跟踪直到完成，避免释放软件预算后真实流量仍在运行。

## 10. 如何验证“有价值的问题还没解决好”

### 10.1 第一阶段：建立问题证据，而非先写完整管理器

固定两个资源档次内的代表模型和 2–4 个可路由副本；至少一次跨节点运行，单机无法证明网络恢复问题。模型具体选择由可用显存确定，当前不假设拥有某台远程服务器。

收集以下时间点及能获得的 proxy：router arrival/dispatch、backend admission、cache match、restore start/end、first token、完成或取消。拿不到内部 queue 或 I/O 时间时要标记不可观测，不能把 TTFT 差额全部归因于某一阶段。

先回答三个问题：

1. 使用强基线时，有多少延迟/失败可归因于恢复与路由配合不当？
2. 补充状态即可解决，还是确实需要新增恢复准入动作？
3. 这类损失是否在至少两种不同业务模式中稳定出现？

### 10.2 成对干预实验

| 实验 | 保持一致 | 改变什么 | 检验的假设 |
|---|---|---|---|
| 相同命中量、不同位置 | 请求、模型和 load 水平 | HBM/CPU/远端状态 | 静态命中收益能否代表实际收益 |
| 相同位置、不同恢复压力 | 请求和缓存大小 | source/target 并发与背景传输 | 在途资源是否改变最优选择 |
| 相同路由策略、不同恢复准入 | engine/backend 与候选集合 | 是否控制恢复操作的并发 | 额外动作是否优于单纯换分数 |
| 相同协调器、不同预测器 | 控制能力和 telemetry | 固定代价、实测分桶、在线校准 | 收益是否真需要复杂预测 |
| 相同初始状态、负载阶段切换 | 总请求和业务组成 | 稳态、突发、冷热转换 | 适应性和重建开销 |
| 无复用/纯 HBM | engine 和总资源 | 插件开启与关闭 | 基础开销和退化边界 |

强干预应来自真实负载中观察到的范围。极端限速和注入事件延迟属于稳健性测试，不能代替自然负载主结果。

### 10.3 公平基线

每个对照都固定 engine、模型精度、KV 格式、缓存总容量、网络、流量、SLO 与 warmup 方法。

- 起点：round-robin、power-of-two、session affinity；
- 实用基线：SGLang/vLLM 风格 cache/load-aware；
- 强调度基线：LMetric 原实现或经过验证的移植；Dynamo 或 Ray 中最适合部署的 KV/token-load-aware 配置；
- 新增近邻：QUARTZ-style 成本/准入方法；有数据移动时增加 topology/in-flight-aware 简单方法；
- 自我消融：同一个插件只选点、只做恢复预算、二者联合；
- 条件允许时再做整栈比较，明确“Mooncake 系统”与“vLLM+Mooncake Store”不同。

LMetric 的公开 repo 使用 patched vLLM（yaullm）和 step-level 指标；无法直接运行时应说明移植差异，不能把代理指标版本当作忠实复现。[L2]

若新增一个恢复并发上限就能取得全部收益，优先交付这个简单机制；无需为了保持原先架构而保留复杂预测器。

### 10.4 负载设计

至少覆盖多轮 chat、RAG/企业问答、coding/tool agent、共享模板批量请求，以及无复用和 decode-heavy 负对照。混合负载中保留原来的长度相关性、轮次依赖和 think time；不同会话并发方式也是输入的一部分。[W1][W2]

对异步到达用固定 offered-load 阶梯比较；对自然交互 trace 同时观察闭环 session 完成时间。不要只在固定并发下得出最大服务容量结论。

### 10.5 主要指标与证据矩阵

| 拟主张 | 所需证据 | 当前状态 |
|---|---|---|
| 恢复协同能提升有效容量 | 相同资源/SLO 下的 goodput 或可持续到达率提升 | 待测 |
| 收益不限单一业务 | 至少两类常见负载与一类混合负载的独立结果 | 待测 |
| 不是简单加存储容量的效果 | 相同 backend、容量和初始 warmup 的对照 | 待测 |
| 确实需要新增控制动作 | 相同 telemetry/预测器下，选点-only 对比联合准入 | 待测 |
| 不通过牺牲长请求获益 | 分类别 TTFT/TPOT、等待、公平性和完成率 | 待测 |
| 低复用和无恢复场景可用 | 插件 overhead 与最强实用基线的退化曲线 | 待测 |
| 插件形式成立 | 稳定版本安装、接口契约测试、第二适配器演示 | 待测 |
| 核心差异尚未被覆盖 | 与固定版本 Dynamo、QUARTZ、Mooncake 等的实现级对照 | 部分核查，未完成排重 |

goodput 定义为单位时间内完成且达到预先规定 SLO 的请求数。同时报告总到达量、完成量、拒绝/错误/超时和按类别的表现，避免靠少接请求制造好看的延迟。

TTFT 从客户端发出请求计起，包含网关等待。TPOT 或逐 token TBT 的口径需预先固定；平均 TPOT 不足以表示流式输出中的长停顿。

### 10.6 不要用错误的反事实验证策略

一条请求日志只记录实际选择的结果，不会告诉我们同一时刻发到另一个 worker 会怎样。路由会改变后续 KV 分布和排队，不能用旧日志中的 service time 直接宣称新策略更好。

可以使用仿真筛选设计，但必须先校准并在真实集群确认。在线比较应使用隔离的副本池或按策略运行的完整 replay；共享同一 cache pool 的逐请求 A/B 可能互相污染。shadow 模式可验证接口、预测和开销，不证明端到端收益。

## 11. 工程推进顺序与继续/停止条件

| 阶段 | 交付物 | 继续条件 | 不满足时怎么处理 |
|---|---|---|---|
| P0：版本与接口审计 | 固定版本清单、状态/动作 capability 表 | 能观察恢复成本，至少有一类可控制恢复动作 | 先做观测与路由；暂停恢复协同主张 |
| P1：损失归因 | 三类主负载、负对照、强基线、时间分解 | 损失稳定、规模足够，且不是配置错误 | 修基线或转为现有系统补丁 |
| P2：最小协同原型 | 选点＋一个 backend 的恢复预算/回执 | 联合机制优于选点-only 与简单限流 | 删除无效模块，重审主线 |
| P3：鲁棒与兼容 | 负载切换、状态过期、故障、第二适配器 | 退化可接受，接入成本可控 | 明确适用边界或缩小支持范围 |
| P4：公开发布 | 安装示例、容器、兼容矩阵、可复现 benchmark、限制 | 所有性能主张可由脚本复现 | 以实验项目发布，不宣传生产级 |

可设置以下**建议验收门槛**，用于控制工程投入，数字不代表预测结果：

- 在至少两类自然负载中，相对最强实用基线得到约 10%–15% 的 SLO capacity/goodput 增益，或用户认可的成本/运维收益；
- 常见负对照的吞吐和尾延迟退化目标控制在约 5% 内，并报告重复运行的不确定性；
- 插件造成的延迟开销设定相对预算，例如不超过目标 TTFT 的 1%，再根据实际 QPS、上下文长度与 CPU 预算确定绝对值；
- 若收益只来自人工制造的极端网络拥塞、只对一种 trace 成立，或必须长期维护大规模 engine fork，则重新评估轻量通用插件的定位。

不存在这些门槛的普适保证。发布前应公开真实通过和未通过的矩阵。

## 12. 可以直接用于项目讨论的问题陈述

### 解决什么问题

多副本 LLM 服务已经具备 prefix caching 和外部 KV 存储，但请求路由时的缓存命中与负载信息，未必能反映 KV 在目标实例上的实际就绪代价。多个请求的恢复操作还会相互竞争，使局部看起来有利的选择在执行后引起等待、重复计算或 decode 干扰。本项目研究在现有 engine/backend 的插件接口内，如何协调请求分配和 KV 恢复准入，把复用机会转化为稳定的 SLO goodput。

### 为什么重要

这一问题由同构副本之间不同的缓存位置、资源占用和请求相关性产生，可出现在对话、企业问答、coding agent 和共享模板服务中。解决它有望在固定 GPU 和缓存预算下提高有效服务容量，并减少不同负载下的人工调参。其价值需要通过多类真实或可追溯负载、强基线和退化测试证明。

### 现有工作为什么仍可能不够

已有工作已覆盖缓存亲和、token load、延迟预测、在线校准、分层存储和计算—存储协作。本项目不将这些能力重新声明为新问题。要验证的剩余缺口是：在可组合的工程部署中，worker 选点与具体 KV 恢复的准入、在途资源占用和执行结果，是否仍缺少足够紧密且低成本的协同。如果成熟组合已达到相同效果，则应复用或改进现有组件，而非新建重复系统。

### 预期差异与当前证据

预期差异是一个能够执行恢复操作、记录资源占用并回收恢复预算的插件协议及其调度机制，能够在多种负载下减少决策与执行脱节产生的损失。该差异仍是待验证假设；当前完成的是资料核查、问题收敛与评测规划，没有实测优越性结论。
