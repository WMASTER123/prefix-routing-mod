# 分布式 KV 路由系统能力矩阵与工程缺口

更新时间：2026-09-30

## 0. 目的与口径

本文承接《近三年分布式 KV 与 LLM 推理路由论文调研》，把代表性系统拆成三层比较：

1. 系统**知道什么状态**；
2. 系统**能执行什么动作**；
3. 系统**优化什么目标、适用于什么负载、何时退化**。

重点不是给系统排名，而是寻找跨论文、跨 vLLM/SGLang/Dynamo 后仍稳定存在的工程缺口。

符号说明：

- `●`：原生、明确支持，且是系统核心能力；
- `◐`：部分支持、近似支持，或依赖外部组件/特定配置；
- `○`：没有作为显式控制状态或主要能力；
- `—`：该项对系统不适用。

矩阵中的“知道”指该状态能进入控制决策，而不是系统内部某处存在一个计数器。“能执行”指系统可以主动触发该动作，而不只是被动接受引擎行为。

## 1. 状态能力矩阵：每个系统真正知道什么

状态维度定义：

- **KV 位置**：知道具体 prefix/block 位于哪个 worker；
- **真实/近似**：主要数据来自真实 engine events，还是由路由历史推测；
- **多层位置**：区分 HBM、CPU、SSD、远端共享存储；
- **引擎负载**：至少知道 active requests、queue、active tokens 或 batch；
- **执行进度**：知道 prefill/decode/chunk/token progress，而不仅是“请求活跃”；
- **数据移动**：知道 KV 正在 loading/transferring 及其进度或 ETA；
- **网络拓扑**：将带宽、链路或数据位置纳入决策；
- **未来关系**：知道 session、program DAG、未来访问提示或 sibling 关系；
- **失败/版本**：显式管理取消、失败、过期、租约或状态版本。

### 状态矩阵的直接结论

没有一个系统同时原生拥有以下全部状态：

```text
真实 KV block/tier 位置
+ engine queue/batch/token progress
+ KV loading/transfer progress与ETA
+ network/topology cost
+ session/program/future hints
+ cancellation/failure/version语义
```

Dynamo 最接近，但其 router 主要通过事件、预测索引和 worker load model 拼接这些信息；传输、引擎本地 scheduler 和 storage lifecycle 仍由不同组件拥有。Strata/Bidaw 对加载状态理解更深，但作用域集中在特定 engine 或分层缓存设计。Llumnix/Libra 有更强动作，却不是通用外部控制面。

## 2. 动作能力矩阵：系统能主动改变什么

动作维度定义：

- **初始路由**：选择请求进入哪个 worker；
- **本地重排**：改变 queue/batch 顺序；
- **副本规划**：主动复制、预热或稳定放置 prefix；
- **Fetch/Offload**：在存储层之间加载或卸载 KV；
- **迁移**：运行中把请求及 KV 换到另一实例；
- **切分/PD**：拆请求、拆阶段或跨实例继续；
- **Admission**：排队、限流、拒绝或按 SLO admission；
- **驱逐**：控制 cache eviction，而不是只接受引擎默认 LRU；
- **闭环纠错**：动作后根据真实结果修正模型或再次决策。

### 动作矩阵的直接结论

当前主流开源 router（vLLM Production Stack、SMG、Dynamo）最成熟的动作仍是：

```text
为新请求选择一个 endpoint
```

而论文系统已经证明以下动作在各自场景中有效：

```text
迁移运行中请求          Llumnix
把请求按 token 切分      Libra
主动规划 prefix 副本     Preble / CacheRoute
比较 fetch 与 recompute  CacheGen
加载感知的本地重排       Strata / Bidaw
应用提示驱动预取         SYMPHONY
按 program 调度          Agentix
```

问题在于这些动作分别被封装在彼此不兼容的专用系统中，尚未形成一个面向 vLLM/SGLang 的通用、渐进增强的控制面。

## 3. 目标、有效负载与退化条件矩阵

| 系统 | 首要优化目标 | 最有效的负载/环境 | 主要退化条件 |
|---|---|---|---|
| vLLM/PagedAttention | 单实例吞吐、KV 内存利用率 | 多并发、动态长度、严格前缀复用 | 跨实例状态不可见；prefix reuse 少时 APC 收益低；block/hash 管理仍有 CPU 成本 |
| vLLM load-aware router | cache hit 与 endpoint load 折中 | 多副本、稳定 prefix reuse | `beta` 需适配；只看 matched ratio 与 in-flight count；缓存信息或负载过期 |
| SGLang/RadixAttention | 结构化调用中的本地 KV reuse | agent/few-shot/分支、共享 prefix | 跨 worker cache 被打散；radix 操作与大 waiting queue 有 CPU 开销 |
| SGLang SMG | cache affinity + shortest queue | prefix groups 明显、负载差异可由 queue 反映 | approximate tree 与真实 eviction 不一致；阈值切换抖动；多 router 视图延迟 |
| Dynamo | 通用生产路由、KV reuse、负载与队列 | vLLM/SGLang/TRT-LLM，多层 cache、PD | 配置面复杂；事件/预测可能不一致；不同组件缺少统一完成时间；策略仍需场景调优 |
| llm-d | K8s 原生 KV-aware routing + P2P sharing | vLLM fleet、NIXL 网络、共享 cache | promised block 未交付、外部组件依赖、控制面部署复杂 |
| LMCache | 减少历史 KV 重算、扩展 cache capacity | 多轮、长上下文、可复用 KV | 低复用时只增加元数据/I/O；加载可能慢于重算；上层 router 不感知 I/O 时会误选 |
| Preble | 平均/p99 延迟 | 高 prefix sharing 的分布式 prompt workload | 低复用时全局 tree/affinity价值下降；热点复制与负载估计失准；动作集中在 placement |
| LMetric | TTFT/TPOT，免调参 | cache 与 batch size 足以解释成本的同构集群 | 网络/分层 cache/迁移成本显著；batch size 不能代表真实排队；论文已给出少数乘法失效条件 |
| Mooncake | SLO goodput、长上下文成本 | 大规模长上下文、多轮、快速互连与大 DRAM/SSD 池 | 架构和基础设施重；KV 传输带宽不足；短上下文或低复用收益有限 |
| Sarathi-Serve | 单 engine throughput-latency balance | prefill/decode 混合、pipeline parallel | chunk 太小增加调度开销，太大仍阻塞；不解决跨实例 placement |
| DistServe | TTFT/TPOT 双 SLO goodput | P/D 特性明显、网络足够快、负载相对可规划 | KV 传输昂贵；P/D 比例快速变化；资源池静态配置不匹配 |
| Llumnix | tail latency、优先级、弹性 | 负载动态、热点漂移、需抢占/扩缩容 | 迁移带宽竞争；短请求迁移得不偿失；实现侵入 engine lifecycle |
| CacheGen | context loading latency | 远端长 KV、带宽波动 | 编解码开销超过节省；短上下文；压缩质量预算严格 |
| Strata | hierarchical cache throughput | 超长上下文、CPU/SSD cache、大 I/O | 短上下文/高 HBM hit；专用 I/O 路径不可用；调度与 engine 紧耦合 |
| Bidaw | multi-turn latency/throughput | 交互式会话、host+SSD 两级缓存 | 单轮或不可预测返回；预测错误；额外队列可能损害公平性 |
| Libra | SLO goodput、动态负载平衡 | 输入/输出强不平衡、严格 SLO | KV segment transfer 成本高；短请求切分无益；需要较强 engine 修改 |
| SYMPHONY | latency、request-level load balance | 可从工作流/交互提前获知下一访问 | hints 缺失或错误；预取污染；应用不愿修改 |
| Agentix | program end-to-end latency、公平性 | 多步 agent/program workload | 独立单请求无优势；program identity 缺失；程序级优先级可能伤害 request tail |
| CacheRoute | capacity、稳定 hit rate | 长期稳定的高频 prefixes | 低复用/快速热点变化；计划窗口滞后；论文报告某些低复用 32B 负载下低于 flat LB |

## 4. vLLM、SGLang、Dynamo 当前究竟缺什么

以下判断以 2026-09-30 的公开文档和代码为准。这里的“缺”不是完全没有相关代码，而是缺少可作为通用工程控制面的完整语义。

### 4.1 vLLM：强执行引擎，弱跨实例控制闭环

#### 已经具备

- 成熟的 block allocator、hash-based APC、refcount 与 LRU；
- full-block 精确复用、cache salt、LoRA/multimodal identity；
- continuous batching、chunked prefill、抢占、pause/resume；
- KVEvents、KVConnector、NIXL、Mooncake、LMCache、offload 与 PD 接口；
- Production Stack 中的 cache-aware/load-aware routing。

#### 稳定缺口

1. **引擎事件与外部路由决策之间没有统一完成时间语义。** `Stored/Removed` 描述结果，queue、prefill progress、connector loading/transfer 分散在不同接口中。
2. **Production Stack router 的核心仍是入口 endpoint selection。** 它没有把 migration、replication、fetch-vs-recompute、eviction coordination 统一成一个动作模型。
3. **KVConnector 是数据路径扩展点，不是统一控制协议。** 不同 connector 对位置、加载失败、取消、租约、共享 materialization 的语义不同。
4. **跨实例策略与本地 scheduler 缺少协同契约。** 外部 router 很难准确知道请求进入 worker 后将形成什么 batch、何时获得 prefill token budget。
5. **版本/能力差异需要调用方自己处理。** connector、event、hash 与 scheduler 能力随版本演进，缺少标准 capability negotiation。

### 4.2 SGLang：强本地 prefix/program reuse，集群视图仍不统一

#### 已经具备

- RadixAttention、真实本地 radix cache、丰富本地 queue policy；
- hierarchical cache/HiCache 与 PD serving；
- 生产级 Rust Model Gateway，支持 cache-aware、power-of-two、consistent hashing、prefix hash、health、retry、rate limit 和 observability；
- 默认 cache-aware router 可维护每 worker approximate radix tree，也能接外部 indexer。

#### 稳定缺口

1. **默认 gateway cache view 是“根据路由历史推测缓存”，不是完整 engine truth。** Worker 的真实 eviction、partial materialization 和非本 gateway 流量可能造成偏差。
2. **gateway 和 SRT scheduler 各自做决策。** gateway 不掌握 radix match 后的真实 batch formation、chunked prefill 进度和 hierarchical loading ETA。
3. **threshold switching 是启发式控制。** cache threshold、absolute/relative balance threshold 对 workload 敏感，且可能在临界点反复切换。
4. **强大的本地缓存动作难以由外部策略组合。** Strata、HiCache、RadixAttention 的 loading/eviction 状态尚未形成稳定、引擎无关的控制 API。
5. **多 gateway/多模型/PD 的状态域正在演进。** pool/model 隔离与 mesh 同步已在改进，但这也说明接口稳定性和统一视图仍是工程问题。

### 4.3 Dynamo：最接近通用控制面，但仍是组件拼装而非统一决策模型

#### 已经具备

- vLLM、SGLang、TensorRT-LLM 等后端；
- event-driven 与 approximate KV index；
- predicted TTL 解决 sibling 请求早于 KV event 的竞态；
- device/host/disk/shared cache credits；
- active block、prefill token、active request、output growth 等 load tracking；
- queue、FCFS/WSPT、priority、policy classes、custom worker-selection policy；
- session/parent-agent affinity、AIS prefill duration model、topology-aware KV transfer；
- 完整生产部署、发现、健康和配置体系。

#### 稳定缺口

1. **状态统一但尚未“时间化”。** KV overlap、active load、host/disk hit 各自进入 cost model，但没有通用的 `time-to-usable KV` 与端到端 `predicted completion time` 契约。
2. **predicted TTL 表示“可能将存在”，不表示生产进度、共享条件和失败概率。** 它可让 siblings co-locate，却不能完整比较等待、重算、远端 fetch 或建立第二副本。
3. **策略扩展主要替换 worker ranking。** discovery、queue、reservation、accounting 由 Dynamo 管理，但迁移、复制、驱逐、fetch/recompute 仍不是统一 policy action。
4. **大量独立 knobs 增加调优与归因成本。** overlap credit、decay、prefill scale、host/disk weight、queue threshold、policy class 等能表达很多场景，也可能形成复杂配置空间。
5. **跨层反馈不完全闭合。** routing decision、engine KV event、connector transfer、最终 TTFT/TPOT 可以被观测，但尚无通用在线校准器把结果反馈为策略参数、置信度和自动回退。
6. **可解释的反事实评估不足。** 当前能记录选择和指标，但不能原生回答“若选另一 worker/动作，预计会怎样”，也缺少统一 shadow-policy 对比接口。

## 5. 跨系统后仍然稳定存在的工程缺口

### G1. 缺少引擎无关的 KV 状态与能力契约

不是缺一个 cache index，而是缺少统一表示：

```text
KV identity / compatibility domain
physical tier and owner
resident / computing / loading / transferring / evicting
ready progress and estimated ready time
size, compression and transfer form
lease, version, cancellation and failure
sharing/isolation scope
```

vLLM、SGLang、Dynamo、LMCache、Mooncake/NIXL 各自暴露部分信息，但没有一个轻量公共契约允许 router 在不理解 backend 内部实现的情况下正确比较动作。

### G2. 缺少“端到端完成时间”而不是指标加权的决策接口

现有系统常分别观察：cache overlap、queue、batch size、active tokens、host/disk hit、network topology。它们最终仍需要手工权重或特定启发式组合。

稳定缺口是把候选动作转换成同一单位：

```text
预计 TTFT / TPOT / completion time
置信区间
违反 SLO 的概率
产生的增量 GPU work 与 network bytes
```

这不是要求一定用复杂 ML 模型。LMetric 说明简单模型可能更稳健；关键是预测接口、在线校准和误差回退必须统一。

### G3. 缺少超越“初始放置”的通用动作平面

论文已经分别验证 migration、replication、prefetch、fetch-vs-recompute、segment split、queue reorder 有价值，但主流开源 router 没有统一的：

```text
Action = Route | Wait | Fetch | Recompute | Replicate |
         Migrate | Split | Evict | Reject
```

工程上不应第一版全部实现，而应先定义 capability-based action API：backend 支持什么就安全启用什么，不支持就退化为普通 route。

### G4. 缺少自动策略选择与安全退化

不同负载下不存在永远最优的策略：

- 高复用：prefix affinity 有效；
- 低复用：least-loaded/LMetric 更稳；
- 稳定热点：副本规划有效；
- 快速突发：长期规划跟不上；
- 网络拥塞：远端 KV 可能不如重算；
- 严格 SLO：可能需要牺牲 cache hit；
- agent workload：program/session 信息比纯 prefix 更重要。

当前系统允许人工选择策略，却普遍缺少基于在线证据的 regime detection、shadow evaluation、切换迟滞和 no-regression guardrail。

### G5. 缺少路由—执行—存储的闭环归因

一次请求慢，可能来自：

```text
router stale state
queue prediction error
local batch interference
KV load/transfer stall
cache eviction
engine preemption
network contention
output length underestimation
```

现有 observability 多能记录其中部分指标，但缺少统一 request/KV/action trace，把最终 TTFT/TPOT 归因到某次路由和数据动作，并反向更新估计器。

### G6. 缺少跨引擎公平、可复现的评测与兼容性层

不同项目常使用不同模型、trace、SLO、cache warmup、tokenizer、block size 和网络，因此论文中的倍数难直接比较。工程项目需要：

- 同一 workload 同时驱动 vLLM 与 SGLang；
- 统一请求与 KV trace schema；
- 同时报告 request metrics、GPU work、KV bytes、cache amplification、control overhead；
- 记录版本与 capability；
- 对 unsupported feature 自动降级，而不是静默改变语义。

### G7. 多租户安全与共享收益缺少统一策略

vLLM 已支持 cache salt，但跨 router、external cache、P2P transfer 和 session affinity 时，sharing domain 需要端到端一致。当前缺少同时表达：

```text
谁可以知道 prefix 存在
谁可以复用其 KV
谁可以接收远端 KV
不同 tenant 是否允许共享物理副本
性能指标是否泄露 cache residency
```

这不是第一版性能核心，但决定插件能否进入真实多租户环境。

## 6. 缺口优先级：哪些值得成为工程核心，哪些先不要做

| 优先级 | 缺口 | 工程普适性 | 与现有系统差异 | 第一版可行性 | 建议 |
|---|---|---:|---:|---:|---|
| P0 | 统一状态/能力契约（G1） | 高 | 高 | 高 | 应成为基础，不必先声称算法创新 |
| P0 | 跨引擎统一 benchmark/trace（G6） | 高 | 中高 | 高 | 先做，决定后续所有结论是否可信 |
| P1 | 完成时间/SLO cost interface（G2） | 高 | 高 | 中高 | 先从可解释模型和在线校准做起 |
| P1 | 自动策略选择与安全退化（G4） | 高 | 高 | 中 | 最有机会形成项目特色 |
| P1 | 跨层 action trace 与归因（G5） | 高 | 高 | 中高 | 既提升效果，也提升可运维性 |
| P2 | capability-based action plane（G3） | 高 | 高 | 中低 | 先支持 Route/Wait/Fetch，后扩展迁移/复制 |
| P2 | 多租户共享策略（G7） | 中高 | 中 | 中 | schema 先预留，性能闭环稳定后实现 |
| 暂缓 | 跨模型/异构 KV 复用 | 场景依赖 | 高 | 低 | 符合当前“不做异构”的边界 |
| 暂缓 | 自研 KV 压缩/attention kernel | 中 | 低到中 | 低 | 作为 backend capability 接入，不作为核心 |
| 暂缓 | 全面 program-aware scheduler | 增长中 | 中 | 低 | 先支持 hints/session/program ID，不接管完整 DAG |

## 7. 从能力矩阵导出的三个候选工程定位

这一步只形成候选，不立即确定最终核心问题。

### 候选 A：跨引擎 KV Control Plane

一句话：为 vLLM/SGLang 提供统一的 KV 状态、负载、传输与能力抽象，使同一策略可以在不同 backend 上运行并安全退化。

- 优点：工程价值明确，兼容性强，适合 GitHub 项目；
- 风险：如果只做 adapter 和 dashboard，容易被评价为工程整合；
- 必须补足：基于统一状态实现至少一个现有系统做不到的闭环能力。

### 候选 B：Adaptive KV Routing Runtime

一句话：不预设唯一最佳策略，在线识别 workload regime，在 LMetric、least-loaded、prefix-affinity、session-affinity 等策略之间进行有迟滞的安全选择。

- 优点：不是为某个小场景服务；可直接面向“整体效果好”和 no-regression；
- 风险：策略切换本身可能被认为只是 meta-heuristic；
- 必须补足：shadow policy、反事实估计、可解释切换和严格 guardrail。

### 候选 C：Closed-loop KV Orchestrator

一句话：把路由、KV fetch、等待/重算选择及执行结果串成闭环，用真实 TTFT/TPOT 与 KV 数据移动结果持续校准决策。

- 优点：同时覆盖效果、可运维性和多层 KV；比一次性 routing score 更完整；
- 风险：第一版动作范围过大时会失控；
- 必须补足：先限制为 `Route + Wait/Fetch/Recompute`，迁移/复制作为后续 capability。

### 当前推荐的组合方式

```text
A 作为基础架构
+ B 作为第一阶段可见特色
+ C 的最小闭环作为效果来源
```

也就是：先做跨引擎统一状态和 benchmark，再实现可自动退化的多策略 runtime，最后加入少量跨层动作和在线校准。这样既不是只解决一个小场景，也不是一开始就重写 Mooncake/Dynamo/SGLang。

## 8. 下一步验证清单

在确定最终核心问题前，需要用代码与实验回答这些问题：

1. vLLM 和 SGLang 能否以可接受开销持续提供统一的 queue、active tokens、cached blocks、eviction、load/transfer events？
2. 仅使用公开接口时，Dynamo 与 SMG 的路由决策和实际 TTFT 误差有多大？误差主要来自状态陈旧还是模型不准？
3. LMetric、least-loaded、prefix-affinity、session-affinity 各自在 workload matrix 的哪一块占优？是否存在可在线识别的 regime？
4. 自动选择策略能否在每类 workload 上接近最佳静态策略，并把最坏回退控制在 5% 内？
5. 统一状态与 tracing 的控制面开销能否控制在请求 CPU 开销的 2%–5% 内？
6. 当 event 丢失、worker 重启、transfer 失败、请求取消时，系统能否退化为正确的普通路由？
7. 同一套策略在 vLLM 与 SGLang 上是否仍成立，还是收益来自某个引擎的特定实现？

只有这些问题有了数据，才应该决定项目最终的核心问题与组件边界。
