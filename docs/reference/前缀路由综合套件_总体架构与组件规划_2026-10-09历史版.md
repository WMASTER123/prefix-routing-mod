# 前缀路由综合套件：总体架构与组件规划

更新日期：2026-10-09。状态：产品边界已有用户确认；以下逻辑架构为建议基线，尚未冻结代码接口、具体算法或实现底座。本轮仅整理资料和规划，未连接服务器、部署服务或运行性能实验。

## 1. 当前定位与决策依据

项目定位：**面向已有多副本 LLM 服务的、性能优先且便于接入的前缀路由综合套件。优先做好 vLLM-Ascend，在固定加速器资源下提高满足 TTFT 与生成停顿要求的可持续服务容量。**

综合套件包含在线路由、状态感知、运行保护、接入检查、性能校准及可复现实验工具。它不承担模型部署平台的全部职责。缓存干扰治理、渐进请求放置等既有设想保留为候选增强，是否启用由实际收益决定。

### 1.1 已确认、建议与未确认事项

| 事项 | 状态 | 当前约定 |
|---|---|---|

| 首版兼容范围 | 用户本轮确认 | 先做好 vLLM-Ascend，再增加其他后端；首个可用版不以第二种引擎为发布前提 |

| 性能口径 | 用户此前确认 | 固定 NPU/GPU 资源下的达标容量，受分类延迟、完成率、公平和控制开销约束 |
| 硬件 | 用户提供，未取得资源 | 华为 NPU，型号与实际显存未知；不借用其他项目服务器来代替本项目核验 |

| 交付形态 | 建议基线 | 一个外部路由服务，加命令行检查/评测工具；可选观测适配器按需要安装 |

| 性能优势 | 待验证 | 尚不能声明超过原生路由、Preble、DualMap、CacheRoute、Dynamo 或 SGLang |

## 2. 要解决的问题及工程收益

### 2.1 工作问题定义

> 对已有的多副本 LLM 服务，如何用低接入成本、可控的路由开销和可核验的状态感知，把前缀复用机会与各实例的实际服务余量结合起来，使不同复用率、输入输出长度和到达变化下的流量获得更高的达标容量，并能诊断何时有效、何时应关闭增强功能？

这是产品工作目标，不是“此前无人研究”的学术结论。缓存与负载协调已经存在大量有效方案。本项目必须证明的是在明确后端和负载范围内的增量，以及部署、诊断与复现的可用性。

潜在收益分为四类，应分别测量：

1. **计算与排队**：避免本可复用的 prefill 重算，同时不把高命中实例压成热点。
2. **服务容量与稳定性**：减少实例空忙不均及不恰当的请求聚集，改善 TTFT、生成停顿和完成率。
3. **路由自身开销**：控制解析、tokenization、索引查询、事件同步和流式转发成本，避免新增 CPU 瓶颈。
4. **使用成本**：提供经验证的默认配置、明确的能力报告、复现实验与故障诊断，减少用户手动调参和维护补丁。

第 1、2 类是待实测性能假设；第 3 类需要微基准及端到端验证；第 4 类可通过安装与操作验收确认。易用性不能替代性能证据。

### 2.2 对现有工作的基本判断

| 资料中已有的能力 | 对本项目的含义 |
|---|---|
| vLLM Router 已有 cache-aware、P2C、亲和等策略；公开路线图继续推进精确 KV 状态与 CPU 快路径 | 这些属于基础能力和强基线，不足以单独证明特色；路线图是计划，不能当作已发布能力 |
| SGLang 网关已有转发、健康、负载与缓存路由等工程能力；其一个 cache-aware 实现使用请求历史近似树 | 必须比较成熟网关，也要区分历史亲和估计与设备真实驻留；不能概括为所有 SGLang 模式都没有精确状态 |
| Dynamo 已提供状态驱动选点及策略扩展接口，宿主管理生命周期和资源记账 | 可以借鉴职责划分；不能声称“模块化路由”或“状态与策略分离”是新贡献 |
| LMetric 表明较简单的工作量与 batch 指标也可形成强策略 | 框架应容纳低开销方法，不把完成时间预测模型设为运行前提 |
| Preble、DualMap、CacheRoute 已覆盖不同形式的局部性、拥塞与放置问题 | 候选增强要在相同资源上证明增量，不靠更换名称界定区别 |

对应一手资料：[vLLM Router 策略](https://github.com/vllm-project/router/blob/main/docs/load_balancing/README.md)、[公开路线图](https://github.com/vllm-project/router/issues/244)、[SGLang 网关](https://github.com/sgl-project/sglang/blob/main/sgl-model-gateway/README.md)、[cache-aware 实现](https://github.com/sgl-project/sglang/blob/main/sgl-model-gateway/src/policies/cache_aware.rs)、[Dynamo 策略接口](https://docs.nvidia.com/dynamo/dev/knowledge-base/modular-components/router/write-custom-routing-strategies)、[LMetric 原文](https://arxiv.org/html/2603.15202)。论文之间更详细的比较见本地调研。

**目前没有足够证据支持“现有系统普遍没解决好，因此一定能超过它们”。**更稳妥的立项条件是：现有框架可作为基础；在 vLLM-Ascend 上建立可靠强基线后，有可重复、值得投入的剩余损失。若已有方案经合理配置已经满足目标，应优先复用、补齐适配或提交上游改进，缩小自研范围。

## 3. 总体框架：一个在线服务，配套工具，按需增强

以下是逻辑关系，不代表每个方框都是微服务。

```text
应用客户端
    │ 保持业务请求语义
    ▼
路由服务
    请求接入与生命周期
        → 合法实例筛选
        → 前缀/负载快照查询
        → 当前策略选点
        → 在途记账与转发
        → 流式响应、完成与异常反馈
             ▲                         │
             │                         ▼
      有界状态与配置快照 ← 后端适配/事件/指标
             ▲                         │
      可选后台优化计划                 ▼
                              既有 vLLM-Ascend 副本池

配套工具：配置生成与 doctor / 校准与 replay / 契约和故障测试
可选增强：持续亲和与放置 / 分层 KV 感知 / HA / 其他引擎适配
```

首版建议一个路由进程，状态在进程内通过明确接口共享；事件处理和后台分析异步执行。不要为了“可扩展”先增加多次每请求 RPC、数据库访问或一组独立微服务。评测与负载生成器独立运行，不挤占在线服务资源。

路由器管理 KV 的**元数据与请求落点**。KV 张量、分配器、本地淘汰及算子执行继续由推理引擎或已接入的缓存系统负责。只有一个后端实例时可做转发、观测和诊断，不宣称取得分布式放置收益。

### 3.1 复用现有框架与插件形式

产品可以作为外部服务安装，但不意味着必须从零实现 HTTP 网关。实现前对 vLLM Router 等候选底座做一次受限接口审计，检查：能否替换选点、接入所需状态、取得完整生命周期回调、保持请求字段、复用记账、独立升级及满足 NPU 接入条件。

- 若正式扩展点足够：优先把新增状态/策略/工具做成可维护扩展，复用其协议、连接池和基础运维。
- 若只能通过大面积 fork 才能接入：选用成熟网络组件构建薄宿主，保留策略核心，不复制一整套推理引擎。
- 选择嵌入模式时，由一个宿主负责队列、计数、最终发送及取消，避免两层路由器相互重新选点或重复记账。

此决策尚未完成，不能把“外部服务”误写成“已决定自研网关”。Dynamo 的公开扩展也明确区分策略选择与宿主职责；该接口当前文档标注实验性质，不能推导任意版本热加载兼容。[Dynamo 接口边界](https://docs.nvidia.com/dynamo/dev/knowledge-base/modular-components/router/write-custom-routing-strategies)

## 4. 稳定核心：八个逻辑组件

| 组件 | 必须承担的职责 | 性能或工程价值 | 不承担的职责 |
|---|---|---|---|
| 1. 协议接入与请求生命周期 | 保持请求字段、流式转发、超时/取消、连接池、背压、错误传播；有限入口等待 | 控制路由附加延迟，避免请求与资源泄漏 | 改写 prompt、执行工具、管理对话数据库 |
| 2. 实例池与能力管理 | 模型兼容域、实例/rank 身份、健康、代次、加入/排空；声明状态接口能力 | 避免错投、陈旧端点和不支持的优化 | 启停模型、申请设备、自动扩缩容 |
| 3. 后端适配 | 把原生请求、指标、缓存事件及错误映射成明确语义；管理连接/订阅 | 隔离版本差异，降低核心和引擎耦合 | 把缺失字段伪装成零值或精确观测 |
| 4. 前缀身份与驻留目录 | 前缀匹配、实例位置、状态来源/时效；区分真实事件、历史推断、预计形成 | 识别可复用机会，减少虚假命中；限制元数据成本 | 保证缓存不会淘汰、存储 KV 张量 |
| 5. 负载与在途工作记账 | 已分派请求、可得的等待/运行工作量、输出进展、引擎负载；处理迟到反馈 | 避免连续请求共同涌向看似空闲的实例 | 把软件预记账当成引擎显存预留 |
| 6. 路由策略执行器 | 按能力取状态、运行一个明确的当前策略、验证结果、提交选点、回退 | 容纳强默认策略和后续改进，维持低开销 | 让多个控制器同时覆盖最终落点、强制依赖未来预测 |
| 7. 运行保护与观测 | 有界资源、公平/过载保护、配置验证、采样决策记录、指标、故障降级 | 限制增强策略损失，定位瓶颈和兼容问题 | 承诺所有负载零退化、掩盖拒绝与超时 |
| 8. 接入与验证工具链 | doctor、启动示例、校准、基线/replay、契约/故障测试、版本支持报告 | 让性能可验证、使用可重复、兼容可维护 | 在线执行压测或未经授权修改生产配置 |

这八个模块是为了明确所有权，并非要求八个独立包。前缀目录与负载账本分开，是因为两者来源、更新频率和失效规则不同；由策略层联合读取。工具链独立于请求路径，避免为了使用路由而强制运行评测系统。

### 4.1 核心契约：现在明确，字段细节稍后设计

| 对象 | 最少需要表达的语义 |
|---|---|
| 请求上下文 | 请求 ID、模型/隔离域、输入类型、可得输入规模、服务约束、可选会话提示；不依赖应用必须加标签 |
| 实例状态 | 实例及重启代次、可路由地址/rank、健康与排空状态、能力、观察时间 |
| 前缀匹配结果 | 匹配单位、可复用范围、来源、观察时间、未知部分；不把近似文本相似度当作真实 KV 命中 |
| 负载快照 | 指标单位、来源、覆盖范围、时间戳、本地未反映分派量；允许 unknown |
| 路由决定 | 目的地、策略/配置版本、简短理由、使用状态的质量、提交/撤销状态 |
| 后台建议 | 生效范围、版本、有效期、变化预算；失效后有默认行为，不是无限期硬绑定 |

现在不冻结通用的 `migrate/split/evict/replicate` 动作总线。核心动作是选点与有限接入控制；未来有真实后端能力时，再为有副作用的操作设计专用契约、幂等 ID 和完成回执。

## 5. 必须从第一版保证的性能与正确性边界

### 5.1 前缀身份和状态可信度

同样的文本不自动代表同样的实际 token 前缀。精确模式要匹配模板、tokenizer、模型配置、块边界和隔离域；涉及 LoRA 等配置时还需额外身份。vLLM 的块标识依赖前序块、token 和附加键，缓存盐也参与隔离。[vLLM APC 设计](https://docs.vllm.ai/en/latest/design/prefix_caching/)

因此，建议支持两种明确标识的感知级别：

- **基础亲和模式**：根据经过验证的历史请求特征估计机会，配合可得负载；不能把历史发送成功当成缓存现在驻留。
- **事件感知模式**：使用核验过的后端事件和兼容 token/block 身份建立目录；异步事件仍有传播延迟，不保证选点后必然命中。

“计划送过去”“已发送”“预计稍后产生 KV”“观测到驻留”分别记录。缓存事件也不是所有请求访问记录；`BlockStored`、`BlockRemoved` 可用于目录更新，不足以单独精确归因每次访问与重算。[vLLM 事件接口](https://docs.vllm.ai/en/latest/api/vllm/distributed/kv_events/)

重启代次变化应失效旧目录。丢事件时使用后端确实支持的重放/快照恢复；没有恢复接口或已超出重放窗口时，标记受影响状态不可信并降级。不得假设任意后端都支持全量快照。

Ascend 官方矩阵列出 APC 支持，为首后端提供可行性依据；它不能证明将来申请的具体版本具有完整事件和负载接口。[Ascend 特性矩阵](https://docs.vllm.ai/projects/ascend/en/latest/user_guide/support_matrix/supported_features.html)

### 5.2 请求生命周期、排队和资源所有权

选择目的地后，先记录本路由器已分派但尚未反映到后端指标的工作，防止突发流量重复消耗同一份“空闲”。必须明确哪些本地计数已经包含在引擎指标中，避免重复相加。

前端连接断开不必然意味着后端计算结束。取消需尽可能传播；状态不确定时保留有界的不确定工作记录并对账，而非立即宣称资源已释放。超时、完成与迟到回执应幂等处理。已输出内容的请求不得透明换副本重启；发送后接纳状态不明时，也不能默认安全重试。

入口默认不做长时间集中排队。仅允许有上限的接入等待和背压，等待时间计入 TTFT，拒绝与超时计入服务结果。优化不能通过压低完成率或长期推迟长请求提高表面 goodput。

若同一后端同时接收绕过本路由器的流量，局部账本只能反映部分工作。doctor 应报告覆盖范围；优先结合引擎指标，无法观测时降低状态置信度。首版验证优先使用流量边界可控的副本池。

### 5.3 在线开销与数据最小化

- 单次请求尽量复用解析和 tokenization 结果；若后端仍需重新 tokenization，应如实计入总开销，不能称已消除端到端重复。
- 不为获取新鲜状态而逐请求查询所有副本；读取带时效的快照，在后台更新。
- 索引、请求历史、观测队列、日志缓冲和指标标签均有上限；禁止每请求扫描全部历史前缀。
- 对前缀索引更新和查询的锁竞争、事件积压、CPU、RSS、p99 附加延迟建立预算；数值经校准冻结。
- 关闭增强模块时，应同时停止不必要的后台计算；不因“只做观测”而忽略开销。
- 默认不记录原始 prompt、完整输出、凭据；哈希与 token 元数据也按敏感数据处理，租户隔离和访问控制不可由策略绕过。

### 5.4 生成停顿如何衡量

客户端 TTFT 从提交开始计时。若服务端合并多个 token 到一个 SSE chunk，客户端 chunk 间隔不能直接当成逐 token TBT。评测需要区分客户端可见停顿、平均 TPOT 和后端真实 token 时间；后者只有拿到相应观测才能报告。既有“生成停顿目标”保留，具体统计口径与阈值在实验前确认。

## 6. 增强组件：保留扩展位置，逐项验收

| 增强模块 | 何时值得启用 | 依赖与边界 | 当前优先级 |
|---|---|---|---|
| 性能校准与配置建议 | 需要为给定模型/设备确定合理默认参数 | 先离线校准；不要求精确预测每次完成时间，不自行扰动生产流量 | 首版工具能力；复杂模型后置 |
| 持续亲和、热点分流与渐进放置 | 基线存在可重复的过度分散、热点或调整损失 | 软建议、有有效期、拥塞逃逸和变化预算；利用真实请求形成副本 | 首轮重点评估候选 |
| 缓存干扰与重建分析 | 强基线下观察到可避免的重算及服务损失 | 区分必要淘汰、重启、私有 KV 和可复用工作集；观测不全时标明估计 | 保留原研究方向，非框架前提 |
| 分层 KV 感知 | 现有服务已接 CPU/远端缓存，位置影响选点 | 区分设备可用、远端可取、加载中；复用已有缓存系统的数据路径 | 有部署需求再接入 |
| 预热、复制、保留提示 | 被动导流不足且有明显净收益 | 后端正式能力、带宽/容量预算、操作回执；不能覆盖任意引擎淘汰 | 后续增强 |
| 第二种引擎适配 | vLLM-Ascend 首版已稳定，需证明接口可扩展 | 复用契约；按功能逐项支持，不只测试 HTTP 能通 | 后续兼容版本 |
| 多路由副本与 HA | 单路由吞吐或可用性不能满足目标 | 控制权、跨副本在途量、计划版本、状态恢复及故障语义 | 成熟部署必需；首版明确单实例限制 |
| P/D 分离与传输协同 | 用户接入已有分离部署 | 分阶段目的地、传输与取消的真实接口；不自研全套传输系统 | 后续独立适配 |
| 会话/Agent 提示 | 应用愿意提供可靠提示且实测有增益 | 普通请求仍能用；不要求重写应用或公开完整 DAG | 可选 |
| 本地 batch/kernel 协同 | 后端明确支持且必要 | 硬件与版本独立验收，需承担更高适配成本 | 不列为当前交付承诺 |

其中“后台慢路径”指按一段历史更新亲和或放置建议，“快路径”指每个请求立即执行选点。没有慢路径也能运行完整基础套件；慢路径不阻塞请求。这种划分用于控制开销，并非额外的性能创新声明。

扩展能力不应各自修改最终落点：后台生成建议，前台由一个执行器综合当前状态作最终选择，统一经过合法性和过载保护。

## 7. 用户使用方式与兼容性承诺

建议最终入门流程：

1. 按支持版本的示例启动或沿用已有 vLLM-Ascend 服务，填写模型池、后端地址与必要认证信息。
2. 运行检查工具，得到协议、模型身份、APC、事件、指标、连通性和当前优化级别报告。
3. 启动路由服务，应用主要修改 API base URL；不要求业务增加特殊标签。
4. 使用健康与统计接口查看运行状态；在独立测试环境执行配套基线实验。
5. 根据实际瓶颈选择增强模块。关闭模块后回到验证过的基础策略，不要求用户修改算法。

检查报告分为“协议可接入”“前缀/负载增强可用”“缓存操作可用”，逐项解释缺失能力；不要只显示一个“完整优化”绿灯。可选 hook 由项目提供版本化包或镜像、开启说明和卸载路径。用户是否允许安装尚未确认，基础转发与降级模式不得依赖其接受补丁。

首版不强制 Kubernetes、Redis、外置 KV 存储或完整监控集群。基础日志、健康检查和指标必须可用；企业可按需接入自身观测系统。认证、TLS、管理接口隔离和凭据处理需提供经过验证的部署方案，允许由已有入口设施承担，不能因已有设施就省略安全边界说明。

## 8. 哪些需要自研，哪些优先借鉴

| 部分 | 处理原则 |
|---|---|
| HTTP、流式转发、连接池、标准指标 | 优先复用成熟实现，测试行为与开销，不重复造基础设施 |
| Ascend 能力映射、版本兼容、状态质量 | 项目必须落实；这是可靠优化的基础，但不自动是性能特色 |
| 前缀与工作量状态接口 | 结合原生能力设计；借鉴事件索引和在途记账，避免承诺得不到的数据 |
| 默认选点方法 | 比较成熟低开销方法再决定；LMetric 等提供候选，不拼接所有论文公式 |
| 持续亲和/放置、干扰控制 | 若实测显示增量空间，自行设计适合接口与目标的控制；借鉴已有工作并正确署名 |
| 分层存储与传输 | 接入已有系统，首版不重建 LMCache/Mooncake 类数据层 |
| 评测、诊断、支持矩阵 | 从第一版建设，是产品交付的一部分，不能留到“算法做好之后” |

构建特色的合理路径是：找出强基线中反复出现的损失，形成可安装的改进，再通过同资源对照确认。候选包括低开销可信状态、变化负载下的稳定放置及 NPU 上的完整工程验证。它们目前都是候选价值，不是已证明的独有能力。

## 9. 性能验证与功能准入

### 9.1 三层实验

| 层次 | 目的 | 最少对照 |
|---|---|---|
| 协议与控制开销 | 确认加网关未造成不可接受成本 | 直接后端、仅转发、基础路由、打开观测但不改变选点 |
| 基础路由效果 | 建立强默认方案 | P2C/负载路由、原生缓存感知、亲和策略；可运行的更强实现或明确标注差异的移植 |
| 增强净收益 | 确认每个新模块必要 | 相同核心开/关模块，静态与动态配置，冷启动与阶段变化全部计入 |

保持同一 vLLM-Ascend 后端、模型、精度、总设备、KV 预算、原生优化和输入/输出规则。Dynamo/SGLang 整栈对比需额外验证 NPU 可部署性；策略移植不等于原系统复现，也不能借不同引擎内核差异宣称路由增益。

### 9.2 负载与主指标

负载至少包含自然前缀复用、多轮增长、长短输入/输出混合、突发与变化，以及无复用、低压力、短输入长输出等负对照。现有规划中的 WildChat、LongBench、BurstGPT/Azure 等作为候选，继续区分真实内容、到达统计与半合成组合；不只挑选有利 trace。

主指标为在指定服务合同下可持续承载的请求到达率，并同时报告达标完成率/达标请求数、全部完成率及分类延迟。不能仅展示更高的瞬时 tokens/s 或命中率。SLO 的统计口径、各类别目标、窗口和热身方式先冻结再比较。

评测包含客户端排队与网络等待、迁移/调整成本、路由 CPU/内存、状态陈旧程度及兼容模式。影子选点可检查开销和决定分歧，但不能证明改变缓存分布后的收益；同缓存域逐请求 A/B 会互相影响，优先完整独立 replay 或隔离资源池。

### 9.3 增强模块进入默认配置的条件

1. 能解释损失来源，必要状态可获得且语义正确。
2. 在多个代表性负载中相对强基线有可重复净收益，改善达标容量而非只改善代理指标。
3. 常见负对照和分类服务约束通过事先设定的门槛。
4. 增量 CPU、内存、元数据和调参成本可接受。
5. 故障、取消、重启、事件丢失、状态恢复和关闭增强功能都有测试。

既有文档的“10%–15% 改善、约 5% 负对照退化”保留为候选投入门槛，并非本轮新承诺；由硬件校准与服务需求确认。回退不能撤销已发生的淘汰和重算，不保证任何负载零退化。

## 10. 实施顺序与尚待确定的信息

| 阶段 | 交付与退出条件 |
|---|---|
| A. 框架确认与底座审计 | 确认本文职责、已有框架扩展点、协议及状态契约；没有环境也可先完成设计审查 |
| B. 资源申请后的能力核验 | 固定 NPU/软件版本、APC 与事件实测、模型参数、独立副本数、真实可用状态；不以支持矩阵代替测试 |
| C. 可用基础套件 | 一个后端、稳定转发/状态/强默认路由、检查和评测工具，公开支持边界；先测增量和开销 |
| D. 有证据的性能增强 | 按主要损失选择持续亲和、干扰治理等模块，逐个消融；没有净收益不进入默认配置 |
| E. 扩展与发布成熟化 | 增加后端、HA 或分层能力，按用户需求逐项验收；维护版本 CI、安装示例和可复现报告 |

现在已有足够信息讨论并采用逻辑框架，不需要用户继续选择算法。后续信息的必要时间如下：

- **资源申请后**：确切 NPU 型号/数量、是否独占、服务启动命令与镜像、vLLM/Ascend/CANN 等版本、网络与 CPU 条件。当前不用提供服务器输出。
- **打包方式确定前**：是否允许容器或适配包、离线安装要求、现有认证入口。此前未确认，不默认取得安装 hook 的许可。
- **正式实验前**：TTFT 与生成停顿阈值、统计口径、关注的业务类别及可接受控制成本。无生产 trace 也可先用公开资料，但不能据此保证特定企业的真实收益。
- **若首版已有特殊需求**：多模态、P/D 分离、不能统一入口的共享后端、多租户严格隔离等，应提前说明。这些会改变接口审计范围；当前不默认纳入全面支持。

**本轮结论：产品定位和部署边界已明确；八个核心组件及增强位置可作为架构讨论基线。具体实现底座、数据结构、参数与算法尚未冻结，性能优势尚待验证。下一步应完成接口/状态契约与复用审计，再进入受控实现，不直接围绕旧研究假设堆叠功能。**
