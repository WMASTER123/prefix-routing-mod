## 核心问题和适用边界

### 问题的因果链

当前问题的研究对象不是“KV cache 越多越好”，也不是泛化的“同时优化缓存和负载”，而是**请求放置的跨请求外部性**：一次路由决定的不只是当前请求的命中率和排队时间，它还会改变目标副本此后的 KV 工作集、可复用状态和 decode 压力，进而影响尚未到达的请求。

| 论证位置 | 本项目中的具体内容 |
|---|---|
| 背景 | 多副本 LLM 服务依靠 prefix KV cache 跳过重复 prefill；真实流量同时包含共享模板、多轮会话、长上下文和低复用的一次性请求。 |
| 直接原因 | 这些请求竞争有限的 KV 空间和执行容量，而路由选择决定每个副本接收什么工作集。 |
| 结构性根因 | 只依据当前 cache hit 和当前负载的逐请求选择，不能完整表示本次放置对后续缓存存活、重复计算、输出 KV 增长及未来队列的影响。 |
| 第一类后果 | 过度分散或混合放置使可再次使用的前缀被低复用 KV 挤出，后续请求重新执行本可避免的 prefill。 |
| 第二类后果 | 过强的亲和、保留或单副本聚集把热点请求集中到少数实例，造成排队、生成停顿和资源闲置，并可能牺牲低复用请求或低频租户。 |
| 用户可见结果 | TTFT 与 TBT/TPOT 尾部恶化，缓存命中不能稳定转化为 SLO goodput，固定资源的有效服务容量下降。 |

这里的“有价值前缀”仅表示其未来复用所节省的计算或服务时间大于保留、复制和负载偏斜的代价，不表示业务优先级更高。所谓“低复用请求”也不等于低优先级请求，系统仍须满足其等待、公平和完成率约束。

### 论文式问题陈述

> **现代多副本 LLM 服务通过复用 prefix KV cache 避免重复 prefill，但混合在线流量的复用程度、上下文长度和生成工作量持续变化，使一次请求放置同时改变当前执行负载和未来 KV 工作集。仅依据即时缓存命中与负载进行选点时，这种跨请求影响会累积为两类相反损失：可复用前缀被低价值 KV 反复挤出并重算，或请求因缓存亲和被集中到少数副本而形成拥塞。本文研究如何在延迟和服务公平约束下，通过可插拔控制协调请求落点与前缀副本，使缓存复用稳定转化为固定资源下的 SLO goodput。**

如果需要在摘要或项目主页中压缩成一句话，可使用：

> **混合 LLM 流量使请求放置同时改变当前负载和未来 KV 工作集；忽略这种跨请求影响，会导致可复用前缀反复重算或因过强亲和形成热点。本项目研究一种可插拔的请求放置与前缀副本协调机制，在 TTFT、生成停顿和服务公平约束下提高固定资源的 SLO goodput。**

这里没有把“插件”提前写成问题根因。插件是工程约束和交付形态；真正的问题是路由决策对未来缓存和服务状态的持续影响。

产品暂定定位为**面向混合负载的 KV 干扰感知路由与弹性请求放置插件**。弹性放置指调整请求的优选实例集合，不要求修改 GPU 数量，也不默认包含运行中请求迁移。

### 建议申请多少设备

优先申请 **4 个同型号、每个约 60GB 级显存、可独占的 NPU 设备**，目标是 4 个可独立路由的模型副本。这里按引擎可见设备计数，不把物理板卡、芯片或服务器名称自动等同；实际设备编号与可用容量须核实。

| 阶段 | 建议资源 | 目标与局限 |
|---|---|---|
| 环境与接口核验 | 1 个 NPU | 验证模型、APC、流式协议、指标和事件；不能证明分布式路由收益 |
| 最小机制验证 | 2 个 NPU，优先 2 × TP=1 | 能做亲和、分流、缓存竞争实验；实例少，隔离和借用空间有限 |
| 主实验 | 4 个 NPU，优先 4 × TP=1 | 有空间比较动态放置、静态分池、热点分流和混合流量；首批推荐规模 |
| 扩展验证 | 8 个 NPU | 条件允许时测试 8 个单设备副本，或较大模型的 4 × TP=2；不作为首轮必需 |

4 个设备组成一个 TP=4 模型实例，通常只有一个可路由目的地，不能替代 4 个独立模型副本。若单设备模型不能稳定承载目标上下文，先换较小模型或增加设备，不为凑副本而强行启动。

同一服务器上的 4 副本足以启动机制实验，但不证明跨服务器伸缩性。后续多服务器验证须记录 CPU、内存、网络和事件通道条件。基线与新策略可以顺序使用同一组设备，独立重复运行，无须首轮申请两倍设备做同缓存域内的逐请求 A/B。

控制器和压测客户端使用 CPU，不额外申请 NPU。CPU/RAM 的确切额度由 tokenization、事件量与压测规模测量确定；避免客户端或控制器争用 CPU 而被误认为路由效果。

### Qwen 模型建议与容量核验

首选候选为 **Qwen/Qwen3-8B，BF16，TP=1**；第二档候选为 **Qwen/Qwen3-14B，BF16，TP=1**。选择常规 dense 模型先验证路由，暂不引入 MoE、多模态或混合注意力布局。若既有验证环境对 Qwen2.5-7B-Instruct 更稳定，可以用它完成首轮接口核验，再独立验证 Qwen3。

官方支持矩阵列出 Qwen3-Dense 在 A2/A3 上的 BF16、前缀缓存和 chunked prefill 支持，但不证明用户当前芯片、镜像和参数组合已经支持。先固定 vLLM、vLLM-Ascend、CANN、torch-npu 与驱动组合，通过功能测试后再冻结。[Ascend 模型矩阵](https://docs.vllm.ai/projects/ascend/en/latest/user_guide/support_matrix/supported_models.html)、[Ascend Qwen3 教程](https://docs.vllm.ai/projects/ascend/en/latest/tutorials/models/Qwen3-Dense.html)

| 模型 | BF16 权重粗估 | 使用理由 | 必须保留的限制 |
|---|---|---|---|
| Qwen3-8B | 约 16–18 GB，按参数量 × 2 bytes 估算 | 首轮候选，权重之外留出较多运行与 KV 空间 | 不是实测总显存；单设备运行仍需核验 |
| Qwen3-14B | 约 28–32 GB，同一粗估口径 | 第二档容量与计算成本验证，不只验证一个小模型 | 若 KV/运行余量不足，用较小上下文或 TP=2；不要默认 60G 就足够所有并发 |
| Qwen3-32B | 仅权重已约 64 GB 级 | 后续多设备候选 | 不建议在约 60G 单设备上以 BF16 作为首模型；并行/量化方案另行验证 |

上述为 GB 级粗估，不是设备可用 GiB，也不包含运行时、图缓存、算子临时空间和权重额外副本。KV 容量以引擎启动日志的实际 block 数及配置为准，不用“显存减权重”直接作为承诺。

普通全注意力、BF16 K/V、TP=1 的简化 KV 估算为 `2 × 层数 × KV heads × head_dim × 2 bytes/token`。官方配置中 8B 为 36 层、8 个 KV heads、head_dim=128，得到约 144 KiB/token；14B 为 40 层、同样的 KV heads/head_dim，约 160 KiB/token。单条未共享的完整 32K 上下文分别约 4.5 GiB、5 GiB KV。这不包含引擎对齐、布局等开销，且共享块不能按每个请求重复相加。[8B 配置](https://huggingface.co/Qwen/Qwen3-8B/blob/main/config.json)、[14B 配置](https://huggingface.co/Qwen/Qwen3-14B/blob/main/config.json)

上下文长度首轮暂定 16K 和 32K 两档，均指输入加输出的总预算；不默认启用额外 RoPE 扩展。主模型先用明确的 non-thinking 配置，另设长输出/thinking 压力验证；所有策略使用相同生成配置，不能以缩短输出换容量。[Qwen3 模型说明](https://huggingface.co/Qwen/Qwen3-8B)

## 为什么这个问题重要

重要性不能只写成“KV cache 很重要”或“命中率能降低 TTFT”。本项目值得做，必须同时满足以下四层理由。

### 一 这是常见工作负载产生的持续问题，不是人为构造的缓存角落案例

长上下文、多轮对话、共享工具描述和 agent 工作流让 prefix reuse 成为常见服务特征，但复用并不均匀。Preble 对五类 workload 的研究中，85%–97% 的 prompt tokens 可与其他请求共享，而且 prompt 比输出长 37–2494 倍；这使错误落点带来的重复 prefill 很昂贵，同时也使纯亲和容易形成热点。[Preble，ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/file/5bc342f48de8264779952fac378f96dc-Paper-Conference.pdf)

Mooncake 的真实 conversation 与 tool/agent traces 平均输入约 8.6K–12K tokens、平均输出约 182–343 tokens，cache ratio 为 40%–59%。这些数据说明长输入和可复用状态已足以影响服务容量，而不是只影响一次微基准的 TTFT。[Mooncake，FAST 2025](https://www.usenix.org/system/files/fast25-qin.pdf)

ATC 2025 的大规模生产研究进一步发现，KV 复用具有明显偏斜：约 10% 的 KV blocks 贡献 77% 的复用；不同请求类别的复用概率和时间分布又明显不同。这说明“所有前缀一视同仁”或只按最近访问处理，难以稳定保护真正有后续价值的工作集。[KVCache Cache in the Wild，ATC 2025](https://www.usenix.org/conference/atc25/presentation/wang-jiahao)

### 二 损失对象是固定资源下的服务容量，而不只是一次 cache miss

被挤出的 prefix 需要重新 prefill，占用的计算还会延迟正在进行的 decode。Sarathi-Serve 的实验中，未经切分的 prefill 与 decode 混合可使 TBT 相对 decode-only 最坏增加 28.3 倍；DistServe 则说明 prefill/decode 干扰会迫使系统在 TTFT 与 TPOT 之间取舍或过度配置资源。[Sarathi-Serve，OSDI 2024](https://www.usenix.org/system/files/osdi24-agrawal.pdf)、[DistServe，OSDI 2024](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin)

因此，一个 prefix 被重复构建的代价不只是该请求多等一次 prefill，还包括：

- 占用本可用于其他请求的加速器时间；
- 干扰已有 decode，造成流式输出停顿；
- 增加 KV 创建与淘汰，使后续请求继续 miss；
- 在高负载下提前触发 SLO knee，降低单位设备可承载的达标请求率。

项目主指标采用 TTFT/TBT 双约束下的 SLO goodput，正是为了把这些连锁损失计入，而不是只优化 hit rate 或平均 TTFT。

### 三 两种朴素解法会走向相反的坏结果

只做均匀负载会把相同 prefix 分散到多个副本，增加重复计算并缩短每个副本上的复访频率；只做缓存亲和又会把流量偏斜映射成队列偏斜。Preble 和 LMetric 都把 reuse–load 冲突作为核心问题；CacheRoute 的实验进一步显示，较高 hit rate 并不自动意味着更高容量：其低复用 32B 负载中，残余负载偏斜会减少甚至抵消 affinity 收益。[LMetric，OSDI 2026](https://arxiv.org/abs/2603.15202)、[CacheRoute](https://arxiv.org/html/2608.19677)

缓存保护同样不能无限加强。PrefixShield 在受控实验中证明，一次性 KV 创建可以严重污染其他组的缓存，也证明引擎内保护能够改善该问题；但保护和配额若不结合全局落点，仍可能把低复用流量集中到少数实例，造成等待或闲置。[PrefixShield](https://arxiv.org/html/2608.01657)

由此可见，本问题不是简单追求更高命中率，而是在两个失败方向之间寻找可测的运行区间：

```text
过度分散 ── 重复 prefill / 缓存重建
      可用运行区间
过度聚集 ── 热点队列 / TBT 恶化 / 公平性损失
```

### 四 现有强系统说明机会存在，也抬高了项目成立门槛

现有 KV-aware routing 已经能取得很强效果。LMetric 在真实 workload 上相对 vLLM-v1 和生产 scheduler 分别报告 TTFT 降低 92%/52%、TPOT 降低 21%/20%；Mooncake 在真实 traces 中报告满足 SLO 的有效容量提高 59%–498%。这些结果证明协调 cache 与 load 确实能影响端到端容量，也意味着本项目不能靠“支持 prefix affinity”或“比 round-robin 好”证明价值。[LMetric](https://arxiv.org/abs/2603.15202)、[Mooncake](https://www.usenix.org/conference/fast25/presentation/qin)

本项目仍可能有工程价值的原因，是首版约束与完整系统不同：目标是在不重写推理引擎和存储系统的前提下，利用现有 vLLM/SGLang 类接口协调全局请求落点，并显式约束混合流量、公平性和退化风险。若成熟原生路由经过合理配置后已经消除目标环境中的损失，正确结论应是交付配置、观测或小型扩展，而不是强行建立一个新平台。

### 重要性的最简表达

> **Prefix caching 只有在可复用 KV 留在未来请求能够到达的副本上时才产生价值。混合负载使请求落点同时决定缓存存活和执行拥塞；错误的长期分布会把有限加速器时间消耗在重复 prefill，或把复用收益换成热点与不公平，最终降低 TTFT/TBT 约束下的服务容量。**

## 已有系统覆盖和剩余机会

“没解决好”在本版中表示特定条件下仍可能存在可测损失，不表示系统整体失败。文档没有写某项功能，也不能证明实现中没有。

| 工作 | 已经解决或支持什么 | 本项目应验证什么 |
|---|---|---|
| vLLM APC | 块级精确前缀复用、共享和回收 | 外部请求分配是否仍导致可减少的缓存重建；本地高占用不是直接证据 |
| SGLang 与其路由层 | 前缀复用、缓存感知选点及负载保护；部分部署支持优先级淘汰 | 在合理配置和原生保护启用后，分布式软分配是否还有增量收益 |
| Dynamo 默认 KV 路由 | 缓存层级、prefill/decode 负载、请求生命周期和队列 | 混合流量造成的持续缓存损失能否用现有调参解决；不能预设它只看瞬时请求数 |
| LMetric | 使用新增 prefill tokens 和当前 batch size 联合选点，并研究异常条件 | 其准确状态与回退启用后，额外干扰管理是否仍值得 |
| Preble | 全局前缀树、淘汰重算成本、重平衡和前缀复制 | 本方案是否超出已有 E2 思想，且能在当前公开接口下交付 |
| CacheRoute | 周期规划热前缀的目的地与数量 | 变化的前缀大小、冷流量竞争和渐进调整是否改善其边界 |
| ThunderAgent | 程序级工作集准入和重分配；Dynamo 开发版有原生插件 | 适用于一般混合请求的计量和分配是否优于已有机制；不重新宣称程序感知是空白 |
| PrefixShield 和工作负载感知淘汰 | 在缓存管理层改善保留与回收选择 | 改变请求落点能否减少进入各缓存域的竞争，或与原生保护互补 |
| Mooncake 等完整 KV 系统 | 全局缓存、调度、传输及副本管理 | 能否复用其方法；若没有同条件部署，不宣称击败整个系统 |

关键核查依据：[vLLM APC](https://docs.vllm.ai/en/latest/design/prefix_caching/)、[SGLang 原生保护](https://docs.nvidia.com/dynamo/latest/knowledge-base/modular-components/backends/sg-lang/agents-on-sg-lang)、[Dynamo 路由模型](https://docs.nvidia.com/dynamo/dev/knowledge-base/modular-components/router/routing-concepts)、[LMetric](https://www.usenix.org/conference/osdi26/presentation/zhang-dingyan)、[Preble](https://arxiv.org/html/2407.00023)、[ThunderAgent](https://docs.nvidia.com/dynamo/dev/agents/thunder-agent-program-scheduler)。

其中两个事实直接影响规划：Preble 已经把淘汰后重算纳入成本；Dynamo 原生 ThunderAgent 插件已经按程序做容量管理，但官方说明其逻辑 token 估计不是物理 KV 占用，且未去重共享前缀。后者提供计量改进的启发，不证明该插件性能不足。

### 可以检验的剩余缺口

1. **持续影响没有充分兑现为请求分配。** 一次性新缓存造成的后续重算，是否在当前强配置下仍稳定发生？
2. **共享与隔离的取舍仍需人工配置。** 静态分池能否消除干扰，流量变化后是否又造成排队或闲置？
3. **本地保护与全局落点是否互补。** 本地优先级淘汰已经打开后，改变落点还有多少作用？
4. **插件接口是否足以实现有效治理。** 仅使用可获得的状态和动作，能否获得稳定收益？

这四项是待验证假设。若已部署系统在目标负载下充分解决它们，应选择现有系统配置或小补丁，不以新增平台为目标。

## 系统特色和借鉴边界

拟建立的工程特色是：**感知不同流量造成的缓存收益与创建压力，在竞争出现时调整请求分布，并用整体及分组服务结果约束调整。**

| 特色 | 与普通路由相比关注的内容 | 成立条件 |
|---|---|---|
| 缓存干扰计量 | 当前请求之外，近期缓存移除与重建的持续影响 | 状态可靠，且干预确认损失可减少 |
| 动态软分配 | 优选集合可以变化，不永久划分冷热池 | 优于调参和静态分池，而非制造新热点 |
| 副本收益管理 | 副本满足需求且值得占用，不盲目最少或最多 | 能看到共享块与副本，建立成本可控制 |
| 服务质量约束 | 保护缓存时不长期牺牲低复用、长请求或低频组 | 分组延迟、完成率与等待约束通过评测 |
| 能力分级插件 | 基础路由独立成立，增强动作按能力启用 | 支持版本有契约测试与明确降级行为 |
| 可解释运行闭环 | 能说明触发调整的信号、执行动作和结果 | 观测开销有界，收益不是只看命中率 |

以上是产品目标，不是已经证明的原创贡献。可以借鉴 E2 的成本思想、生产研究的类别统计、既有工作集分析和稳定放置方法。需要由自己的实现、组合取舍、低接入成本和实验结果建立价值，不按论文的新颖性门槛决定是否值得发布 GitHub。

## 优化目标和收益口径

主目标已经由用户确认：在固定模型、NPU/GPU 硬件、缓存预算及预先规定的服务目标下，提高可持续的达标服务能力；分类延迟、完成率和控制开销作为约束。

Goodput 定义为单位时间内完成且满足所配置 SLO 的请求数；同时测量满足各类目标时的最大可持续输入速率。TTFT 从客户端发出请求计起，包含入口等待；流式输出除平均 TPOT 外还要测 token 间停顿。不同业务可以配置不同 SLO，但所有对照使用相同配置。

TTFT 和生成停顿的确切阈值、百分位与允许违反比例仍待确认。客户端可能一次收到多个 tokens，SSE chunk 间隔不能未经说明等同逐 token TBT；区分用户可见输出 gap 与可得的引擎 token/iteration 时间。主实验先校准原生服务能力，再冻结统一服务合同；不得各策略使用自己的 SLO，也不以超时/拒绝或延后下一轮制造优势。

| 收益层面 | 可能的改善 | 必须报告的证据 |
|---|---|---|
| 计算 | 少执行公共前缀的重复 prefill | 实际命中、新 prefill、近期前缀重建及可得的计算时间 |
| 缓存 | 有收益的工作集存活更久，少建低收益副本 | 唯一驻留块、副本、移除后复用和重建；不能仅报告占用下降 |
| 服务容量 | 同样 GPU 服务更多达标请求 | offered-load 阶梯、goodput、积压趋势和失败率 |
| 延迟 | TTFT 更低或波动更小，减少长 prefill 导致的输出停顿 | 整体和分类的 p50/p95/p99 TTFT、TPOT/TBT |
| 公平 | 复用不同的请求都能得到合理服务 | 分组吞吐、等待、超时、完成率，冷流量不得饿死 |
| 运维 | 减少手工分池与亲和参数调整，定位缓存损失原因 | 安装步骤、配置量、行为解释、兼容及故障测试 |
| 后续分层缓存 | 降低不值得的加载、复制和带宽竞争 | 同存储预算下的传输字节、加载等待和端到端收益 |

缓存命中与占用均是解释指标。引擎通常可以回收空闲历史 KV；高缓存占用不必然限制新请求。减少副本还可能降低热点并行服务能力，须看净效果。

若减少的是 decode 内核瓶颈之外的少量 prefill，入口插件可能没有明显收益。单副本、无复用、低并发、缓存工作集轻松容纳或已经使用有效硬隔离时，也可能只产生开销。

## 机制设计和动作边界

### 一 观察收益与创建压力

按前缀块或有界前缀族维护近期复用、驻留、建立、移除及重建记录，结合请求长度、输出进展、队列和服务结果。请求类别和 session ID 可以辅助，但不是精确缓存身份。

不能把长请求自动认作冷流量。公共头部和独特后缀分别计量；同一实例内共享块按物理驻留去重，跨实例副本仍有实际占用。预计输出增长与历史缓存也要区别处理。

保留有界的近期移除记录，可以识别“过去缓存过、现在又在计算”的前缀。此类重建不自动等于可避免损失：有些淘汰是必要的，有些移除来自重启或清理。用干预实验确定改善空间；仅凭时间相关性不得断言某个请求导致另一组受损。

### 二 建立软优选集合

慢路径为有足够复用证据的前缀族维护少量优选实例。持续创建新 KV 的流量，在满足延迟与资源约束时优先进入预计缓存损失更小的实例。不同集合可以重叠，空闲资源可以被借用。

“缓存压力预算”是决定优先落点的软目标，不是 GPU 物理分区、精确 block 配额或保留保证。全局负载高时允许越过优选集合；没有收益证据时保留普通强路由。

首个原型采用小步规则即可：观察到反复重建且当前队列允许时，调整少量流量；冷流量排队变差时扩大候选集合；热前缀形成拥塞时增加目的地。先证明动作有效，再决定是否需要更复杂优化器。

### 三 快路径保护当前服务

每次请求先满足模型、隔离域、健康和配置兼容性；读取近期状态快照，在优选集合与全局可用实例之间进行选择。沿用已验证的 KV/token-load 策略做短期选点，避免对每个请求同步扫描全部缓存。

选择应考虑当前未命中 prefill、活跃 decode、已分派未完成请求，以及入口等待。对预计将明显违反服务目标的软亲和关系允许打破；状态不可信时停止使用对应缓存收益。

有界队列与背压属于必要工程保护，但不能通过延后冷请求、减少完成量或增加拒绝来制造性能优势。设置最大等待与公平调度，保留用户业务优先级；缓存复用收益不能自动变成业务优先级。

输出长度只使用可用提示和统计估计，不能把 max_tokens 当实际输出；记账是软件预测，最终分配由引擎负责，不能承诺避免所有抢占或 OOM。

### 四 渐进调整副本与亲和

已有热前缀拥塞时，让一部分真实请求进入另一实例，按需形成新副本。观察到收益后再扩大比例。减少优选目的地是停止继续往那里导流，不代表立刻删除已存在的缓存。

保存现有有效映射，限制每次变化规模，设置保持时间和不同的进入/退出门槛。评估建立缓存成本及调整后的整体结果，不依据一个短窗口立刻来回切换。

这不要求准确预测下一批请求。历史访问仅用于估计持续性；当前拥塞可以直接驱动短期分流。更昂贵的主动复制必须通过额外收益门槛、资源预算和后端能力审计。

### 五 按能力增强本地缓存与生命周期

保留原生淘汰作为基础。后端支持时，可以使用独立缓存保留提示、会话结束通知或明确的缓存管理接口；控制器不替换其 allocator。

SGLang 的 priority 可同时影响请求调度和缓存淘汰，不能为了保护高复用缓存而擅自抬高业务调度优先级。只有语义符合用户服务合同，或接口提供独立控制时，才允许启用。会话结束也不代表所有共享前缀都能删除，必须依赖后端的引用与共享规则。

### 六 观察结果并降级

对比调整前后总体与分类的服务结果，检测新热点、冷流量损害、状态陈旧和控制振荡。达到风险阈值后冻结慢路径、取消未开始的增强操作并恢复验证过的普通路由。

降级不能撤销已经执行的重算、复制和缓存淘汰，不构成所有未知负载的无退化保证。影子选点用于验证接口和开销；策略收益通过完整 replay 或隔离资源池测试。

## 必要组件和初步架构

这些是逻辑模块，不要求拆成独立微服务。首版一个控制器进程、一个后端适配器即可。

| 组件 | 输入与职责 | 输出与边界 |
|---|---|---|
| 请求接入与生命周期 | 请求、隔离域、截止时间、流式进展、取消与完成 | 规范化请求和生命周期；不改 prompt 及生成语义 |
| 后端适配与能力协商 | 版本、模型、布局、实例/rank、事件、指标和可选动作 | 支持能力与可信状态；未实现项标记不可用 |
| KV 与负载状态目录 | 存储/移除事件、已分派请求、容量和负载更新 | 有界快照与前缀位置；区分 ready、pending、unknown |
| 工作负载与干扰分析 | 近期复用、创建、重建和服务结果 | 有界前缀族、收益/压力估计、置信度及诊断 |
| 慢路径放置控制 | 干扰证据、实例能力、延迟及公平目标 | 版本化优选集合、导流比例和变化预算 |
| 快路径决策与等待控制 | 请求、快照、计划和服务约束 | 选点、有限等待、回退；不操作运行中 decode |
| 运行保护与观测 | 决策、真实结果、错误、状态质量和配置 | 指标、解释、暂停/降级、管理接口和灰度开关 |
| 离线评测与契约测试 | 可追溯流量、固定配置、事件及故障脚本 | 可复现实验、基线、消融、能力与兼容测试 |

工作流程是：请求接入读取快照和最新计划后选点；后端反馈更新状态；分析与慢路径在后台生成新计划；保护模块独立检查服务退化。慢路径不得阻塞每次请求，事件积压不得无界增长。

第一版单控制域减少重复记账风险。第二阶段才支持多个路由副本：必须有计划版本、控制权租约或唯一规划者，以及明确的生命周期同步。多个路由器各自读到空闲并不代表可以同时消耗同一份余量。Dynamo 已提供相关活动状态同步选项，接入它时应复用宿主机制，不再重复预留。[Dynamo 多副本状态管理](https://docs.nvidia.com/dynamo/dev/knowledge-base/modular-components/router/router-operations)

| 有限主动复制与预热 | 后续增强 | 缩短确有需求时的新目的地冷启动 | 持续收益证据、带宽/显存预算和失败回收 |
| 多路由副本与 HA | 发布成熟期 | 控制面可用性和吞吐 | 控制权、同步、状态重建和降级测试 |
| P/D 分离适配 | 后续场景 | 扩展已有服务形态 | 分离路由与传输依赖经独立验证 |
| 全新本地淘汰、运行中迁移、自动扩缩容 | 不列为当前必做 | 可能拓宽动作空间 | 仅当实测表明它们不可替代且接入成本可接受 |

## 插件契约与兼容性确认

### 易用性优先的交付要求

企业和个人易上手是已确认的产品要求。小型 hook 是引擎里的“观测接头”，用于报告缓存建立/移除、请求进展等状态；适配模块负责把这些状态转换为插件认识的格式。它们不是要求用户手写算法，也不代表需要修改 attention kernel、allocator 或淘汰策略。

建议交付方式如下；容器/安装包权限尚待用户确认，以下为交付目标，不是当前已具备功能：

1. 用户保留受支持的原生推理服务，在配置文件中填写后端地址、模型和访问凭据；应用主要修改 API base URL。
2. 优先使用已有健康、metrics、缓存事件接口；需要开启接口时提供完整且版本匹配的启动配置。
3. 仅在缺少必要状态时考虑可选观测适配器，由项目提供版本化安装包或匹配镜像及卸载说明；不让用户手动编辑 site-packages 或维护源码 fork。是否采用仍须接口审计和安装权限确认。
4. 预检明确报告“完整优化”“基础路由”或“不可用”的原因。原生接口已经足够时不安装额外模块；状态不足时停用依赖该状态的干扰控制，不默默假装精确命中。
5. 提供配置样例、健康检查、基准脚本、指标面板、认证/TLS 部署说明及回退操作；不默认收集原始 prompt，尊重租户隔离。

个人可以从两个已有服务端点开始；只有一个副本时可做转发和诊断，不宣称获得分布式放置收益。4 个 NPU 是本项目实验推荐，不是所有用户的安装门槛。

“无需手改源码”不等于无需安装 CANN/驱动、设置引擎参数或重启以启用事件；这些由预检和文档明确说明。自动降级也不等于自动重启原生引擎或保证所有负载无退化。首个易用版不强制 Kubernetes、Redis、全局 KV 存储或专门 decode kernel；企业 HA/集群部署作为后续层级。

### 接入形态

优先开发外部网关/sidecar 形态，策略核心与后端适配分离。需要嵌入已有路由器时，使用宿主正式策略接口，避免双重路由、双重队列和双重记账。

Dynamo 自定义策略主要替换 worker 选择，宿主继续拥有 discovery、eligibility、queue、reservation 和 accounting；自定义策略通常按同版本构建链接，不能将其宣传为任意版本可热加载。纯 ranking 接口也未必提供干扰分析所需的全部事件与反馈。[Dynamo 策略边界](https://docs.nvidia.com/dynamo/dev/knowledge-base/modular-components/router/write-custom-routing-strategies)

### 能力分级

| 模式 | 接入条件 | 可承诺什么 |
|---|---|---|
| 通用接入 | OpenAI-compatible 请求接口、基础健康与负载 | 路由、转发与有界等待；缓存只能近似估计 |
| 引擎感知 | 指定版本的缓存事件、容量、请求或指标反馈 | 更可靠的缓存干扰计量和请求放置 |
| 缓存协同 | 受支持的保留、加载或复制接口 | 在验证的层级及范围内执行增强动作 |

广泛 API 接入不等于全部优化能力广泛可用。关键能力缺失应降级，不让用户以为强优化已开启。

### 必须审计的状态与动作

状态最少包括实例/rank 身份及重启代次、模型与缓存配置、观察时间、缓存块层级/链关系、容量、负载和请求生命周期。`BlockStored` 不等于所有请求访问记录，事件也未必能精确归因到请求；访问和创建计量需要结合匹配及后端反馈，缺失时标记估计。[vLLM KV 事件](https://docs.vllm.ai/en/latest/api/vllm/distributed/kv_events/)

路由计划最少记录优选集合、有效期、版本、变化预算和降级条件。可选数据操作必须有 operation ID、接受/拒绝、执行状态和最终回执；不能通过查询函数暗中执行有副作用的预留或复制。

## 规划风险和必须修正的假设

| 风险或错误假设 | 本版要求 |
|---|---|
| 只要高占用就说明缓存干扰严重 | 区分活跃不可回收状态与空闲可回收缓存，结合重建和服务损失 |
| 缓存移除后重算都能避免 | 排除必要淘汰、重启和清理，用分配干预验证 |
| 冷流量应该全部集中到一个实例 | 软分配、借用和拥塞逃逸；比较总服务结果 |
| 热缓存必须永久保留 | 路由不能保证驻留，低收益或过时缓存应允许回收 |
| 简单相加热度、长度和请求数就够 | 先分清物理占用、计算时间和延迟约束，避免无单位混加 |
| 从历史频率准确知道未来请求 | 使用短期统计和置信度，昂贵操作保守启用 |
| 业务标签或文本相似就是缓存身份 | exact token/block 链与配置域决定有效性，不改用户 prompt 以增加命中 |
| 可以替换任意后端的淘汰算法 | 基础路由不接管淘汰；可选接口按版本验收 |
| cache priority 与业务 priority 可随意互换 | 尊重用户合同，检查是否同时改变引擎执行顺序 |
| 估计的软件预算等于显存/带宽保证 | 明确它只是路由记账，最终资源控制属于后端 |
| 回退可以保证任何负载都无退化 | 限制损失并测试边界；已经执行的状态变化不可撤销 |
| HTTP 返回异常可以随意重试 | 跟踪是否已接纳/已输出；流式输出开始后不得透明换副本重启 |
| 状态同步即可做到强一致预留 | 多控制器需要清晰权属与幂等释放，允许状态不确定时保守降级 |
| 哈希元数据没有隐私风险 | 尊重租户盐、访问控制、传输安全；不暴露跨租户缓存查询和原始 prompt |
| 小模拟即可证明超过强系统 | 仿真用于筛选，真实 GPU replay 与公平对照才支持性能主张 |

还要限制前缀族、历史、ghost 记录与指标标签基数，防止长尾流量让控制器内存或 Prometheus 指标失控；避免每请求全树扫描。提示词渲染和 tokenization 必须与后端一致，成本计入路由开销。

## 验证方案与验收条件

### 先验证根因

| 假设 | 验证方法 | 通过或失败的含义 |
|---|---|---|
| 强基线下仍有缓存干扰损失 | 固定流量，比较混合运行和改变落点后的缓存重建与服务结果 | 有信号才需要控制；不是看到淘汰就通过 |
| 路由权限足以减少损失 | 不修改淘汰，仅小比例改变落点 | 若只有修改引擎才有效，重新评估插件定位 |
| 动态分配比静态分池值得 | 稳态、流量比例切换和热点漂移 | 若静态分池已充分解决，优先交付简单配置工具 |
| 原生保护之外还有增量 | 同后端开启合理优先级/会话保护，再加路由控制 | 新机制不应以关闭已有优秀功能换收益 |
| 收益不是牺牲一类流量 | 同输入、同服务合同，报告全部与分类指标 | 冷流量恶化、拒绝上升或任务完成量下降须计入 |

### 强基线和比较原则

普通对照包含 power-of-two、token-load 和原生 cache-aware；强对照选择固定版本、适合目标部署的 Dynamo KV 路由与 LMetric 原实现或验证过的移植。若无法获取原始指标，明确移植差异，不把一个代理乘法公式等同原系统。

首轮全部采用相同 vLLM-Ascend 服务实例，APC 与合理的原生优化保持一致，验证插件增量。Dynamo 等系统须先确认可在当前 NPU/软件组合上接入，再作为直接对照；不能因 CUDA 论文或功能说明就假定 NPU 可部署。算法移植仅代表对应策略实现，不等于原系统复现；不可得的强对照需列为限制，不据此宣称全面超过现有系统。

额外基线必须包含调过参数的缓存路由、静态业务分池、最简单的亲和保持，以及后端实际支持的缓存保护。Preble-style 与 CacheRoute-style 实现可帮助分析，但自行重实现不得宣称复现原论文全部系统性能。

优先做同一引擎下的插件增量对照。不同整栈之间的对比另行报告，不能把内核、batching、缓存精度或存储容量差异归功于路由。

### 负载与资源矩阵

#### 公开数据与工作负载候选

公开内容数据不自动具有到达时间、真实前缀复用或工具生命周期；内容、到达过程、输出生成和复用身份分别记录。优先选能暴露工程机会的自然负载，同时保留负对照，不只挑选成功 trace。

| 资料 | 第一阶段用途 | 可能暴露的机会 | 不能据此声称什么 |
|---|---|---|---|
| [WildChat-1M](https://huggingface.co/datasets/allenai/WildChat-1M) | 候选多轮对话内容；单轮与多轮分层 | 会话前缀增长、重复访问间隔、混合长度 | 公开对话不是本项目真实生产流量；含 timestamp 不代表有完整可直接重放的系统到达过程 |
| [LongBench v1](https://github.com/THUDM/LongBench/blob/main/LongBench/README.md)、[任务构造](https://github.com/THUDM/LongBench/blob/main/LongBench/task.md) | 长文档问答、摘要及代码内容；先筛选模型上下文可容纳的子集 | 共享文档与独有问题共存时的缓存干扰 | 长输入不等于共享前缀；没有相同 context 的样本不得当作自然复用 |
| [BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html) | 后续 tool/agent 内容候选，固定具体版本与子集 | 重复工具定义及多轮增长，需核验实际 token overlap | 工具调用 benchmark 不等于在线 agent trace；若构造重复 schema，须标为半合成 |
| [BurstGPT](https://github.com/HPMLL/BurstGPT)、[Azure LLM 2023](https://github.com/Azure/AzurePublicDataset/blob/master/AzureLLMInferenceDataset2023.md) | 到达过程、长度/突发性参考 | 流量比例变化与突发下的放置稳定性 | 这些统计/长度 trace 没有可直接还原的 prompt 文本，不能恢复真实 prefix 身份或缓存命中 |
| 可复现机制生成器 | 扫描前缀长度、复用间隔、长后缀与输出增长 | 验证因果机制和策略边界 | 受控构造只支持机制结论，不能独立证明普遍生产收益 |

第一轮推荐内容组合为 WildChat 多轮/单轮 + LongBench 长文档内容，先分别测试，再做明确标注的混合。筛选相同文档后再核验渲染后的精确 token 前缀；若人为重复文档或重新排列 prompt，归入半合成实验，不声称数据集本身具有该复用率。变化后的 prompt 对所有策略完全相同，正式插件不能为了命中而改业务 prompt。

BurstGPT 等资料提供到达/长度参考，与其他内容结合后必须命名为“公开内容 + 公开 trace 驱动的半合成负载”，说明映射、缩放与保留/丢失的相关性，不把任意跨数据集拼接宣传成真实 trace。trace 中记录的输出长度仅用于负载生成或事后分析，不可泄露给路由器当作已知未来。

多轮采用两种独立报告的模式：固定历史内容重放保证策略间输入一致，但与本次模型生成的历史可能不同；闭环模式把本次生成加入下一轮，保留会话依赖与思考间隔并报告任务完成量，不假装两种模式完全相同。会话可能存在重复累计历史，先检查去重，不能把同一记录多次出现算成自然热度。

负载至少覆盖共享前缀 + 低复用长上下文混合、多轮增长、热前缀突发、复用/流量比例变化，以及低复用、低缓存压力、短输入长输出。自然容量先行；人为缩小缓存、强制固定输出或禁用 EOS 的设置仅作为单独标记的机制实验，不能成为主结果唯一来源。

发布前保存数据版本、许可/内容使用条件、过滤与去重规则、抽样清单和种子；公开聊天仍可能含敏感内容，仅提取实验所需文本与轮次，不保留无关 IP/位置/header 信息，检查脱敏和内容过滤。不默认把完整聊天内容再分发到 GitHub。模型质量不是主指标，但不能通过删改输入或缩短回答改变任务来获得容量优势。具体子集、占比、到达参数和 SLO 待环境核验后冻结。

至少覆盖共享模板、多轮增长、真正有前缀复用的长文档请求、coding/tool 流量，以及无复用和 decode-heavy 负对照。混合时保留每客户端长度相关性、轮次依赖、工具间隔和阶段变化；不随机拼凑 prompt 长度与到达间隔来代表生产。ServeGen 的 per-client 建模可以用于生成可追溯负载。[ServeGen，NSDI 2026](https://www.usenix.org/conference/nsdi26/presentation/xiang-servegen)

覆盖自然缓存容量及压力变化、不同复用比例、不同前缀大小、稳定/突发/漂移和至少两个模型或配置档次。人为缩小缓存可以解释机制，但不能作为唯一主结果。华为 NPU 平台已明确，建议首批 4 个设备、至少 2 个可路由实例；型号、版本和可独占资源仍待确认，不据此承诺工期。

对照保持输入流量、总 NPU/GPU、KV 总预算、模型精度、引擎配置、SLO、初始状态和预热方式一致。报告预热及调整过渡成本，不能只选最有利的稳态窗口。对多轮业务同时报告闭环任务完成时间，避免将少做下一轮误认为负载下降。

### 必做消融与故障测试

- 同一强路由，增加观测但不改变选点，测基础开销。
- 静态软集合与动态软集合，区分配置收益和控制收益。
- 固定副本与按需渐进形成副本，验证热点改善及创建成本。
- 有/无近期重建反馈，验证计量是否有用。
- 有/无拥塞逃逸与公平限制，展示保护机制的代价。
- 可选保留、加载、复制各自开关，避免把全部收益归给核心。
- 状态丢失、事件乱序/延迟、worker 重启、取消、超时、控制器失效和负载突变。

影子选择只能检验接口、预测及开销，不会改变实际缓存分布。性能比较使用隔离副本池或完整独立 replay；同缓存域内逐请求 A/B 会互相影响。重复运行并报告不确定性。

### 建议验收门槛

下列数字是投入与发布的候选门槛，不是预测收益；在硬件、服务合同及负载确定后再冻结。

- 至少两类代表性负载及一类混合负载，相对最强可用基线取得约 10%–15% 或更高的达标容量改善，并能解释损失减少来源。
- 无复用、低压力及 decode-heavy 等常见负对照，吞吐和关键尾延迟退化目标不超过约 5%；同时公开置信区间和未通过项。
- 各类请求达到既定服务合同，不能用不对等拒绝、延后长请求或牺牲任务完成量获得优势。
- 路由 CPU、内存、tokenization、事件处理和 p99 延迟开销满足事先确定的预算。
- 第二适配器与版本契约测试通过，发布无需维护大规模引擎 fork。

若优势只在构造的极端污染、小缓存或某单一 trace 中出现，或成熟基线调参即可取得相同效果，停止扩展当前主线，保留有用的观测/配置工具或提交上游补丁。

## 实施阶段和当前决策

### 方法设计的分工与尚未冻结项

| 决策部分 | 可借鉴的方法 | 本项目必须自行落实 | 当前状态 |
|---|---|---|---|
| 当前请求选点 | 原生 KV/load 路由、LMetric、DualMap 的亲和与 SLO 思想 | 用可得状态实现可信强默认策略；当前负载保护与宿主权属一致 | 待接口核验后选择，不同时拼接全部公式 |
| 缓存损失计量 | Preble 的淘汰重算成本、工作负载类别统计、近期移除记录 | 共享块去重、创建/复用/重建计量、置信度与故障排除 | 核心待设计；先确认事件是否足够 |
| 持续放置与副本需求 | CacheRoute 放置规划、既有亲和/按需复制 | 软优选集合、借用条件、低扰动调整与净收益反馈 | 核心待设计；先用可解释的小步控制验证动作 |
| 生命周期负载保护 | 已有 decode tracking、输出统计及公平调度思想 | 使用实际进展更新，不把 max_tokens 或离线真实 OSL 当已知输出 | 核心约束，模型精度与阈值待实测 |
| 本地 cohort/batching/kernel 协同 | 专项补充中的相关工作 | 验证入口能否影响 batch，以及 Ascend 版本是否提供可用能力 | 可选增强，不作为首版依赖 |
| 接入、观测与评测 | 原生协议、事件、指标、标准测试 | 安装预检、能力报告、可回退契约和公平可复现实验 | 标准工程，从首轮建设 |

算法可以随后细化，但必须先明确输入、输出、状态缺失行为、运行开销和验证条件。快慢路径是架构分工，不是独立创新；基本框架已讨论到逻辑层面，尚未完成 API、数据结构与故障契约设计。

### 进入实现前仍需讨论

1. **环境，申请后核验**：NPU 的确切型号和总显存、可用设备/服务器数量、是否能独占，以及新环境的镜像/启动命令和软件版本。当前无需用户回答这些现场信息；现在仅讨论申请规模。
2. **安装方式**：允许容器、可安装适配包，还是只能沿用原有环境；“无手改源码”作为目标，可选观测模块的权限不能默认接受。
3. **服务合同**：TTFT 与生成停顿阈值、百分位/违反比例、业务类别和可接受开销。目标口径已确认，具体数值待单实例校准和用户确认。

上述问题不要求用户选择算法。先完成讨论与文档确认，再进行环境审计、基线和原型；首轮仅申请推荐规模。若强基线下没有自然且足够大的可优化损失、仅路由动作不能改善，或静态简单配置已充分解决，就停止增加复杂机制并重新讨论产品核心，而不是为了保留设想堆功能。

| 阶段 | 交付物 | 进入下一阶段的条件 |
|---|---|---|
| 版本和接口审计 | 一个后端的版本清单、状态能力表、请求/事件契约 | 能可靠识别缓存机会和服务结果；关键缺失有明确降级 |
| 基线与损失确认 | 可重复负载、强基线、重建与延迟分析 | 有自然条件下稳定且足够大的可优化损失 |
| 最小治理原型 | 快路由、分析、有界软集合和拥塞逃逸 | 比静态配置及强默认路由有增量，不靠损害冷流量 |
| 自适应与工程加固 | 渐进调整、公平限制、实例生命周期、诊断与降级 | 变化负载、故障及负对照通过 |
| 兼容和可选增强 | 第二引擎适配、选择性保留/分层/加载功能 | 接入成本可控，增强项各自有净收益 |
| GitHub 发布 | 安装包/容器、示例、能力矩阵、benchmark、限制和版本 CI | 性能主张可复现，支持范围可审计 |

当前确认：问题方向具有工程合理性，核心动作可在插件边界内实现，值得投入受控原型。当前不确认：相对最强现有系统的优势、最佳分配算法、所有后端的增强接口，以及不退化保证。

可以固定的架构决定是策略核心与适配器分离、快慢路径分离、状态和动作分级、保留原生资源管理，以及端到端/分组评测先行。不应现在冻结编程语言、服务拆分数量、深度预测器、跨层迁移协议或完整 KV 存储架构。

本版核心研究问题依次是：如何量出值得治理的缓存干扰，如何用有限的请求分配动作改善它，如何在流量变化时保持净收益和服务公平。后续增强都应回答这条主线中的实际瓶颈，不因功能清单而无限扩展。
